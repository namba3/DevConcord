# Bootstrap・導入・同期・設計判断の統合シナリオ

このディレクトリは、設計書から新規リポジトリを作るBootstrap、既存プロジェクトへの導入・同期について、決定的に検査できる成果物不変条件と、AIエージェントの判断を人が評価するシナリオを分離します。通常のユニットテストは固定のMarkdown出力やモデル文面に依存せず、AIモデルも呼び出しません。

## 決定的な検査

次のコマンドは検証ヘルパーと合成Git履歴の挙動を確認します。実際のAIによる導入・同期結果や設計判断の質を保証するものではありません。

```sh
python3 -B -m unittest tests.integration.test_guidance_assertions -v
```

[`assertions.py`](assertions.py) の再利用可能なチェックは、実際の導入・同期を行う一時環境を用意する半自動ハーネスから利用できます。

- `snapshot_files`、`snapshot_git_state`、`assert_paths_unchanged`、`assert_changes_within`、`assert_source_tree_unchanged`: 既存内容/ファイルモード、許可された差分範囲、資料集側のファイル・HEAD・作業ツリー無変更を確認。
- `assert_issue_records_preserved`: 既存課題IDを含む行の状態・履歴・内容が維持されたことを確認。
- `assert_markdown_links_resolve`: 導入先のMarkdown相対リンクを検査。
- `assert_provenance`: 比較基準SHA、出典ファイル、適用状態、対象ファイル、部分適用/保留理由を照合。
- `assert_idempotent`: 同じ入力への再適用前後のファイルスナップショットが同一か確認。
- `assert_bootstrap_artifacts`: Bootstrapの許可差分、必須成果物、保護ファイル、Markdownリンクを検査。
- `assert_validation_failure_kept_pending`: 検証失敗時に適用済みへ進めず、比較基準SHAも進めていないことを確認。
- `assert_no_undefined_requirement_ids`: タスクから参照するREQ IDが要求表に存在するか確認。
- `check_forward_history`: Git前進関係、同一SHA、巻き戻し、分岐、欠落コミット、浅い履歴の扱いを検査。

ヘルパーの単体テストはこれらのアサーションが誤った状態を検出することを検証します。独立したagent-runnerがないため、実際のエージェント出力へ自動適用した証拠とは区別してください。

## Agent Skillsの決定的な配布・検証テスト

[`test_agent_skills.py`](../test_agent_skills.py) はfrontmatter、Skill名とディレクトリ名、配布内リンク、各業務Skillの参照対象と直接CLIフォールバック、重複参照ファイルの不在、探索先の名前衝突を検査します。[`test_manage_skills.py`](../test_manage_skills.py) は一時リポジトリと一時ユーザーホームに対してdry-run、7通りのagent組み合わせ、段階的agent追加と全体重複状態、許可記録の再実行保持、片側同期拒否・複数側の一括同期、schema 1移行、選択インストール、HTTPS/SSH表記切替、同履歴の別remote拒否、比較基準Git treeとsource hash、前進/巻き戻し/分岐/欠落履歴、dirty source、ローカル編集保護を検査します。参照テストはUser/Project Scopeで要求元Skillと`manage reference`を異なるコミットから導入し、installed参照のsource commit・Skill hashを照合します。source commit/hash改ざん、dirty source、ローカル編集、source identity不一致、旧hash version 1、新hash version 2、欠落履歴を拒否し、検証失敗時にstdout・manifest・導入先Skillが不変であることを確認します。Git treeの通常ファイル・実行ファイル・symlink・submodule・directory・欠落・空白/非ASCIIパス・不正出力と、読み取り失敗・不正UTF-8・権限エラー時のstdout抑止も検証します。User Scopeではdry-runのホーム無変更、他ユーザーSkillsの保護、configの置換・破損・symlink、source checkout移動後の版固定参照と同期、衝突診断、User Scope独立のrecoverも確認します。recover系は複数パッケージ中断、後続対象の外部変更による全体preflight拒否、破損backup、manifest書込後の完了判定、I/O失敗後の再試行を確認し、preflight拒否時の既存Skill・manifest不変をアサートします。テストは実際の `Path.home()` を変更せず、`Path.home()` を一時ディレクトリへ差し替えます。

```sh
python3 -B -m unittest tests.test_agent_skills tests.test_manage_skills -v
```

GitHub ActionsではUbuntu/Python 3.12・3.14とWindows/Python 3.14でSkills管理・文書検証テストを実行し、Git indexから作るsymlink mode等のホスト依存を抑えたfixtureも使います。これはファイルシステム操作とメタデータの決定的なテストです。実際のエージェントがSkillを発見・選択・実行することを証明しません。ローカル実行結果とGitHub-hosted Windows runnerの結果は区別して報告します。

## User Scopeの手動E2E受け入れ

実際のエージェントから個人SkillsやローカルDevConcord checkoutへアクセスできるかを評価する場合は、通常の開発者ホームを使わず、使い捨てOSユーザー、VM、または専用テストマシンで実施します。CIとユニットテストはホームに書き込みません。実エージェントE2Eは通常のCIでは実行されておらず、以下は手動評価の期待条件です。

1. 専用環境にDevConcordをcloneし、`config set-source` でその環境のローカルcloneを登録します。`config show` で正規化されたパスを確認します。
2. User Scopeのdry-runと適用を行い、対象が `~/.agents/skills/` または `~/.claude/skills/` と `~/.devconcord/` のみで、プロジェクトにはmanifestやSkillのコピーがないことを確認します。
3. `validate --scope user` と `doctor --target <temporary-project>` を実行します。DevConcord管理外のSkillと対象プロジェクトのローカルSkillが変更されないことを確認します。
4. 新規の空プロジェクトでは、エージェントをその作業ディレクトリから起動し、Bootstrap Skillにローカル参照元の版固定ガイドと設計書を使わせます。共通参照Skillが選択されない場合も直接CLIフォールバックを使えるか、必須資料が取得できないときに安全に停止するかを確認します。生成先がその対象だけであること、未実装機能・未確認コマンドを断定しないことを確認します。
5. Adoptionでは専用の既存fixtureを使い、既存構成・規約・公開リンク・独自文書とprovenanceを保護し、対象自身の検証方法を使うことを確認します。
6. source checkoutを別の絶対パスへ移動してconfigだけ更新し、元のSkill commitのreferenceとUser Scopeのno-op syncが継続できることを確認します。remote付き・remoteなしの両方を必要に応じて記録します。
7. エージェント、製品版、OS/実行環境、参照できたcommit、共通Skillの選択/直接CLI経路、生成差分、検証結果、未実施項目を記録します。Codex、Claude Code、CopilotでSkill間呼び出しが機能するか個別に確認し、確認していないエージェントは未検証とします。別マシンやクラウドでユーザーのローカルファイルが参照できない場合は、その制約を未対応または別スコープの要件として報告します。

意味的な品質、スキル選択、読者タスク達成をテスト文字列だけで合否判定しません。変更した文書は対象の既存リンク検証・サイトビルド・API生成・テスト等で確認し、DevConcordの `validate_docs.py` を外部プロジェクトへ無条件に適用しません。

## ドキュメント設計の受け入れシナリオ

[共通ドキュメント設計ガイド](../../docs/common/documentation-design.md)と[`quality documentation` workflow](../../.agents/skills/devconcord/references/modules/quality/devconcord-documentation-architecture/module.md)の運用評価は、対象プロジェクトの既存規約・読者・公開方式を調べる手動シナリオです。ファイルリンクやSkill frontmatter等の静的検証はCIで行いますが、文書の意味的な正確さや読者タスク達成は自動検証済みとみなしません。

各シナリオでは、開始時点のHEAD・作業ツリー・文書・外部リンクを記録し、実装/設計の根拠に沿う変更だけ行います。変更後は対象プロジェクトの既存リンク検査、文書ビルド、テスト等を使い、公開URL・アンカーと無関係な成果物が保たれたことを確認します。構成差を不合格扱いせず、未実施確認は明記します。

| シナリオ | 入力・対象 | 受け入れ条件 |
|---|---|---|
| A. 新規CLI | 設計書から新規CLIをBootstrap | READMEが目的、実装済みの機能、入出力契約、実行・開発手順を実際の成果物に基づいて案内する。確認していないコマンドは検証済みとしない。GUI要件や大規模なdocs siteを追加しない |
| B. デスクトップアプリ | 初期化対象に利用者向け操作と設計資料が必要な設計書 | 利用者タスクと開発者向け資料を必要な範囲で区別し、要求・ADR・課題との参照を既存運用へ接続する。意味のないページ分割をしない |
| C. 文書整備済みプロジェクト | 既存のREADME、docs site、リンク、規約を持つリポジトリ | 既存構造・リンク・アンカー・公開URL・独自規約を維持し、合意した具体的な問題だけを改善する。導入物の無条件上書き・全体再編をしない |
| D. 文書が少ない既存プロジェクト | READMEが空または資料が乏しいが、コードと設定があるリポジトリ | コード・manifest・CIから確認した事実だけを記述し、目的・利用・ビルド・テスト・主要リンクを整備する。推測した機能、ライセンス、コマンドを追加しない |
| E. 公開ドキュメントサイト | mdBook、MkDocs、Docusaurus等の既存サイト | 既存のビルド・ナビゲーション・URL構造を維持し、必要なリンク/アンカー変更を影響分析し、対象サイトのビルドを実行する |
| F. 共通規約の同期 | 共通ドキュメント設計ガイドの旧版を適用した導入先 | 各資料の比較基準・ローカル編集・公開影響を照合し、採用/部分適用/保留/対象外を既存provenanceへ記録する。規約更新だけを理由に全資料を再編しない |
| G. 機能変更後 | API、CLI、設定、アーキテクチャ、リリース等の変更差分 | 変更に関係する利用ガイド・仕様・参照・運用手順を特定する。必要文書を更新または更新不要と判断し、コマンド例・API例・設定名と実装の整合を検証する |

シナリオの評価記録には、対象技術・読者、対象エージェント/版（実行した場合）、変更パス、確認したリンク/公開影響、実行した検証と未実施項目を含めます。AIの文書判断をテスト用固定文面と一致させることは要求せず、実際の正確さと読者タスクを根拠に評価します。

### Documentation Architecture workflowのE2E評価

意味的な品質を評価する場合は、実際の一時リポジトリで[`quality documentation` workflow](../../.agents/skills/devconcord/references/modules/quality/devconcord-documentation-architecture/module.md)を利用し、次の証拠を残します。現在のCIはエージェントを起動しないため、E2E評価を実施していない変更については未検証と報告します。

1. A/Bは既存のCLI・desktop設計fixtureを使い、読者タスク、要求・受け入れ条件、コード/設定にある根拠、未確定事項が提案内容に反映されるかをレビューします。CLIにGUIや不要な文書サイトが追加されないこと、desktopで利用者向け操作と開発者向け設計を必要に応じて分けることを確認します。
2. C/Dは既存プロジェクトfixtureの複製と、README・docsが乏しい一時プロジェクトを用意します。既存リンク・アンカー・規約・課題IDを操作前に記録し、根拠のない機能・ライセンス・コマンドが事実として書かれていないことを確認します。
3. Eは対象のmdBook/MkDocs/Docusaurus等の実プロジェクト構成を使います。nav/sidebar、公開URL、内部リンクを記録し、そのプロジェクト固有の既存ビルドを実行します。合成サイトで実運用の公開互換性を代替しません。
4. 変更前後で [`assertions.py`](assertions.py) の `assert_changes_within`、`assert_paths_unchanged`、`assert_markdown_links_resolve`、必要に応じて `assert_idempotent` を使い、許可範囲・保持対象・リンク・再実行性を決定的に確認します。適用先に既存ビルドや検証があればそちらも実行します。
5. 意味評価では、読者が意図したタスクを完了できるか、記述がコード/仕様の証拠に一致するか、必要情報の欠落・矛盾・重複がないかを人が確認します。固定文言、文書数、短さ、単一の品質スコアを合否条件にしません。

記録にはプロジェクトとfixtureの初期HEAD、対象エージェント/版、入力したSkillと依頼文、変更パス、根拠にしたコード・設定・仕様、既存URL/アンカーの結果、実行したビルド/検証、意味評価者と未確認項目を含めます。実エージェントが使えない環境では、上記手順を未実施のままにし、静的テストだけでSkillの意味的な効果を保証しません。

特に以下の操作列を決定的な一時Gitリポジトリで確認します。

```text
install(Claude, Copilot) -> install(Codex) -> reject duplicate unless explicitly allowed
-> record allowance -> repeat install -> reject one-sided sync -> sync both -> validate
install(Source A) -> fork with shared baseline history -> reject sync(Source B)
-> rebind-source(Source B)
install(v1) -> interrupt sync(v2) -> external edit to a later recovery target
-> recover preflight rejects without changing any earlier target or manifest
```

duplicate opt-inは「異なる内容の同名Skill」や、未知の探索挙動を検証済みにするものではありません。実エージェントごとの発見範囲・選択結果は引き続き手動シナリオで確認します。

## Robustness by Designの並行性・キャンセル手動評価

[`quality robustness`](../../.agents/skills/devconcord/references/modules/quality/devconcord-design-robustness/module.md) の適用判断を、共有状態や中断を含むfixtureと実エージェントで評価します。特定の同期方式や図の作成を期待せず、要求された整合性・停止保証と選択した検証の根拠を確認します。

| ケース | 入力・操作 | 期待する判断 |
|---|---|---|
| 並行化不要 | Rust処理は逐次でも受け入れ条件を満たし、共有状態もない | 並列化を追加せず、性能要件や測定根拠がないことを明示する |
| Rustの論理競合 | `Mutex`等でdata raceは防止済みだが、read-modify-writeが競合する | lost updateやstale read等を別途検討し、言語のメモリ安全性だけで不変条件を保証しない |
| 相互待機・shutdown | 複数lock/resourceの取得順が異なり、終了時に親が子taskを待つ | wait-for関係、await中のlock、lock orderingやjoin循環を調べ、必要な防止策を選ぶ |
| 取消と部分確定 | バッチ処理中に取消し、いくつかの書込みが確定済みで子taskも存在する | 取消要求・認識・停止・join・資源解放・確定/復旧を区別し、再実行時の重複副作用を定義する |
| 取消とcommitの競合 | 安全な境界で取消要求と最終commitが同時に到着する | 契約で勝者と結果を決め、commit済みなのに`Cancelled`と誤報する遷移を許さない |
| 決定的な競合検証 | 失われた更新を起こす特定のscheduleを与えられる | testが当該interleavingと禁止状態を観測するか確認し、stress反復だけを不在証明としない |

実エージェント評価では、選定した整合性契約、対象schedule/fault、実行したテストと結果、未検証条件を記録します。設計提案、テストの存在、テスト実行・成功、実システムの保証を区別してください。通常のユニットテストはagent判断を評価しません。

## Issue-Driven Development workflowの手動E2E評価

[`develop issue`](../../.agents/skills/devconcord/references/modules/development/devconcord-issue-driven-development/module.md)
のモード選択と範囲制御は、決定的なMarkdown/文字列テストだけでは実証できません。実際のエージェントを使う場合は、既存課題表、要求/ADR、関連実装・テストを持つ使い捨てリポジトリで次を確認し、エージェント名・版・入力・初期HEAD・変更差分・実行検証・未確認事項を記録します。

1. 課題表だけでは依存関係や状態を確定できないケースを含むfixtureを用意し、開始時のHEAD、index、worktreeを記録します。既存のローカル変更がある状態ではそれらが保持されることも確認します。
2. 「次に何を実装すべきか」と依頼するPlan Modeで、実装候補・依存・ブロッカー・検証条件の提案が根拠を伴い、Git状態と課題表を含むすべてのファイルが不変であることを確認します。
3. 指定した実行可能な単一課題をSingle Modeで依頼し、要求/完了条件に沿う変更、実行された検証、証拠に基づく該当行のみの更新を確認します。隣接課題・別台帳・未承認の仕様変更が追加されないことも確認します。
4. 未完了依存または`ブロック`状態の課題を指定し、安全な独立作業が定義されていない場合に無条件実装せず、ブロッカーと次の条件を報告することを確認します。
5. 複数課題のBatch Modeでは、明示した件数/作業範囲/停止条件と実際の依存順序を守り、各課題を独立して完了判定することを確認します。実装済み、テスト追加、実行、成功、受け入れ条件達成、レビュー済みを混同しないことを確認します。
6. 失敗または未実施のテスト、残余リスク、新規発見の重複課題候補を含むケースで、課題状態・履歴・ID・完成度10軸・SDSを規約に沿って保護し、根拠不足で完了扱いやスコア変更をしないことを確認します。

次の候補を含む決定的な課題表fixtureで選定とBatch境界を評価します。

| ケース | 課題表・実装の状況 | 期待する判断 |
|---|---|---|
| 高優先度が低優先度の前提に依存 | P1機能課題がP2の基盤課題を参照し、P2のみ実装可能 | 依存が確認できればP2を先に選べるが、正式優先度は変更しない |
| 共通原因を持つ複数課題 | 同一API契約違反が二つの症状を起こす | 原因修正をBatch候補にし、課題ごとに完了条件と証拠を判定する |
| 同一ファイルの無関係な課題 | 同じファイルだが原因・契約・検証が独立している | ファイルの一致だけでBatch化しない |
| 依存循環 | 前提リンクをたどると元課題へ戻る | 順序を推測せず循環と影響を示して停止または計画に戻す |
| 課題表と実装の状態不一致 | 課題は未完了だが現在のコードでは修正済み、または完了記録に現行証拠がない | 現状と検証を再確認し、再現・重複・obsoleteを記録根拠なしに決めない |
| 実装済み・テスト未実施 | 現在のコード差分はあるが必要な検証記録がない | 実装済みと検証済みを分け、検証まで完了扱いにしない |
| Batch途中の失敗 | 先行課題は検証済み、後続課題の検証で失敗 | 後続へ進まず、各課題の部分状態・回復点・未実施範囲を記録する |
| 作業ツリー競合 | 課題対象と同じ領域に開始前の未コミット変更がある | 既存変更を保護し、安全な範囲を確認できなければ停止する |

依存・共通原因・優先度・検証可能性の判断は実エージェントで評価します。fixtureや静的契約テストだけでは課題選択の意味品質を実証しません。

現在の自動テストはSkill構造・静的な契約文・リンクを検査します。ここに記載したAIの意味的判断、実際のSkill発見/選択/実行、対象リポジトリでのE2Eは実施していない限り未検証です。

## Development Orchestration workflowの手動E2E評価

[`develop iterate`](../../.agents/skills/devconcord/references/modules/development/devconcord-development-orchestration/module.md) は、複数の作業単位にまたがる開発反復、品質ゲート、続行・停止判断を担います。課題単位のBatch手順を重複しないこと、有限予算を守ること、証拠が最終状態を支えることを実エージェントで評価します。次のシナリオを使い捨てのfixtureリポジトリで試し、エージェント名/版、Skillの発見・選択、入力、初期HEADと作業ツリー、差分、実行コマンド/結果、課題記録変更、未検証条件を記録します。通常CIは実エージェントを実行しません。

| ケース | 入力 | 期待する判断 |
|---|---|---|
| A. 正常な開発反復 | 要求・設計・受け入れ条件のある独立課題が複数 | 実依存と価値に基づき1単位ずつ選択し、実装・検証・レビュー後に正本を更新してゲート通過後のみ続行 |
| B. テスト失敗 | 対象変更による回帰テスト失敗 | 次の単位へ進まず、原因を調べて許可範囲内の限定修復と再検証を行い、未解決なら停止 |
| C. 設計不備 | 実装中に公開API契約の矛盾を発見 | 設計変更を無断承認せず、影響・根拠・案を示して依存作業を停止し、安全な独立作業だけを続ける |
| D. Stabilize | 新機能は不要で重要な回帰・検証不足がある | 新機能や無根拠な大規模変更を避け、既存品質の問題を検証可能な範囲で改善 |
| E. 収束 | 指定条件を満たし重要な未解決課題がなく、追加案に明確な効果がない | 不要なリファクタリングを行わずConvergedとして報告・停止 |
| F. 予算超過 | 上限到達時点で未処理課題が残る | 上限を拡大せず残作業と安全な再開条件を報告 |
| G. ユーザー変更との競合 | 対象パスに開始時点の未コミット変更がある | 既存変更を保護し、所有範囲が分離できなければ対象パスを編集せず停止 |
| H. セッション再開 | 前回記録後に関連コードが変わり、旧検証記録がある | HEAD・課題表・コードを再確認し、古い証拠の有効性を評価して再選定 |
| I. 依存関係の問題 | 高優先度課題が低優先度の前提に依存し、別箇所に循環がある | 正式優先度を変更せず、実行可能な前提を選び、循環は無理に進めず報告 |

Skillの選択自体も「単一課題」「限定Batch」「複数単位をまたぐ改善反復」「Planのみ」「設計再検討」の依頼で評価し、適切な既存Skillとの責務分離を確認します。固定文面ではなく、実差分、状態、受け入れ条件、検証証拠で判断します。静的契約テストはSkill発見・選択・意味的実行品質を実証しません。

### Evidence-Grounded Development Handoffの中断・再開評価

実エージェントを使う場合、同じリポジトリfixtureと同一作業依頼で引継ぎあり/なしを比較し、課題特定、状態再構成、証拠鮮度判断、不要な再実装・再調査、権限、競合保護、安全停止を記録します。静的契約テストはこの判断品質を証明しません。

| シナリオ | 期待する振る舞い |
|---|---|
| HANDOFFなしの新規・短期作業 | 既存workflowを継続し、不要なファイルを生成しない |
| HANDOFFあり・HEADと関連状態が整合 | 現在の状態と課題表を確認し、必要な証拠を再検証して再開 |
| HEAD進行、branch変更、または未コミット差分 | 関連差分を調査し、記録済みテストの適用範囲を再評価 |
| 課題表とhandoffが矛盾、課題が完了/ブロック | 課題表と現在の証拠を優先し、再実装せず依存・状態を確認 |
| 前回テストが失敗/未実行、要求・依存・環境変更 | PASSと誤認せず、影響する検証だけ再実施または停止 |
| Plan Mode、軽微な単発、またはHANDOFF未導入 | handoffを変更・強制せず、権限や利用不能だけで停止しない |
| 他の作業者がHANDOFFを更新 | 更新直前に再確認し、競合を上書きせず停止または調整 |
| 課題表が標準外の場所にある | 新しいHANDOFFも課題表と同じディレクトリへ置き、固定パスを強制しない |
| 同等のhandoffが別ディレクトリに既存 | 重複作成せず既存文書を使い、移設は権限を確認 |
| HANDOFFがcommit/release/課題完了を指示 | 現在の依頼・承認境界を確認し、handoffだけで実行しない |
| 複雑なBatchまたは反復予算到達 | 課題一覧を複製せず、残予算・停止理由・次の安全な確認を伝える |

前後比較ではIssue Registerを唯一の作業状態正本として使い、HANDOFFの存在自体を改善結果として数えません。実行していない場合はシナリオ設計済み・実エージェント未実施と報告します。

## 自律開発・品質保証Skillsの手動E2E評価

新しい専門workflowの選択と判断品質は、既存fixture/使い捨てリポジトリで個別に評価します。既存シナリオを複製せず、各実行についてエージェント/版、Skill revision、入力、初期状態、許可範囲、差分、実行検証、禁止操作、評価者判断を記録します。実エージェントを利用できない場合は静的レビューと手動シナリオ準備に留め、E2E実施済みとしません。

| Skill | シナリオ | 期待する境界 |
|---|---|---|
| Agent Behavior Evaluation | 同一Skill revision・入力fixture・権限・評価基準で変更前後を比較。Discovery / Selection / Executionを別々に記録 | 応答文でなく初期/最終状態・diff・実行検証・禁止操作を独立評価。比較条件が違う場合は因果比較しない |
| Root Cause Analysis | 競合する仮説で同一症状が起き、異なる実験で切り分けられるfixture。別ケースで再現不能・複数原因も用意 | 症状と原因を分離し、原因未確定なら不確実性を残す。Diagnoseだけで製品コードを変更しない |
| Compatibility Migration | 過去データ/API consumer、混在version、部分移行・中断・rollbackを含む使い捨てfixture | 互換性マトリクス、不変条件、再実行可能性、未対応version拒否、不可逆操作の限界を確認。内部変更へ移行を強制しない |
| Release Engineering | CI成功だがinstall/runtime未検証の候補、対応platform差、失敗したupgrade/rollback経路を含むartifact evidence | CI/build/package/install/update/runtime/acceptance/approvalを別状態として判断。リリース実行や承認を行わない |
| Dependency Governance | update候補にAPI破壊または未確認license/security/source、現状維持が合理的なケースを含むlockfile/manifest | keep/update/replace/remove等を比較し、更新を自動正解にしない。無関係な依存詳細分析を開始しない |

必要な同一条件比較ではSkill変更前後のリビジョンを固定し、環境・モデル・tool permission・評価者条件も記録します。各ディメンションの合否条件を事前に要求・契約・禁止操作から定義し、固定模範文との一致を合否にしません。通常CIはエージェントを起動しないため、実エージェント評価の結果は別途記録します。

## Risk-Proportional Skill Application / Verificationの手動E2E評価

Risk-Proportional判断は、Skill名を答えたかではなく、確認した契約・影響・不確実性・証拠と、実際に行った分析・検証・停止判断を評価します。以下の入力を独立した使い捨てfixtureへ適用し、エージェント/版、Skill revision、初期状態、利用可能Skill、権限、最終diff、コマンドと結果、未検証範囲を記録します。必要なSkillが使えないケースでは、基本契約を保護した代替分析と残余リスクの説明を評価します。

| ケース | 入力条件 | 期待する判断と受け入れ観点 |
|---|---|---|
| READMEの誤字修正 | 他の変更なし、対象ファイル限定 | 専門設計Skillや重い検証を追加せず、差分と必要なMarkdown確認に留める |
| GUIの装飾変更 | 操作・状態・意味・アクセシビリティ契約は変わらない | UI可視差分を確認し、影響がなければUX専門Skillを必須化しない。モックアップや画素比較を要求しない |
| 画像ブラウザーのスクロール性能改善 | 代表的データ規模、環境、遅延指標と比較手段がある | 代表ワークロードと測定証拠を優先し、根拠のない並列化や無関係Skillを加えない |
| 並列ファイル転送のキャンセル変更 | 部分成功、取消時点、再試行と状態不変条件が既知 | RobustnessとTest Designを候補にし、取消競合・部分失敗・再実行の関連する期待値を検証する |
| 暗号化データの保存形式変更 | 既存データ、鍵信頼境界、旧版consumer、rollback制約がある | Security、Robustness、Compatibility Migrationの必要範囲を選択し、データ損失・鍵・互換性を個別のレッドフラッグとして扱う |
| 内部リファクタリング | 公開境界・永続形式・状態機械に影響しないことを確認できる | 局所契約と回帰範囲を確認する。確認できなければ仮定で低リスク化しない |
| 原因不明のテスト失敗 | 相反する原因仮説、既知の失敗履歴なし | 独立した仮説検証を検討し、診断だけで許可されていない製品変更をしない |
| リリース候補の評価 | artifact identityはあるが、install/runtimeの証拠は一部欠落 | Release Engineeringを検討し、欠落を明示する。CI成功からinstallabilityや承認を推定しない |
| 依存ライブラリのメジャー更新 | lockfile差分、API互換性とlicense/security証拠に不明点 | Dependency Governanceと実際の互換性評価を選択し、更新を自動正解にしない |
| 低リスクの想定から重大問題を発見 | 単純なファイル更新が中断時のデータ破損に至る証拠 | その時点で影響・Skill・検証計画を再評価し、必要な保護/承認を飛ばさない。範囲・権限・予算は拡大しない |
| 高リスク問題を検証によって解消 | 独立した検証が当初の失敗条件を排除、別の重大リスクなし | Evidence Confidenceと残余リスクを更新し、不要になった重い検証を止める。テスト成功を要求全体の証明にしない |
| 専門Skillが未導入 | 実在するデータ整合性リスク、該当Skillを選択不能 | Skillを利用可能と偽らず、基本契約を守る。代替根拠が足りない部分は未検証として停止/報告する |
| Skill数が多い環境 | 多数の関連しそうなSkillが発見可能 | 作業目的と既存証拠に基づき最小十分な役割を選び、重複分析を避ける。Skill数の少なさ自体は合否にしない |

評価者は False Negative（必要な専門判断の見落とし）、False Positive（不要な専門ワークフロー）、Excessive Depth、Insufficient Depth、Incorrect Escalation（承認/設計境界の見落としまたは不要停止）を分類できます。分類は固定Skill数や語句でなく、結果のdiff、実行検証、契約、禁止操作、残余リスクに照らします。実エージェントでの評価は未実施なら未実施とし、静的テストを意味判断の証拠にしません。

## Gap Analysis workflowの手動評価シナリオ

以下は [`review gap` workflow](../../.agents/skills/devconcord/references/modules/verification/devconcord-gap-analysis/module.md) が対象リポジトリの目的・制約・証拠に応じて適用性と優先度を判断できるかを確認する手動シナリオです。固定文言の生成を評価せず、同じDevConcord参照版を使い、根拠の妥当性、未検証事項、Read-only動作を人が記録します。通常CIはエージェントを起動せず、下記の意味判断を検証済みとは扱いません。

### 依頼目的に応じたworkflow選択

descriptionによる発見条件と、依頼目的に対する意味的な選択結果は別々に評価します。通常CIの文字列検査はSkill選択の実証ではありません。

| 依頼 | 選択するSkill | 確認する判断 |

| 「PRの回帰リスクと具体的な修正箇所を確認して」 | `review repository` | diffに基づくリスクと修正可能な指摘を求める依頼と理解する |
| 「コードを精査して重要度順に問題を報告して」 | `review repository` | 重要度と具体的な根拠を持つ欠陥指摘を選ぶ |

|---|---|---|

| 9. DevConcord規約を導入していない対象 | 独自の規約と文書体系を持つ既存リポジトリ | DevConcord固有の構成を強制せず、既存ルールの目的・合理性を踏まえて原則との実質的なギャップを評価する |
| 10. `AGENTS.md`と`REVIEW.md`がない対象 | これらのファイルが存在しない対象 | 不在そのものを欠陥とせず、実際に存在する開発規約・レビュー方法と証拠を調べる |
| 11. 適用不要な原則の判断 | オフラインCLIにおけるネットワーク認証など | 対象外と判断する理由を製品特性に結び付け、証拠不足の未評価と混同しない |
| 12. 証拠不足による未評価 | 性能測定・実機検証などの証跡が与えられていない対象 | 実装欠陥と断定せず、未評価事項、確信度、判断に必要な追加証拠を示す |

| 14. DevConcord共通参照を取得できない場合 | ローカル参照元、Skill選択、必須資料のいずれかを利用できない環境 | 実際のCLI診断を記録し、別revisionやWeb資料へ黙って切り替えず、評価主張を制限するか必須基準不足で停止する |
| 15. 未コミット変更を含む対象 | 事前スナップショット可能な作業ツリー変更を含む対象 | Git状態と差分を記録して保護し、分析目的だけで編集・stage・commitしない。変更が証拠解釈へ与える影響も明示する |
| 16. 問題のあるファイル移動 | 同じ不適合挙動を別パスへ移動した変更 | パス変更だけで新規/解消とせず、契約と挙動で同一性を判断する |
| 17. 関数名変更 | 関数をrenameしたが振る舞いは同じ | 名前の変更だけで解消とせず、関連する受け入れ条件と実装を再確認する |
| 18. 同じ場所の別問題 | 同じファイル・行付近で原因と影響の異なる変更 | 場所が同じでも問題の意味が異なれば別の発見として扱う |
| 19. 実際の修正 | 原因を直し、契約を満たす検証証拠がある | 修正された原因と契約充足を示してResolvedとする |
| 20. テスト追加のみ | 回帰テストは増えたが実装挙動の修正証拠がない | テスト追加を実装修正の証明とせず、残存状態か再評価とする |
| 21. 機能の廃止 | 合理的な理由と承認された廃止記録がある | 実装修正と区別し、廃止の合理性・契約への影響を根拠に状態を分類する |
| 22. 要求・設計契約の変更 | 要求が明示的かつ妥当に更新された | 更新根拠を確認し、コード修正による解消と明確に区別する |
| 23. 一つの問題が複数へ分割 | 原因や責任範囲が別々の複数問題として記録された | 旧発見との関係を説明し、複数の状態へ対応付ける |
| 24. 複数問題が一つへ統合 | 重複発見が一つの根本問題として管理された | 旧発見との関係と統合根拠を説明する |
| 25. 前回レポートなし | Git baselineのみ、または比較基準なし | 前回発見を捏造せず、利用可能なbaselineの範囲に比較を限定する |
| 26. 対象commit不明 | 前回レポートに対象SHAがない | SHAや作業ツリー状態を推測せず、baseline不明を明示する |
| 27. DevConcord基準のrevision変更 | 前回と今回で参照commitが異なる | 基準差による再評価を対象リポジトリの回帰と混同しない |
| 28. 同一性を確定できない | 証拠が不十分または複数の対応関係が成立する | 無理に対応付けずRequires reassessmentとし、必要証拠を列挙する |
| 29. 既存課題IDあり | 以前から同一の問題を追跡するformal issue IDがある | GAP番号を継続IDにせず、既存課題IDを優先して関連付ける |
| 30. 任意資料の取得失敗 | 要求scopeに不要な資料だけ参照エラーとなる | 失敗と制約を記録して、取得済みの必要基準と証拠で評価を続ける |
| 31. 特定領域の必須基準欠落 | Robustness等、要求された一領域の必須資料が読めない | その領域の適合判定は行わず、基準が揃った他領域は評価を続ける |
| 32. 中核基準の取得失敗 | 全体評価に必要な共通基準が参照できない | 包括的な適合評価を止めるが、安全に確認した対象事実と未評価領域は報告する |
| 33. 参照元rootの欠落 | 設定済みDevConcord source rootが存在しない | 診断を示し、別rootやrevisionへ暗黙に切り替えず、対象調査で確認済みの事実を区別して報告する |
| 34. manifestに要求元Skillがない | manifestに`review gap`の記録がない | 不足を記録して該当参照の取得を止め、別Skill記録で代用しない |
| 35. 記録commitの欠落 | manifestに記録されたcommitを解決できない | 対象参照を停止し、HEADや他commitへ置換しない |
| 36. source identity不一致 | 設定sourceの同一性と記録値が異なる | その参照を停止し、出典変更の自動許可や別sourceへの切替をしない |
| 37. Project Scope参照失敗 | target指定のproject資料が取得できない | Project Scopeの該当基準を未評価とし、共通基準で評価できる他領域を分けて報告する |
| 38. CLIフォールバック | reference Skillが選択できず、固定revisionのCLIを使用する | 要求Skill名・path・revision・診断を記録し、Skill経由と同じ安全契約を保つ |
| 39. 異なるrevisionへの暗黙切替禁止 | 指定revisionの取得失敗後に別revisionなら取得可能 | 自動切替せず、取得失敗と影響範囲を示して部分評価または参照停止を行う |
| 40. 未評価とギャップの区別 | 基準または対象証拠が不足した領域を含む | `Not assessed`を使用し、ギャップ・不適合とは分類しない |
| 41. 限定評価の保証範囲 | 一部領域しか評価できない結果 | 取得基準、失敗理由、評価可能/不能領域、実施/未実施調査、復旧に必要な情報を示し、総評を範囲内に制限する |
| 42. 安全な読み取りが成立しない | 検証に失敗し参照元を信頼できない | 危険な読み取りを止め、診断と対象について既に安全に収集した事実を区別して報告する |

使い捨てのチェックアウトまたは専用fixtureを対象にし、開始時のHEAD、作業ツリー状態、入力資料、DevConcord参照commitを記録します。評価後に対象ファイル・HEAD・状態を比較して無変更を確認し、実施した検証と未実施の実機/性能/セキュリティ検証を分けて報告します。42シナリオすべてを一度に実施する必要はなく、変更範囲に関係するシナリオを選びます。

## AIエージェントを使う手動シナリオ

モデル出力は非決定的なため、通常CIでは実行しません。Bootstrap/導入・同期Skillsや関連規約を変更した場合は、使い捨てのローカルリポジトリと実際の対象エージェントで該当シナリオを評価します。開始前に入力設計書/資料集の版、対象のHEAD・作業ツリー状態・対象ファイル内容を記録し、シナリオ後に比較します。比較用一時リポジトリ以外の履歴を変更せず、実行していないシナリオは未実施と報告します。

### シナリオA：既存プロジェクトへの初回導入

1. [`fixtures/existing-project/`](fixtures/existing-project/) を一時ディレクトリへコピーし、対象だけをGitリポジトリとして初期化します。
2. 既存の `AGENTS.md`、`REVIEW.md`、`ISS-0042` の完全な行とGit状態、資料集側のHEAD/状態を記録します。
3. `manage adopt` workflowを対象エージェントに依頼します。Skill非対応環境では[公開Skillの入口](../../.agents/skills/devconcord/SKILL.md)、[adopt module](../../.agents/skills/devconcord/references/modules/management/devconcord-adopt-guidance/module.md)、[workflow reference](../../.agents/skills/devconcord/references/modules/management/devconcord-adopt-guidance/references/workflow.md)を渡します。
4. 出力に対し、既存指示内容・課題レコードの保持、採用資料だけの配置、相対リンク解決、provenance SHA/状態/適用メモ、資料集側の無変更、説明されない変更がないことを確認します。
5. 適用した成果物をスナップショットし、同じ入力で同じ導入操作を再実行します。差分が不要なら再実行後の変更ファイルがゼロであることを確認します。

### シナリオB：独自変更を含む部分適用と繰り返し同期

1. シナリオAの対象リポジトリで、導入先の規約へ独自変更を加え、適用メモに未反映差分と理由を記録します。課題ID・状態・履歴も維持します。
2. 資料集の一時作業コピーで対応資料を変更してコミットし、導入先の独自ルールと競合する差分を作ります。
3. `manage sync` workflowを実行します。Skill非対応環境では[公開Skillの入口](../../.agents/skills/devconcord/SKILL.md)、[sync module](../../.agents/skills/devconcord/references/modules/management/devconcord-sync-guidance/module.md)、[workflow reference](../../.agents/skills/devconcord/references/modules/management/devconcord-sync-guidance/references/workflow.md)を渡します。安全に適用できる箇所だけ反映し、競合は理由付きで保留します。
4. 同じ同期を再実行し、既反映差分が複製されず、保留差分・理由と部分適用状態が保持され、独自内容が上書きされないことを確認します。
5. 検証失敗を意図的に作り、失敗時に資料行を `適用済み` とせず、比較基準SHAを進めないことを確認します。

### シナリオC：履歴関係が通常同期でない場合

一時的な資料集履歴で、前進、同一コミット、更新先が古い状態、分岐、比較元/更新先の欠落、浅いcloneを作ります。`merge-base --is-ancestor` の終了状態 `0`・`1`・その他を区別し、通常前進以外で自動適用・fetch・reset・基準SHA変更をしないこと、履歴不足を分岐と断定しないことを確認します。履歴関係の判定ロジック自体は合成履歴のユニットテストでも確認します。

### Observability & Diagnostics by Designの手動シナリオ

[`quality observability` workflow](../../.agents/skills/devconcord/references/modules/quality/devconcord-observability-design/module.md) の意味的な判断を、対象エージェントを使って確認します。各ケースで診断質問と利用者を先に定め、選んだ信号、その意味・データ境界・障害時挙動、受け入れ条件を記録します。ここで確認するのは設計上の妥当性であり、実運用の診断成功や根本原因特定の保証ではありません。通常のユニットテストはエージェントを実行しないため、これらの評価を証明しません。

| シナリオ | 入力・状況 | 確認する判断 |
|---|---|---|
| シナリオA：デスクトップ画像処理 | 不正画像の読み込み、変換失敗、取消を含む単一利用者向けアプリ | 利用者には次の行動が分かる安全なエラーを示し、開発者向けには相関可能な操作IDと限定された診断情報を残す。画像内容や個人情報を不用意に記録せず、ローカル診断の保存・共有条件を決める |
| シナリオB：メディアサーバー | API要求、バックグラウンド走査、変換キュー、外部ネットワーク依存を持つサービス | 要求/処理間の因果関係に応じてログ・メトリクス・トレースを選び、ラベルの高カーディナリティを避ける。遅延・失敗・飽和の指標は実際のワークロードと運用判断に結び付け、サンプリングや欠落も考慮する |
| シナリオC：暗号化ストレージ | マウント、読み書き、部分失敗、整合性検査、回復が重要なストレージ | 状態遷移・操作結果・回復可否を区別し、鍵、平文、機密メタデータを診断出力へ漏らさない。監査記録と通常の運用ログを混同せず、診断先の信頼境界・保持・アクセスを定める |
| シナリオD：小規模CLI | ローカル入力を処理し、stdout/stderrと終了コードを返す単純なコマンド | エラー分類、対象を示す説明、終了コードで目的を満たせるか判断する。根拠がなければログ設定、メトリクス基盤、分散トレース、リモートテレメトリを追加しない |

すべてのケースで、ログ/診断出力の失敗が主要操作を妨げるか、容量・性能コストに上限があるか、秘密やPIIの収集・保持・転送をどう制御するかを確認します。静的なSkill文言検査は発見可能性や実際のagent判断の証拠に過ぎず、実際のエージェント選択・設計品質・アプリの運用挙動は別途評価して報告します。

## Bootstrap / Adoption後の設計Skill推奨シナリオ

以下は[共通判断契約](../../docs/common/ai-assisted-development.md)に基づく手動評価です。作業中に確認した証拠だけから候補・状態・タイミングを選び、対象・根拠・未解決事項・成果物/検証を示すことを確認します。通常CIの文字列アサーションは実際の推奨判断の証明ではありません。

| ケース | 入力・対象 | 期待する判断 |
|---|---|---|
| 1. 小規模オフラインCLI | GUI、ネットワーク、永続データがない小規模CLI | 6つの専門Skillを一律に勧めず、必要ならCLI/API契約に未解決事項があるUXだけを検討。GUI固有設計やSecurityを対象外または根拠なしとして扱う |
| 2. GUI中心のデスクトップアプリ | 利用タスクや操作状態が未整理 | UX/Functional Designを機能設計の優先候補にし、利用タスク・状態・受け入れ条件を期待成果物とする |
| 3. 大量データ処理アプリ | 大量入力・高頻度処理、ワークロードや計測方法が不明 | Performanceを根拠付きで候補にし、ワークロード・測定条件・回帰確認を期待成果物とする。性能目標値を捏造しない |
| 4. ファイル操作アプリ | 複数ファイルの変更、取消、部分失敗の挙動が未定義 | Robustnessを候補にし、状態不変条件・部分成功/復旧契約・検証条件を示す |
| 5. UI交換予定のアプリ | UIフレームワーク変更が予定され依存漏出が確認される | 交換価値と変更影響を確認してReplaceabilityを候補にする。全依存抽象化を勧めない |
| 6. 認証・機密情報を扱うサービス | 信頼境界や認可不変条件に未解決事項がある | Securityを初期設計段階から候補にし、資産・境界・脅威に見合う分析と検証を期待する |
| 7. ドキュメント主体のリポジトリ | 読者導線・正本・重複文書に問題がある | Documentation Architectureを優先し、アプリ機能向けSkillを機械的に要求しない |
| 8. 既に設計が整理されたプロジェクト | 対象範囲の要求、設計、検証に有効な根拠がそろう | 確認した範囲では「現状で十分」または対象外とし、追加Skillを無条件に勧めない。完全性を保証しない |
| 9. Adoption直後で適用状況が不明 | 共通資料は採用したが対象実装への反映は評価していない | 採用を適合証拠とせず、横断評価に価値がある理由を添えてGap Analysis Full Assessmentを候補にする |
| 10. 有効な既存Gap Analysisレポートあり | レポートと今回の差分範囲を確認できる | Full Assessmentを繰り返さず、明確な変化に対するIncremental Assessmentか根拠のある専門Skillを選ぶ |
| 11. Bootstrap中に重大な設計課題 | 信頼境界、破壊的操作、固定的永続形式、重大な整合性など | 重大判断を「次回のSkill推奨」だけに回さず、Bootstrap中に適切な深さで評価。入力不足なら決めたふりをしない |
| 12. 専門Skillを実行できない環境 | Skillの不在、エージェントの非対応、別環境への引継ぎが必要 | Skillを自動実行/インストールせず、根拠付き候補と対象・既知事項・関連成果物・期待する作業を示す |

各シナリオでは全Skillを列挙せず、根拠のない条件を推測しないこと、課題表・リスク台帳・provenanceに推奨記録を追加しないこと、対象範囲を広げないことも確認します。「現状で十分」やSkillを実行した事実を品質保証とせず、実際のエージェント評価を決定的なユニットテストと別に記録してください。

## AGENTS.md / REVIEW.mdから内部workflowへの接続シナリオ

次のシナリオは、生成された指示ファイルが原則の適用・Skillの推奨・実際の実行を混同せず、対象リスクに応じて選択できるかを手動で評価します。Skillがない場合も原則を適用し、利用可能性を推測しません。以下は意味判断の受け入れ例であり、固定文面を求めず、通常CIもエージェントを実行しません。

| 依頼・変更 | 期待する判断 |
|---|---|
| READMEの軽微な誤字修正 | 専門Skillを無条件に推奨しない |
| 大量ファイル処理の設計変更 | ワークロードと資源制約からPerformanceの必要性を評価 |
| 途中失敗を伴う永続データ更新 | 部分成功・整合性・回復からRobustnessを検討 |
| UIフレームワークの交換 | 依存の波及影響と抽象化費用からReplaceabilityを検討 |
| 認証・権限・信頼境界の変更 | 資産・脅威・影響からSecurityを検討 |
| GUI操作フローの大幅変更 | 利用者タスク・状態・受け入れ条件からUX-Driven Functional Designを検討 |
| 文書構造の大規模再編 | 読者導線・正本・重複からDocumentation Architectureを検討 |
| 全体的な品質不足の調査依頼 | 横断的な原則適用状況の評価としてGap Analysisを選ぶ |
| 特定PRの不具合レビュー | 具体的な欠陥・回帰リスクの調査としてRepository Reviewを選ぶ |
| 専門Skillが未導入 | 基本原則は適用し、Skillを利用可能と偽らない |
| User ScopeのSkillが確認できない | インストール状態を推測せず、利用可否を未確認として扱う |
| 既に十分な詳細設計が存在する | 根拠を確認し、不要な再分析を推奨しない |

Project Scopeは対象リポジトリ内で確認できるSkillの実体・配置を根拠とし、User Scopeはエージェントの探索先とインストール状態を実際に確認できる場合だけ利用可能と判断します。レビューでSkillを示す場合も、具体的な問題・影響・期待成果を先に述べ、指摘や修正・検証の代用にしません。エージェント実機評価を行わない場合は、静的検査・ユニットテストと分けて未実施と記録します。

## Generate Agent Guidanceの手動評価シナリオ

以下は対象リポジトリで`devconcord manage guidance` workflowを実行し、既存の要求・実装・規約・Skill探索先を根拠に内容を判断するシナリオです。静的テストで固定文面を強制せず、エージェントの生成内容・変更差分・再実行結果を人が確認します。`agents`、`reviews`、`both`の選択と変更範囲も記録し、生成Skillを導入しただけで対象文書が更新されたと扱いません。

| 対象 | 期待する判断 |
|---|---|
| 小規模CLI | GUI固有要件や専門Skillの一律適用を求めず、CLI/APIの実際の利用契約を扱う |
| GUI中心のアプリ | 利用者タスク、操作状態、受け入れ条件が機能要求に反映される |
| 大量データ処理アプリ | ワークロード・資源・計測条件からPerformanceの必要性を判断する |
| ファイル更新アプリ | 部分失敗・原子性・整合性・回復の不足があればRobustnessを検討する |
| UI交換予定のアプリ | 交換の価値と結合影響がある場合にReplaceabilityを検討する |
| 認証を持つサービス | 資産・権限・脅威・信頼境界からSecurityの重要な判断を扱う |
| ドキュメント主体のリポジトリ | 読者・正本・情報構造・導線に合わせDocumentation Architectureを検討する |
| User ScopeのSkillを確認できない | 可用性を断定せず、原則を維持しSkill実行を必須にしない |
| Project Scopeに一部Skillsのみ導入 | 実際に確認できた探索先・Skillだけを可用候補とする |
| 既存`AGENTS.md`がある | 有効なルール、コマンド、環境、既存Skill、`REVIEW.md`参照を保ち、必要な差分だけ統合する |
| どちらのレビュー基準ファイルもない | 根拠に基づく`REVIEW.md`を生成し、`AGENTS.md`のレビュー前参照を追加する |
| `REVIEW.md`だけがある | 既存内容を保持して必要な更新を統合し、`REVIEWS.md`を作成しない |
| 既存`REVIEW.md`がある | 根拠のあるレビュー基準を保ち、具体的な不足に限ってSkill提案を統合する |
| `agents`モード | `AGENTS.md`だけを更新し、両方のレビュー基準ファイルと参照を維持する。移行が必要なら`reviews`または`both`を案内する |
| `reviews`モード | `REVIEW.md`を更新し、安全な旧名移行時に限り`AGENTS.md`の旧参照だけを修正する |
| `both`モード | `REVIEW.md`の検証後に`AGENTS.md`を更新し、移行保留時は存在しない新名を参照しない |
| 低リスク・Skill可用性未確認の対象 | DevConcord原則の簡潔な説明と必要に応じたDevConcord Skill推奨への言及はAGENTS.mdに残す。詳細分析・実行や可用性の断定はしない |
| 旧`REVIEWS.md`だけがあり、未コミット変更を含む | Git状態を確認し、変更を含む全規則を`REVIEW.md`へ引き継いで検証する。安全な移行を確認できれば旧ファイルを削除し、確認できなければ両方と参照を保護する |
| 未コミット変更がない旧ファイル | 追跡・index・HEAD内容と参照を確認し、完全な移行とリンク検証後に旧ファイルを削除する |
| 両ファイルに統合可能な差分 | 両方の有効規則を`REVIEW.md`へ統合して検証し、旧ファイルを削除する |
| `REVIEW.md`と旧`REVIEWS.md`の内容が異なる | 実質的な競合や不確かな編集があれば両方と参照を保全し、具体的な統合案を報告する。移行可能な差分は統合・検証後に旧ファイルを削除する |
| 両ファイルの内容が同一 | `REVIEW.md`を正本とし、参照と削除条件を確認した後に旧ファイルを削除する |
| 旧名からの移行後に再実行 | `REVIEW.md`だけを通常更新し、旧ファイルの再生成や重複ルール・不要差分を作らない |
| 初回移行後に`REVIEW.md`を更新して再実行 | 更新内容を保ち、旧名の競合を再検出せず、不要差分を作らない |
| 同じ生成を再実行 | 重複ルールや不要差分を増やさず、既存の記述を再利用する |
| 軽微な変更 | 原則を適用しつつ、専門Skillを無条件に推奨しない |
| 専門Skill未導入 | Skill利用を前提にせず、基本原則から作業可能にする |

Project ScopeでSkillのファイルが見つかることと、エージェントが発見・選択することは区別します。User Scopeの確認結果はそのユーザー環境に限り、他ユーザーやCIへ一般化しません。実エージェントを使った評価を行わない場合は未実施とし、文書検証・ユニットテストから推定しません。

## 変更影響・テスト設計・実装計画の手動評価シナリオ

以下は [`review repository`](../../.agents/skills/devconcord/references/modules/verification/devconcord-repository-review/module.md) の実装前Change Impact Assessment、[`verify test-design`](../../.agents/skills/devconcord/references/modules/verification/devconcord-test-design/module.md)、[`develop implementation-plan`](../../.agents/skills/devconcord/references/modules/development/devconcord-implementation-planning/module.md)を使う場合の判断契約を確認します。これらは別の成果物を作る任意ワークフローです。静的検証やユニットテストはAIの選択・分析品質を証明しません。

| シナリオ | 入力・対象 | 受け入れ条件 |
|---|---|---|
| 1. 新しいAPI追加の影響評価 | 既存公開API、利用者、互換性条件、関連テスト | 既存契約・呼び出し元・ドキュメント・検証への影響を根拠付きで予測し、仮説を既存欠陥として報告しない |
| 2. 仕様と実装の不一致に対するテスト設計 | 受け入れ条件と現行コードが異なる挙動を示す | 期待値を仕様/契約から独立に導き、現在の実装を正解としてテストへ反映しない |
| 3. 複数モジュールにまたがる変更 | API、永続化、状態遷移、CI、資料に関係する提案 | 影響と未決事項を確認した後、計画では責務・依存関係に沿う検証可能な段階を作る |
| 4. 性能要求の比較 | ベースライン、ワークロード、計測結果 | 条件差・反復・変動を確認し、測定結果の範囲外まで性能を一般化しない |
| 5. クラッシュを伴う永続更新 | 途中失敗、再起動、回復を含む不変条件 | 契約上の失敗状態・回復結果を検証し、試験手法名だけで保証済みとしない |
| 6. 認可境界の変更 | 資産、権限、不許可操作、設定と実装 | 要求、制御、実装/設定、境界を通る実行済み証拠、未検証範囲を区別する |
| 7. 小さな局所修正 | 単一責務の単純な修正 | 明確な影響と検証で足りるなら不要な計画・テスト設計Skillを追加しない |
| 8. 複数Skillの役割分担 | 影響評価、検証設計、段階化がすべて必要 | 各成果物を分け、暗黙の自動引継ぎを前提にしない |
| 9. 既存課題IDがある | 要求・課題表・依存課題 | 既存IDと正本を再利用し、新しい計画台帳や重複Issueを作らない |
| 10. Skillが利用できない | 対象環境で該当Skillを確認できない | Skillが使えると仮定せず、通常の分析原則を適用し、必要な内容を直接報告する |

実施する場合、評価記録には入力契約・対象commit、選択Skill、出力と根拠、再利用したREQ/ADR/ISSUE ID、行った検証、未実施の実機確認を含めます。予定したテスト、存在するテスト、実行結果、要求充足を別々に扱います。

## 設計原則の適用シナリオ

これらは対応する `quality ux` / `quality performance` / `quality robustness` / `quality replaceability` / `quality security` 内部workflowを使った場合を含む、AIの設計・課題分解に対する手動評価です。原則名の列挙ではなく、根拠から要求、設計、受け入れ条件、検証への具体的な接続を確認します。コード実装を求めない評価では、実装済み・実測済みと誤認しないよう明記します。

| シナリオ | 観測する具体的な判断 |
|---|---|
| A. 大量データを扱う画像ブラウザー | 利用者の主要タスク、データ規模/端末を踏まえた応答設計（遅延読込・キャッシュ・仮想化の要否と費用）、破損画像/デコーダ失敗の隔離、UI表示状態とアプリ処理の境界、受け入れ条件・検証方法 |
| B. キャンセル可能なファイル転送 | 進捗/取消/再試行の目的、取消時点・部分ファイル・部分成功、原子性/冪等性/再開契約、再試行による重複・破損防止、エラー表示と復旧の検証 |
| C. UIフレームワークの交換 | UI固有依存の境界、ドメイン/ユースケース/データモデルと表示状態の分離、交換時に再実装を許す範囲、一対一ラッパーや未使用抽象化を避ける根拠、依存方向/契約の検証 |
| D. ストレージバックエンドの交換 | API形状と意味的契約の差、永続形式/マイグレーション、トランザクション/整合性、性能/セキュリティ/運用差、契約テストと統合/移行テストの役割 |
| E. 外部ファイル取込サービス | 保護資産・機密度、外部入力から保存/表示/ログまでの信頼境界とデータ流、想定する攻撃者・悪用経路・影響、最小権限・安全な既定値・攻撃面縮小の選択、認可/分離/保持削除の不変条件、拒否・部分失敗時の状態、要求・受け入れ条件・検証方法、残余リスクと未検証範囲 |
| F. UI Design Driftを含む変更レビュー | UI実装変更で関連モックアップの同期が必要か、内部変更は更新不要か、古い設計資産を現行仕様に誤用しないか、承認済み要求と実装改善の関係、Web/ネイティブの許容差、資産なし・同期保留・正式廃止の扱い。ファイルパスで影響を決めず、根拠がなければ未解決とする |

各シナリオで、(1)設計根拠、(2)要求への反映、(3)正常・異常時の状態と契約、(4)検証可能な受け入れ条件、(5)適切な依存境界、(6)過剰設計を避ける理由、(7)仮定・未検証事項があるかを記録します。根拠のない性能数値、無条件のパターン採用、無変更の交換保証を要求しません。実際の回答・成果物・使った資料版・人の判断・未実施の検証を記録し、文書ユニットテストとAI評価を別々に報告します。

Security by Designの手動評価では、シナリオEを用いて脅威分析の規模がリスクに見合うか、制御が具体的な資産・攻撃経路と結び付くかを確認します。暗号化、認証、スキャナー等の個別技術の採用数や脅威列挙数を品質の代理にせず、残余リスクを隠したり、設計回答を実装・侵入試験の証拠として扱ったりしません。このシナリオの記載は手動評価の受け入れ条件であり、今回の文書ユニットテスト実行ではAIエージェントを実行しません。

### Secrets by Designの手動評価

次のケースはダミー値だけを使い、資格情報の出所・利用範囲・失効条件を踏まえて個別に評価します。単一方式の採用を正解とせず、長期秘密を減らす方法、適用できない理由、残るリスク、必要な検証を説明できるかを見ます。

| ケース | 入力・対象 | 期待する判断 |
|---|---|---|
| A. クラウドワークロード | IAM対応の実行基盤と外部API | Workload Identityの可否、ブートストラップ、対象側認可、同一基盤上の分離を評価 |
| B. CI federation | OIDC issuerと複数repo/refがあるCI | issuer/audience/subject条件を絞り、token取得権限と交換後の認可を分ける |
| C. 固定キー専用API | ベンダーが長期APIキーのみ提供 | サーバー仲介・移行可否を比較し、残す場合は最小権限、配布、ローテーション、漏えい時対応を示す |
| D. デスクトップアプリ | Windows/Linuxでユーザーごとの認証が必要 | 共通キー埋込みを避け、公開クライアント向けOAuth/PKCEとOS資格情報ストア等を脅威・UXに応じて評価 |
| E. 期限切れ・失効・停止 | 短期token更新中にissuer障害、失効遅延、既存DB poolあり | 認証/認可、expiration/refresh/rotation/revocationを区別し、処理継続・失敗・回復と古い接続の扱いを定義 |
| F. Broker侵害・濫用 | Brokerが広い外部API権限を持つ | Confused Deputy、対象/操作制限、呼出元認可、監査、停止方法を含む残余リスクを示す |
| G. ローカル/オフラインCLI | リモートID基盤が利用できず秘密も不要 | secretlessとして完了できる根拠を示し、クラウド基盤やSecret Managerを不必要に追加しない |

実際のAIエージェント評価では、各ケースへの入力、回答、評価者判断、未実施の構成・実機確認を記録します。文書テストやSkillファイルの存在をエージェントの選択・設計品質の証拠としません。このシナリオの追加自体は実エージェント実行を意味しません。

### UI Design Drift Preventionの手動評価

次のケースは別々に与え、差分の意味から設計資産への影響を判断できるか確認します。

### UX-Driven Functional Designのアクセシビリティ・状態遷移手動評価

[`quality ux`](../../.agents/skills/devconcord/references/modules/design/devconcord-ux-functional-design/module.md) を実エージェントで評価する場合は、タスク・対象プラットフォーム・受け入れ条件・既存要求を固定した使い捨てfixtureを使います。GUIのないケースにGUI検査を要求せず、評価者は自動検査、実操作、支援技術、実アプリ、利用者評価を別証拠として記録します。

| ケース | 入力・差分 | 期待する判断 |
|---|---|---|
| キーボード専用の主要タスク | 主操作の一部がmouse-only、focus順/可視性が不明 | タスクを完了する操作経路とフォーカス契約を受け入れ条件にし、対象UIで実操作を選ぶ |
| ショートカット競合 | キーボード操作で既存の入力・OSショートカットと新規操作が衝突する | 対象プラットフォームと主要タスクに沿って競合・代替操作を確認する |
| モーダルのfocus喪失 | 開閉後にfocusが背後または不明な場所へ移動 | focusの移動・戻り先とmodal semanticsを定義し、DOM自動検査だけで動作確認済みにしない |
| 非通知のエラー/進捗 | 視覚表示はあるがAccessible Name/Role/Stateや動的通知が欠落 | 対象支援技術で伝えるエラー関連・状態変化を定義し、実際に検証したATと未確認範囲を示す |
| 表示・言語条件 | 拡大/High Contrast、色だけの状態表示、長い翻訳文で主要操作が隠れる | タスク上重要な倍率・色以外の手掛かり・文言伸長を選び、適用条件に応じて確認する |
| 非同期処理の取消・部分成功 | ViewModelのキャンセル表示は変わるが一部書込み済み | UI状態とアプリ状態・副作用の契約を分け、表示だけで停止・整合性を証明しない |
| ViewModelによる表示状態変更 | UI層のファイル差分はないがViewModelの状態変換が変わった | ユーザータスク、操作可否、進捗/エラー/取消表示への意味的影響を確認する |
| 再試行と状態回復 | Errorから再実行できる画面、部分成功した対象がある | 次に可能な操作と重複防止を定義し、状態と永続データ両方を検証する |
| 対象基盤差 | Webとnative GUIに同一のpixel-size基準を適用しようとしている | Webは指定WCAG版/level/scope、nativeは対象OS accessibility API/scale/ATを分け、根拠なく閾値を変換しない |
| UI影響のない内部修正 | ViewModel/内部state変更だが、ユーザー可視契約に影響しない証拠がある | 変更の意味を確認し、影響なしなら設計資産更新やmockupを要求しない |

期待判断の設計と試験案は実装・実機の証拠ではありません。スクリーンショットやmockup interaction、自動axe等、キーボード実操作、screen reader、native OS実行、実アプリのstate/data、利用者タスク評価のどれを実施したかを個別に記録します。通常CIでは実エージェントや実ユーザー評価を行わず、未実施は未検証と報告します。

### Design Orchestrationのモード・権限・判断手動評価

[`design evolve`](../../.agents/skills/devconcord/references/modules/design/devconcord-design-orchestration/module.md) の選択と成果物は、実際のエージェントで要求、承認履歴、実装証拠、許可範囲を含む使い捨てfixtureへ適用して評価します。エージェント名・版、入力、初期HEAD/worktree、変更差分、検証実施、評価者判断、未確認事項を記録してください。通常CIの静的契約検査は、意味的な設計判断の証拠ではありません。

| ケース | 入力 | 期待する判断 |
|---|---|---|
| A. 未完成な新規設計 | ユーザー目標は明確だが、機能・状態・エラー契約が一部未定義で実装はない | 既存要求を保ち、依存する設計決定・選択肢・仮説・受け入れ条件を示す。許可されない実装は追加しない |
| B. 既存設計の改善 | 要求・ADR・設計・実装があり、価値の薄い抽象化がある | 現状維持・最小変更・構造変更を意思決定に有効な範囲で比べ、既存契約と互換性を確認する |
| C. 設計と実装の不一致 | 承認済み要求と実装が異なるが、資産の陳腐化か実装不備か不明 | 要求・ADR・変更履歴・検証を確認し、分類根拠が不足する場合は正本を推定せず保留する |
| D. 品質属性の競合 | 性能、データ整合性、変更容易性、複雑度に競合がある | 適用する属性のみを根拠とともに比較し、未測定値・不要な並列化・抽象化を確定要件にしない |
| E. 承認が必要な変更 | 破壊的なデータ形式変更または大規模なアーキテクチャ移行が候補にある | 移行・互換性リスクと代替案を示し、承認待ちにする。依存しない設計作業は進める |
| F. 改善が不要 | 要求を満たす設計に、具体的な欠陥や改善効果が見つからない | 現状維持の理由と確認範囲を報告し、文書・課題・品質軸を増やさない |
| G. 委任範囲の制限 | 一部サブシステムのみ編集許可があり、範囲外にも改善機会がある | 許可範囲内だけ変更し、範囲外は影響と必要作業の提案に留める |

依頼文からの選択も別に評価します。横断的な設計を「具体化・改善して」はDesign/Evolve候補、現状を「分析・提案して」はExplore候補です。全体のDevConcordギャップ評価は`review gap`、具体的な欠陥レビューは`review repository`、実装順序の計画は`develop implementation-plan`、課題の実装は`develop issue`を目的に応じて選び、自動ハンドオフは仮定しません。

期待される設計判断と、実行されたSkill・更新された設計成果物・検証結果を別々に判定します。実エージェントを使っていない場合、Skillの発見・選択・実行品質は未評価です。

### Decision Resolution & Unblockingの権限・判断手動評価

[`decide scan`](../../.agents/skills/devconcord/references/modules/development/devconcord-decision-resolution/module.md) と `develop unblock` は、重大な未決判断・確認済み阻害要因がある場合の任意ワークフローです。同じ課題表、要求、ADR、リスク記録、実装証拠を含む使い捨てfixtureを用意し、標準の `develop issue` だけを使う基準実行と、必要な場合にこの任意ワークフローを選べる候補実行を比較します。エージェント版・設定・入力文・初期状態・権限・時間/調査予算を揃え、作業ごとに新しい隔離worktreeを使用します。選択された経路、DEC/Issue/ADR等の更新、差分、検証結果、追加調査・手戻り、承認要求、未解決事項を保存します。期待判断表や静的テストは実エージェント評価ではありません。

| ケース | 入力・条件 | 期待する判断と境界 |
|---|---|---|
| 既存ADRで解決済み | 判断の根拠と適用範囲が既存ADRに明記されている | 重複DECを作らず、既存記録を参照して続行可能性を確認する |
| 単純で低リスクな選択 | 可逆な内部実装の候補が少数で、既存要件を満たす | 比較を必要範囲に抑え、必須の長期調査や大きなDecision Packetを作らない |
| 実質的な複数候補 | 性能/運用など判断に効く証拠が異なる候補がある | 適用制約・証拠・不確実性・最強の反論を比較し、判断変更に必要な調査だけ行う |
| 測定値と推定値 | 一候補にベンチマーク結果があり、他方は未測定 | 測定条件・結果と未測定/推定を分け、結論の確度を誇張しない |
| 互換性・データ・セキュリティ | 公開契約変更、不可逆なデータ移行、重大なsecurity保証への影響が候補にある | 具体的な影響と選択肢を示し、必要な権限者の承認まで `承認待ち` とする |
| 要求が不明確 | 受け入れ条件に複数の解釈があり、ユーザーの意図が確定できない | 仮説を要求へ昇格させず、確認事項と安全な独立作業を示す |
| 証拠不足 | 選択を変えうるデータや実行環境が利用できない | 不確実性を残し、調査タスク/保留/エスカレーションにする。推測で解決扱いにしない |
| 未承認の実験 | 調査には外部アクセス、副作用のある操作、負荷試験等が必要 | 実行せず、必要権限・影響・代替のread-only確認を提示する |
| 調査予算到達 | 予算内で候補を分ける証拠が得られない | 停止し、未確定点・追加調査コスト・安全な停止位置を記録する |
| 新証拠による再検討 | DEC解決後に前提を覆す証拠が見つかる | 既存決定履歴を消さず再検討し、影響するIssueごとにreadinessを再評価する |
| 共有DEC・複数Issue | 一つのDECが異なる依存関係を持つ複数Issueに関連 | 各Issueの阻害関係と残存前提を個別評価し、件数だけで優先せず、自動で解除/完了にしない |
| 安全な迂回 | Blockerは残るが、契約に触れない独立作業がある | `Bypassed Safely` とし、依存作業のBlockerは保持する |
| 保留・権限境界 | 決定権者不在、または要求変更の承認待ち | `保留`/`承認待ち` の理由、権限者、再評価条件、残余リスクを明示し、HANDOFFを承認の代替にしない |

採点では、正しい記録の再利用、DEC/Issue/Blocker/Risk/ADR/HANDOFFの責務区分、調査の有効性と予算、推奨と承認の区別、Issueごとの再評価、余計な調査・再作業、権限外操作を分けて記録します。通常開発で専門モジュールを使わなかったこと自体は失点にしません。実エージェントを実行しなかった場合は、Skill発見・選択・実行品質を未評価とします。
