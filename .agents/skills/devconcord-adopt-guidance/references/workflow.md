# Adoption Workflow Reference

This distributable reference contains the detailed execution contract for `devconcord-adopt-guidance`. The `SKILL.md` is the entry point and keeps mandatory protection and provenance rules visible. When this workflow needs a DevConcord guide, template, shared document, or test procedure, use the direct CLI fallback described in this Skill's `SKILL.md` DevConcord References section to read the needed path at this Skill's installed source commit. Do not assume the source checkout is available.

## 1. 対象プロジェクトの調査

作業前に対象リポジトリの作業ツリーを確認し、README、`AGENTS.md`、`REVIEW.md`、`docs/`、主要コード、依存・ビルド・テスト・CI設定、既存の課題管理方法を調べてください。既存文書との重複、矛盾、リンク関係を把握します。文書の読者・用途、文書公開/生成基盤、主要ナビゲーション、正本、プロジェクト固有の文書規約と検証方法も調べ、必要に応じて、このSkillの`SKILL.md`にあるDevConcord ReferencesのCLI手順で`docs/common/documentation-design.md`を参照し、有用な場合だけ適用候補として評価してください。

資料集のREADME、`docs/README.md`、`docs/agent-skills.md`を読み、利用可能な資料と相対リンクの前提を確認してください。

`AGENTS.md` と `REVIEW.md` の有無も確認し、両方がない場合や片方だけの場合は、`devconcord-generate-agent-guidance` Skillを使って不足分を整備します。旧名 `REVIEWS.md` がある対象の移行と競合判断も同Skillへ委ね、Adoptionに別の移行処理を作りません。両方がない場合は `REVIEW.md` を先に作成し、その後 `AGENTS.md` を作成してレビュー前に読む指示を含めます。既存ファイルがある場合は生成時にもその内容を調査し、有効なルールを維持して統合します。利用者が指示ファイルの生成を今回の対象外とした場合は、未作成ファイルと使用するSkillを報告し、`AGENTS.md` から `REVIEW.md` への参照を確認済みと扱いません。

## 2. 適用内容の選択

初回導入では、資料集の作業ツリーに未コミット変更がないか確認し、別途指定されていない限りコミット済み資料だけを適用します。実際に確認・利用した完全SHAを記録してください。採用した資料には、そのSHAを行の「比較基準コミット」に記録します。適用状態は次の基準で記録し、比較基準コミットの記録だけで適用完了と判断しないでください。

- 採用した内容をすべて反映した場合は `適用済み`。
- 一部を反映し、未適用の内容が残る場合は `部分適用`。反映範囲、未適用差分、保留理由を適用メモに列挙します。
- 採用候補だが反映を保留した場合は `保留`。未適用差分と保留理由を適用メモに列挙します。
- 採用しないと決めた場合は `対象外` とし、比較基準を `—` にして理由を記録します。

- 編集前に、既存の `AGENTS.md`・`REVIEW.md`・課題表の重要内容、対象リポジトリの作業ツリー、資料集のHEAD/作業ツリー状態を記録し、変更後に照合します。既存ルール、課題ID・状態・履歴、無関係なファイルの変更を削除・置換・完了扱いしません。
- プロジェクトの規模、技術、リスク、既存規約に必要な資料だけ選びます。
- ドキュメント設計ガイドはREADMEや資料体系の改善に有用な場合だけ選択します。導入先の既存構成・公開基盤・命名・リンク・言語を尊重し、DevConcordのディレクトリ配置やREADMEテンプレートを一律導入しません。初回導入では全面再編せず、現状、改善候補、公開URL/アンカー等の影響、合意範囲、検証、未対応事項の順に扱います。
- 長いリファレンスを無条件に丸ごとコピーせず、短い導入ガイドと必要な詳細節を優先します。
- 課題表が既にある場合はそれを維持し、ID、履歴、列、運用を無断で作り直しません。
- 既存の要求、ADR、課題、技術的負債、リスクのID・状態・履歴・リンクを調査し、破棄・置換しません。必要な関係だけIDやリンクで結び、二重の課題表・リスク対応台帳を作らないでください。
- 要求仕様には受け入れ条件、実装状態と検証状態の区別、関連設計・実装・証跡への参照が必要かを確認します。プロジェクト規模に応じ、表やリンクで軽量に導入します。
- 要求仕様を採用する場合、利用者タスクと導出したREQ IDを必要に応じて相互参照し、一対多/多対一の関係も既存の要求表で追跡します。全プロジェクトに独立したトレーサビリティ・マトリクスを追加しません。
- リスク規約を採用する場合、リスク記録は将来の不確実性と残余リスクに限定し、軽減作業は既存課題表へ置きます。
- 共通DoD、変更影響分析、検証証跡、依存課題は既存の管理元へ統合し、固定WIP数・納期・工数・時間管理を追加しません。
- Self-documenting Codeは、コードで表現する意味・責務・契約・振る舞いと、資料で補う要求・判断・制約の役割分担として適用します。SDSが必要なプロジェクトでは補助指標として選択導入し、既存の総合完成度へ加算しません。コードを成果物としないリポジトリは理由付きで対象外にできます。
- Doc Commentsは公開・重要APIの利用契約・制約を対象言語の標準方式で説明し、Annotation Commentsは局所的な未解決事項や重要な注意を示すものとして、共通開発ガイドの選択可能な規模に合わせて導入します。コメント件数や比率を品質目標にせず、課題表を唯一の作業管理元とします。
- DDD、Self-documenting Code、Performance by Design、Robustness by Design、Replaceability by Design、Security by Designを同格の横断的な基本設計原則として扱い、DbC・テスト・計測と接続します。UI/UXは利用者の目的・タスクから機能・操作・状態を方向付ける人間中心の入力とし、性能要求には必要に応じてワークロードや測定条件を、堅牢性要求には重要な異常条件・整合性・回復保証を定めます。根拠のない数値目標、無条件の再試行・多重化、過剰最適化は導入しません。Security by Designは資産・信頼境界・脅威・影響に応じた要求・制御・検証を扱い、全変更に一律の脅威分析を課しません。詳しい共通原則は必要に応じて共通AI支援開発ガイドを参照します。
- Replaceability by Designは、主要な技術選択のうち交換価値があり波及影響が大きいものに限り、変更可能性・影響・抽象化コストから必要な境界を選びます。ドメイン概念に沿う契約と技術Adapterを優先し、全依存の抽象化、ライブラリAPIの一対一ラップ、未使用の複数実装を導入しません。UIビューの無変更移行を約束せず、バックエンドはエラー、整合性、永続形式、性能、セキュリティ等の意味的契約も考慮します。
- UI/UXの理論やチェック項目を機械的に適用せず、対象者・タスク・製品形態に応じて機能要求、受け入れ条件、検証へつなげます。Web/デスクトップ以外のCLI・ライブラリ等にはGUI固有規約を課しません。キャンセルや再試行は処理状態・部分成功・データ整合性・重複副作用まで必要な範囲で設計します。
- Boundary Value / Property-Based / 状態機械 / Fault Injection / Recovery / Concurrency / Resource等の検証を影響と費用に応じて選び、すべてを必須化せず、実施していない検証を保証と扱いません。UX・性能・堅牢性等のトレードオフは重大な場合にADRへ記録します。
- プライバシー・環境衛生の規約を選ぶ場合、実環境の個人情報・秘密・設定値を資料やサンプルへ複製せず、パスは相対表記、環境変数、標準API、プレースホルダーを優先します。OS契約やテストで必要な絶対パスは理由を確認します。
- 既存の `AGENTS.md` や `REVIEW.md` を置換せず、矛盾のない差分を統合します。
- Agent Skillsの導入が指定された場合は、`.agents/skills/` の正本から必要なSkillだけを `scripts/manage_skills.py install` で計画・導入します。まずdry-runを確認し、明示的な `--apply` なしにファイルを書き換えません。未指定ならSkillsを自動導入しません。重複探索先、同名Skill、ローカル変更があれば保護して停止し、Skillsの出典記録を `guidance-provenance.md` へ混在させません。
- 適用できない規約や未確認の前提は明示し、事実として追加しません。

## 2.1 Adoption後の設計・品質フォローアップ

共通原則・規約を採用したことと、対象の実際の要求・設計・実装・テストがその原則を満たすことは別です。Adoptionは共通資料の導入作業であり、採用だけを根拠に適合を報告しません。

完了報告へ後続作業を推奨する場合は、このAdoption作業で既に確認した対象情報・既存成果物・具体的な矛盾や未解決事項だけを根拠とし、共通判断基準の `docs/common/ai-assisted-development.md` §17.3 を版固定参照します。推奨のために未調査のコードやテストを広く読み直してはいけません。適用状況や設計・実装の関係を横断的に評価する必要があるが十分な証拠がない場合は、個別の専門Skillで調査したと推測せず、必要に応じて `devconcord-gap-analysis` のFull Assessmentを候補にします。

Full Assessmentの提案前に、対象リポジトリが既に有効な最新ギャップ分析レポートを持つか、今回の範囲で確認できる情報から調べます。既存レポートがあればFullの繰り返しを無条件に勧めず、明確な変更範囲がある場合はIncremental Assessment、または根拠がある一領域の専門Skillを検討します。レポートの有効性や対象commitが確認できない場合はその制約を示し、最新と決めつけません。

既存文書・規約・要求・ADR・課題・リスク・実装の確認で特定できた重要な専門的検討だけを選び、共通の状態分類、候補条件、出力項目に従います。小さな導線修正など適切な専門Skillがない作業は既存の採用案に含め、Skill名を無理に割り当てません。不明な実装品質は判断保留/未評価とし、Gap Analysisを用いた追加評価が必要かを示します。

実装前に具体的な影響範囲を確認する必要が見えた場合はRepository ReviewのChange Impact Assessment、要求から独立したテスト期待値や方法が未整理なら`devconcord-test-design`、複雑な改善を検証可能な実装単位へ分ける必要があれば`devconcord-implementation-planning`を候補にできます。Adoptionで確認していない実装品質やテスト不足を推測して推奨理由にしません。

推奨はAdoptionの完了報告に限り、課題表、リスク台帳、要求仕様、ADR、`AGENTS.md`、`REVIEW.md`、`docs/guidance-provenance.md` を推奨登録のために変更しません。後続Skillを自動実行・インストールせず、ユーザーの明示した範囲を広げません。実際に確認した根拠と、推奨対象に対して未実施の評価・検証を分けて報告します。

## 3. ファイルの配置と更新

調査後、対象プロジェクトで有効な資料を配置します。既存の名前・階層に合わせ、必要なものだけを追加または更新してください。

- 課題管理規約と課題表テンプレートを一緒に使う場合は、相対リンクを保つ階層で配置するか、リンクを対象内の配置に書き換えます。
- コピーした文書の内部リンク、文書索引、`AGENTS.md`・`REVIEW.md` からの参照を対象リポジトリ内で解決します。
- ドキュメント設計ガイドを採用した場合は、対象の`AGENTS.md`へ短い変更影響確認ルールを、`REVIEW.md`へリスクに応じた読者・正確性・情報構造・重複・導線・実装整合・リンク確認を追加します。詳細規約の複製は避け、導入先内の採用先へリンクします。
- コード、設定、データ、既存課題の状態は、導入資料の配置に必要でない限り変更しません。
- 大きな変更、既存方針と矛盾する変更、複数の妥当な導入方針がある場合は、候補と影響を記録し、安全に可能な独立作業を続けます。

## 4. 確認と報告

- 変更したファイルとその目的を列挙します。
- 変更が選択した資料・必要な指示/適用記録の範囲内であること、既存の指示・課題レコードが保持されていること、出典/比較基準SHA/状態/適用メモが実際の反映結果に合うことを独立に確認します。
- 検証に失敗した場合は `適用済み` と記録せず、変更を成功形に取り繕いません。差分・失敗・未確認事項を報告します。利用可能なら 利用可能な場合は対象リポジトリに文書化された決定的不変条件ヘルパーを使い、AIによる判断の手動評価とは証拠を分けます。
- 既存方針との整合性、相対リンク、課題ID・状態・優先度、`AGENTS.md` から `REVIEW.md` への適用指示を確認します。
- 要求・設計・課題・リスク・検証証跡の参照関係と、作業管理の重複がないことを確認します。
- 自己説明性の規則が命名・コメント量の好みに偏らず、SDSを採用する場合も既存の完成度評価と分離されていることを確認します。
- Doc CommentsとAnnotation Commentsの適用範囲がプロジェクトの言語・API公開範囲に合い、必要な課題IDだけを既存課題表へ結び付け、重複台帳を作っていないことを確認します。
- 対象リポジトリの秘密情報検査はMarkdown用の文書検査と区別し、必要ならソース・設定ファイル等を扱える既存または専用スキャナーを使います。秘密の値を報告やログへ転載しません。
- サンプル、ログ、作業報告に個人・秘密・環境情報が含まれず、性能方針がワークロード・測定根拠に基づき過剰最適化を強制しないことを確認します。
- 重要なユーザータスクが機能・状態・受け入れ条件・検証に接続され、異常条件・データ整合性・回復の契約が必要な範囲で含まれていることを確認します。完成度の既存10評価軸と重みを維持し、新しい作業台帳を作らないことを確認します。
- 交換可能性が重要な依存について、保護対象の境界・意味的契約・許容される変更範囲と検証方法を必要な範囲で明記し、設計・アーキテクチャ/コード品質・保守性を中心とする既存評価軸へ反映することを確認します。抽象化の過剰導入を避けます。
- 実行した確認と未実施の確認を分けて報告します。
- 採用しなかった資料、残る矛盾、利用者が判断する必要のある事項を示します。
- 導入対象のソースや設定に変更を加えた場合、その理由を資料導入の変更と分けて説明します。
- 導入結果を記録するため、対象リポジトリの `docs/guidance-provenance.md` に資料集URL、実際に確認した完全なコミットSHA、適用日、採用資料、保留事項を記録します。資料別の列名は「比較基準コミット」とし、状態・反映範囲・保留差分は適用メモに記録します。既存ファイルがある場合は上書きせず、`devconcord-sync-guidance` Skillによる更新へ切り替えます。
