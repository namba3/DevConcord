# Bootstrap Workflow Reference

This distributable reference contains the detailed execution contract for `devconcord-bootstrap-from-design`. The `SKILL.md` remains the entry point and preserves mandatory safety checks. DevConcord guides and templates are separate optional references: use the direct CLI fallback described in this Skill's `SKILL.md` DevConcord References section to read a specific file at this Skill's installed source commit. Do not assume the source checkout is available.

あなたは設計書に基づいて新規ソフトウェアプロジェクトのリポジトリを初期化します。コードを大量生成することではなく、根拠ある要求・責務・契約・品質特性を反映し、開発可能かつ検証可能な初期状態を作ることが目的です。

## 入力

- 設計書のパス（複数可）: `<Markdown、テキスト化可能なPDF/DOCX等>`
- 初期化対象ディレクトリ: `<パス>`
- プロジェクト名: `<任意。設計書に記載があれば参照>`
- 技術的制約: `<任意。設計書に記載があれば参照>`
- 初期化範囲: `<開発基盤のみ / 最小実装骨格まで / 明示された初期機能まで>`
- Git初期化: `<未指定なら、空かつ未初期化の対象に限りgit init可>`
- 追加指定: `<任意>`

## 1. 対象状態と安全境界を確認する

設計書を読む前後に対象ディレクトリの実体とGit状態を調べ、次を区別してください。

- 空でGit未初期化のディレクトリ
- 入力として明示された設計書だけが存在するディレクトリ
- 検証済みのDevConcord Skillsだけが導入されたディレクトリ
- 明示された設計書と検証済みSkillsだけが存在するディレクトリ
- 既存ファイルのあるGit未初期化ディレクトリ
- Git初期化済みで未コミット・未追跡の成果物がないリポジトリ
- Git初期化済みで履歴または既存成果物があるリポジトリ
- 既に実装・運用記録があるリポジトリ

対象パスが不明確、設計書を読めない、既存内容との重大な競合がある場合は破壊的な変更を止めて報告し、必要な判断を求めます。既存ファイル、Git履歴、未コミット変更、リモートを破棄・置換しません。完全に空でGit未初期化なら、Git初期化の入力が未指定でも `git init` を実行できます。設計書だけがある対象では、指定された設計書と必要な親ディレクトリ以外に内容がないこと、入力パスが通常ファイルで読み取り可能なことを確認し、ファイルを保持したまま追加作業できますが、Git初期化は明示指定がない限り行いません。Skillsも同居する場合は次の限定例外の検証も必要です。Gitが既に初期化されている場合は決して再初期化せず、履歴・remote・index・working treeを保持します。履歴がある対象を「空」と扱わず、未実装に見える場合も競合しない追加のみを行います。既存Git履歴を作り直さず、remote設定、push、GitHubリポジトリ作成、commitは利用者が明示しない限り行いません。秘密情報を追加・記録しません。

例外として、Bootstrap Skillを先にインストールした新規対象は、そのSkillファイルがあるという理由だけで既存プロジェクトと判定しません。ただし、以下をすべて検証できる場合に限り「Skill導入だけの初期状態」として扱えます。

- `.devconcord/skills-manifest.json` が読み取り可能なschema 2で、記録された配置パッケージとエージェントが正規の値である。
- `.agents/skills/` と `.claude/skills/` の各Skillディレクトリがmanifestに記録され、その導入済みツリーSHA-256と一致する。manifest未記録のSkillや余分なファイルがない。
- 対象にある他のファイル/ディレクトリが、検証済みSkillパッケージ、manifest、入力として明示された設計書、および必要な空の親ディレクトリだけである。設計書は読み取り可能な通常ファイルであり、Bootstrapの出力で上書きせず、要求によりコピー・移動・削除しない。
- `.git` がある場合は履歴・remoteがなく、既存の追跡/ステージ済み成果物や他の作業変更を含まない。判断が曖昧なら初期状態として扱わない。

これらを一つでも確認できない場合、内容を保持して停止します。Gitが初期化済みなら、`.git` の有無だけでなくHEAD、履歴、remote、index、追跡・未追跡・変更済みファイルを調べます。unborn HEADでremoteがなく、入力設計書/Skills以外の成果物やstaged変更がない状態は追加作業を検討できます。既存commitや作業成果物がある場合は、その履歴とファイルを保持し、競合しない追加に限る既存リポジトリとして扱います。最も単純で推奨する順序は、設計書を対象外の場所から参照して空の対象でBootstrapを行う方法です。設計書だけを対象内に置く場合は、入力一覧に明示したファイルだけがある状態を許可し、Skill同居時は上記条件も適用します。Skill導入を先に行う必要があるときだけ、Skillの限定例外を適用します。Skill導入済みという事実だけで他の既存成果物やGit履歴を安全とみなしてはいけません。

## 2. 設計入力を読み、出典を保つ

Markdownと通常のテキストは直接読みます。PDF/DOCX等は、現在の環境で利用可能な抽出・プレビュー手段により実際に読める範囲だけを解析します。読めないファイル、画像内テキスト、抽出欠落、曖昧な表は未確認として明示し、読んだことにしません。解析器や依存ツールを無断で追加せず、設計書の機密性・ライセンス・共有範囲を確認してください。

各入力のパス、タイトル、確認できる版/日付/コミット、該当する節やページを記録し、必要な場合だけSHA-256等で内容を識別します。対象リポジトリに残す出典は可能ならリポジトリ相対パスを使い、対象外の入力は安定した文書名と版/節を記録します。個人環境の絶対パスを記録しません。設計書を対象リポジトリへコピーするのは、利用者の指示と著作権・機密性・ライセンス上の許可を確認できる場合に限ります。入力設計書の出典記録は共通資料の適用記録 `docs/guidance-provenance.md` と別概念です。DevConcordの共通資料を初期リポジトリへコピーする場合は `devconcord-adopt-guidance` Skill の選択・出典記録方針を使い、共通資料provenanceは入力設計書の出典情報で代用しません。共通資料を適用しない場合に記録だけを作らず、既存のprovenanceがある対象では保持します。

## 3. 設計内容を整理・レビューする

まず実装を変更せず、設計書群から以下を出典付きで整理します。

1. 目的、スコープ、対象外、成功条件
2. 利用者、利用状況、ユーザー目標、主要タスク
3. 対象OS、プラットフォーム、実行環境、言語、ビルドシステム
4. UI、バックエンド、ストレージ、外部サービス等の技術選択と制約
5. ユースケース、ドメイン概念、責務、不変条件、データ形式
6. アーキテクチャ制約と依存方向
7. 性能、堅牢性、交換可能性、セキュリティ、プライバシー等の品質要求
8. テスト、検証、運用、配布・リリース条件
9. 未決事項、矛盾、欠落、仮定、リスク

文書間の優先関係が明記されていなければ、新旧や具体性だけから一方を確定仕様とみなしません。矛盾と選択肢を出典付きで記録し、影響が重大で安全に進められない場合は確認を求めます。それ以外は明示した仮定に基づく可逆的な基盤作業だけ進め、未決事項を既存課題表へ登録します。設計書にない仕様、数値目標、ライセンス、技術選定を確定事項として補いません。

## 3.1 ドキュメント体系を初期設計する

`SKILL.md`のDevConcord References手順で版固定参照した`docs/common/documentation-design.md`を使い、入力設計書と実際の初期成果物から、読者・目的に必要な文書だけを選びます。少なくとも次を判断し、根拠のない情報は未確認として残します。

1. 想定読者と主要タスク、利用者向け・開発者向け・運用者向け情報の違い
2. READMEに示すプロジェクトの目的、実装済みの特徴、対象環境、確認済みの利用・開発手順と詳細資料への導線
3. 要求、アーキテクチャ、ADR、API、運用、ビルド・テスト資料の必要性とそれぞれの正本
4. 既存の文書公開・生成基盤、リポジトリの用語・命名・リンク・多言語方針
5. 文書更新が必要となる変更と検証方法

小規模なCLIやライブラリではREADMEと必要最小限の資料にまとめて構いません。大規模なアプリケーションや公開サイトでは、読者別の入口・索引・参照資料が有効か評価します。文書数やDevConcordのディレクトリ構成を目標にせず、初期状態で不要な設計サイトやテンプレートを生成しません。コード・仕様・設定とREADMEの説明が一致することを確認し、未実装機能、未確認のコマンド、未確定のライセンスを事実として書きません。

## 4. 設計原則を初期構造へ反映する

- **UI/UX-driven Functional Design:** 利用者の目的・タスクから、主要ユースケース、操作、状態、結果、エラー・復旧を必要な範囲で導出します。進捗・キャンセル・再試行・一括処理は表示だけでなくアプリケーション処理とデータ整合性の契約にします。CLI、サービス、ライブラリには実際の利用者接点に合う要求を適用し、GUI要件を強制しません。
- **Performance by Design:** 対象ワークロード、データ量、環境、重要経路を確認し、アルゴリズム、ストリーミング/遅延読込、I/O、メモリ、非同期・並列、キャッシュと整合性を必要に応じて設計します。測定条件が未確定なら値を捏造せず、後で計測する条件と回帰確認方法を記録します。
- **Robustness by Design:** 重要な失敗条件、状態不変条件、部分成功、原子性、キャンセル、再実行、リソース所有、隔離、復旧、診断を要求・構造・テスト方針へ結び付けます。初期化時に全障害処理を実装する必要はありませんが、後から契約を成立させられなくする構造を作らないでください。
- **Replaceability by Design:** コアのユースケースをUIイベントや技術固有型から分離し、将来の変更価値がある依存だけを境界化します。API形状だけでなくエラー、永続形式、トランザクション、並行性、性能、セキュリティ等の意味的契約を考慮します。全依存へのinterface、使用予定のない複数実装、一対一ラッパー、ビュー無変更交換を要求しません。
- **Security by Design:** 資産、信頼境界、データ/制御フロー、脅威と影響を変更のリスクに応じて設計入力から整理し、必要な最小権限、安全な既定値、攻撃面、データライフサイクル、依存、セキュリティ不変条件、受け入れ条件・検証へ接続します。暗号・認証・スキャナー等の個別制御を根拠なく強制せず、前提、残余リスク、未検証範囲を明記します。
- **DDD / Self-documenting Code:** ドメイン語彙と責務をコード構造・型・APIへ表し、設計理由や契約は適切な資料とテストで補います。必要な範囲を超える層・抽象化を作りません。

原則名を列挙するだけでなく、根拠 → 要求/契約 → 初期構造 → 受け入れ条件 → 検証方法をつないでください。トレードオフが将来に重要な影響を与える場合だけADRを作り、比較した選択肢と許容する変更範囲を記録します。

## 5. 成果物を初期化範囲に合わせて作る

設計書と指定範囲から必要な成果物だけを選びます。特定言語・フレームワークの標準構成を他案件へ強制しません。

- 技術に合った最小のディレクトリ、manifest、モジュール/パッケージ構成、ビルド・開発環境
- 設計根拠を反映した要求仕様、必要なADR、プロジェクト概要
- 既存運用と整合する課題表・リスク記録（重複台帳は作らない）。初期課題は要求ID、機能、受け入れ条件、依存関係、検証条件、優先度、未決事項/リスクを必要な範囲で結び付け、工数・納期を捏造しない
- 開発・テスト・CIの最小構成と、実在するコマンドを記載したREADME
- `AGENTS.md` と `REVIEWS.md`（必要な場合）
- 指定範囲に応じた最小エントリーポイント、コア型/ユースケース、技術Adapter、スモークテスト

要求仕様は `SKILL.md`のDevConcord References手順で取得した版固定の`docs/application-design/templates/requirements.md` を基準にし、入力設計書の出典・節からTASK/REQ/NFR、ADR、初期構造、課題、受け入れ条件・検証へ必要な範囲で追跡できるようにします。出典パスと版等は要求仕様の関連資料欄や要求行、ADRの関連欄へ記録し、専用台帳は複数文書の管理上必要な場合だけ設けます。既存の課題管理方式があれば優先し、完成度10軸とSDSの重み・独立性を維持します。初期化だけを理由に完成度を高く評価しません。

`AGENTS.md` と `REVIEWS.md` は `devconcord-generate-agent-guidance` Skill の調査・記述方針を再利用してください。実装済みの事実と設計上の将来制約を分け、実在しない機能・テスト・保証を記載しません。既存内容がある場合は置換せず統合します。`AGENTS.md` からレビュー前に `REVIEWS.md` を読む指示を保ちます。

初期化範囲の扱い:

- **開発基盤のみ:** 開発/検証環境、設計・運用文書、課題の足場を作成。アプリ機能のスタブを作らない。
- **最小実装骨格まで:** 実行可能な最小入口、必要な責務境界、意味のあるスモークテストまで。未実装機能を成功に見せるダミーを作らない。
- **明示された初期機能まで:** 指定された機能と受け入れ条件だけ実装し、範囲外要求を完了扱いしない。

## 6. 安全に検証し、再実行可能にする

変更前後のGit状態と既存ファイルを照合し、差分を要求・初期化範囲に限定します。対象技術に適した構文/ビルド/テスト、リンク、CI設定、依存方向、既存内容の保持を確認します。実行可能な検証と、機能実装後でなければ検証できない将来条件を分け、実行していない検証を成功と報告しません。必要な依存復元はmanifestと既存手順から安全性を確認して行います。

同じ入力・範囲で再実行するときは既存の生成物を読み、同一内容を無用に書き換えず、二重の課題・設定・テストを作りません。再実行差分が発生した場合は理由を説明します。最終報告には、入力出典、対象の開始状態、変更範囲、主要判断と仮定、成果物、受け入れ条件、実行した検証と結果、未実施/未解決事項、残余リスクを示します。
