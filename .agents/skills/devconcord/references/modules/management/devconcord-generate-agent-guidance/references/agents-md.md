# AGENTS.md Generation Procedure

This distributable reference contains the detailed procedure for its selected output mode. Use the direct CLI fallback described in this workflow's `module.md` DevConcord References section only when optional shared DevConcord guidance is needed; do not assume access to the source checkout.

あなたはこのリポジトリの開発ルールを整備します。リポジトリを調査し、根拠に基づく簡潔な `AGENTS.md` を作成または更新してください。

## 調査

作業前に、少なくとも次を確認してください。

- 既存の `AGENTS.md`、`REVIEW.md`、README、開発者向け文書
- ディレクトリ構成、主要な実装・公開インターフェース
- manifest、ビルド設定、対応する言語・ツールチェーン
- テスト、フォーマッター、リンター、CI設定
- 生成物、外部依存、OS・デバイス固有の検証境界
- リポジトリ内で実際に発見できるAgent Skillsの配置先とSkill名

リポジトリ内に明確な根拠がないルールは作らず、「未確認」として扱ってください。コマンドは設定や既存文書から確認し、推測で実行手順を書かないでください。

## 記載方針

- `AGENTS.md` は日常の変更作業に常時適用する、短く実行可能なルールを記載します。
- **必須記載事項:** `agents` / `both`モードで生成・更新するすべての`AGENTS.md`には、DevConcordの基本原則の簡潔な説明と、利用可能性を確認した単一公開Skill `devconcord` の必要に応じた利用推奨を含めます。対象リスクが低い場合やSkillの利用可否が未確認の場合も、この2点への言及自体は省略しません。言及を必須とすることは、全原則の詳細分析やSkillの実行を必須にする意味ではありません。
- 原則の説明には、DDD、SDD、TDD、DbC、Self-documenting Code、UX-Driven Functional Design、Performance / Robustness / Replaceability、Security by Design、Observability & Diagnosability by Design、Documentation by Designを短く含めます。詳細な説明は導入済みの共通ガイド等へ委ね、対象に関係しない分析を強制しません。
- AGENTS.mdの案内は単一公開Skill `devconcord` を示し、作業目的に対応する論理コマンド（例: `devconcord quality security`、`devconcord verify test-design`、`devconcord review repository`）を必要な場合だけ例示します。コマンドはエージェントが解釈する論理的指示であり、シェルコマンドや全ホスト共通のslash commandとして説明しません。内部module IDを独立Skillや導入対象として案内しません。
- `devconcord` の可用性は対象のProject Scopeと確認可能なUser Scopeの配置先・登録状態に基づいて説明し、Skillファイルの存在からホストによる発見や選択を断定しません。原則適用、ワークフローの推奨、実際の選択・実行を区別し、他の提供元の有用なSkillsも排除しません。
- サブエージェントの利用方針は対象プロジェクトまたはチームの判断として扱います。新規生成・更新の前に既存`AGENTS.md`と今回の明示指示、および作業に適用されるプロジェクト規約にある関連記述を意味から確認し、利用禁止、条件付き利用、対象範囲、並列数、実行環境、承認条件、判断理由を維持してください。キーワードが見つからないことだけで方針なしと判断しません。既存方針がある場合は今回のデフォルトを追加せず、無条件化・範囲拡大・理由の削除・重複追加をしません。意味が曖昧なら既存文を保護し、解釈できない点を報告してください。
- 既存のサブエージェント方針がないと確認できた場合に限り、`agents` / `both`モードで次の趣旨を短く記載してください。これはDevConcord自体の共通開発原則ではなく、生成先向けの任意のデフォルトです。

  > 利用可能な環境では、独立作業の並列化や専門調査・独立レビューの効果が、追加トークン、調整・結果統合の負荷、編集競合などのコストを上回る場合、サブエージェントの利用を推奨します。小規模な作業や依存関係の強い作業は単独実行を優先し、利用できない場合は通常どおり進めます。最終的な品質検証と既存の権限・承認境界は維持します。

- 再実行時は既存の関連方針を優先します。特に、前回生成した推奨を利用者が編集していたら編集後の内容を保ち、既定文へ戻したり重ねて追加したりしません。採用状態を記録するmanifest・marker・追加metadataを作りません。
- この規則は`agents` / `both`のAGENTS.md生成・更新だけに適用します。`reviews`単独ではAGENTS.mdのサブエージェント案内を追加・更新しません。BootstrapとAdoptionはこの共通生成workflowを再利用し、独自のサブエージェント生成規則を作りません。
- 原因不明の実質的な障害、実在する互換性/移行リスク、明示的なリリース/配布作業、依存の変更や重大リスク、エージェントSkillの実効性評価は、それぞれ `devconcord diagnose root-cause`、`devconcord lifecycle compatibility`、`devconcord lifecycle release`、`devconcord lifecycle dependencies`、`devconcord evaluate agent` の任意候補として扱えます。Compatibility、Release、Dependency workflowをDevelopment Orchestrationの標準ゲートにせず、未導入・利用不能で無関係な作業を止めず、非利用を欠陥にしません。リリースの提案は実行・承認を許可しません。実在する互換性・データ損失・セキュリティリスクの通常確認は維持します。
- 既存の同等記述を再利用して重複を避け、対象プロジェクト固有の規約・テストコマンド・既存Skill指示・レビュー基準への参照を保ちます。
- `reviews`モードでは、移行に必要な許可済み参照修正を除き、`AGENTS.md`の開発原則やSkill推奨を変更しません。
- プロジェクト概要やコード構成の説明を大量に複製せず、必要な資料への相対リンクを使います。
- 変更前に読むべき資料、編集上の制約、検証コマンド、生成物の扱い、報告事項を、根拠がある範囲で記載します。
- 変更規模・リスクに応じた影響確認と、共通DoDの適用を短く実行可能なルールにします。全作業に重い手順を課さず、既存の課題表・要求仕様・ADR・リスク記録を管理元として参照し、同じ情報の別台帳を追加しません。
- 意味・責務・契約・振る舞いを名前、型、API、構造、テストで表現し、必要な理由・制約は資料で補う自己説明性の原則を反映します。ドメイン複雑性に応じて適用し、特定のDDD構成や言語機能を強制しません。
- 文書または文書に影響する実装の変更時は、対象読者・目的・正本・関連リンクと公開上の互換性を確認し、必要な資料だけ更新する短いルールを含めます。導入先に共通ドキュメント設計ガイドを採用済みならリンクし、DevConcord固有の配置を強制したりガイド本文を複製したりしません。
- 公開・重要APIには、対象言語の標準方式で利用者に必要なDoc Commentsを付け、契約・エラー・副作用・制約を実装と同期する方針を反映します。未解決事項や重要な注意には必要に応じて標準Annotationを使い、重要な作業だけ既存課題IDへ結び付けます。詳細規約を重複して複製せず参照してください。
- コメント量の削減や命名の好みを目標にせず、AI生成コードも人が理解・保守できることを重視します。SDSを採用するプロジェクトでは、対象スコープの評価・更新方法を規約へのリンクで案内し、全変更に再計算を要求しません。
- DDD / SDD / DbC / TDD / Self-documenting Codeとby Design原則は、対象のドメイン、利用者接点、技術構成、品質リスクに応じて日常ルールへ反映します。UI/UXは対象の利用者目的・タスクから機能・操作・状態を導く設計入力、Documentation by Designは文書の読者・正本・構造・導線・実装との整合として扱い、無関係な領域へ強制しません。性能は重要なワークロード・資源制約、堅牢性は異常時の契約・状態整合性・回復、交換性は変更価値のある依存境界、Security by Designは資産・脅威・信頼境界、Observability & Diagnosability by Designは運用上の診断質問・必要な信号・機密性に応じて検討します。資格情報を扱う場合は、長期秘密が必要か、主体ID・権限・ブートストラップ・ライフサイクルを必要な範囲で確認します。正確性・アクセシビリティ等の要求も保ち、全変更へ同一の分析を要求しません。
- 対象機能に応じ、要求・設計段階でユーザー目標とタスク、受け入れ条件、性能上重要なワークロード/経路、異常条件・状態整合性・失敗時保証・回復を検討する指示を加えます。キャンセル・再試行・一括処理は表示操作だけでなく実処理の意味と副作用を含めます。CLIやライブラリ等にGUI固有要件を課さず、すべてを一律適用しません。
- 既存の要求仕様書がある場合、UX由来のTASK IDとREQ ID、受け入れ条件、設計/実装、検証証跡の相互参照を必要な範囲で保ち、独立したトレーサビリティ・マトリクスを無条件に追加しません。
- 長期・複雑な未完了作業や複数セッションにまたがる開発では、対象に既存HANDOFF.mdがあれば再開時の補助情報として確認する簡潔な案内を必要に応じて加えます。新規作成・許可された移設では課題表と同じディレクトリに配置し、既存の同等ファイルを複製しません。課題表と現在の実装・検証証拠を正本とし、HANDOFFを再検証します。全作業への導入や自動生成、別の進捗台帳化は要求しません。
- 対象に実際のブロッカーまたは重要な未決判断がある場合は、利用可能性を確認して`decide scan`や`develop unblock`等を候補として簡潔に案内できます。通常作業への必須化、DECの二重台帳化、推奨と承認の混同を避け、利用不能でも無関係な作業を止めません。
- 重要なトレードオフは必要な場合にADRへ記録し、根拠のない数値目標、無条件の再試行・多重化、測定根拠のない最適化を要求しません。異常条件に応じた検証方法を選び、未検証の保証を明示します。
- Replaceability by Designは、交換価値のある技術依存に境界を設ける方針として扱います。変更可能性・波及影響・抽象化費用を比較し、すべての依存にinterfaceを要求せず、具体APIを一対一で包む層や未使用の複数実装を作らないようにします。交換時の変更範囲・意味的契約・データ移行・性能/セキュリティ/UXへの影響は必要な場合に検討します。
- 変更に関係する原則は常に考慮し、リスクに応じて `devconcord` の内部workflowを選びます。生成するAGENTS.mdに旧 `devconcord-*` module IDを列挙せず、必要時は `design evolve`、`develop issue`、`develop iterate`、`review repository`、`review gap`、`verify test-design` 等の論理コマンドを選択的に案内します。評価workflowと設計・実装workflowを区別し、利用可能性が未確認ならその状態を示します。利用可能性、推奨、実際の選択・実行を混同せず、自動インストール・実行を要求しません。
- 専門Skillと検証の深さは、実際の影響、不確実性、波及範囲、可逆性、検証証拠に比例して選び、利用可能な全Skillや全手法を一律実行しません。新しいリスクが判明したときは選択と検証を見直します。未知を低リスクの根拠にせず、基本的な互換性・データ保護・セキュリティ義務と委任・承認境界を維持します。詳細は共通ガイドのRisk-Proportional Skill Application / Verificationへ委ね、固定スコアや別台帳を生成しません。
- Skillの選択は、対象の利用者タスク・要求・既存契約・アーキテクチャ境界・品質リスク・既存の設計/検証証拠・未解決事項から行います。重要なセキュリティ変更、データ損失や状態整合性のリスク、実質的な性能制約、機能を方向付けるUX判断、交換価値のある技術依存、文書体系の変更では、対応する専門Skillの検討を優先できます。これは候補の例であり、変更リスクと既存設計の十分さに応じて絞り、問題と期待する成果物に結び付けます。
- 既存課題表から実装対象を選び、課題状態や証拠を更新する依頼では `develop issue` を候補にします。複数単位の有限な開発反復を委任された場合は `develop iterate`、指定変更を分割する必要があれば `develop implementation-plan` を候補にします。短い単独修正や課題表がない対象へこれらを強制せず、自動実行・実装許可・commit/pushの根拠にしません。
- 障害原因の診断や重要な診断信号設計が作業に関係する場合は、対応する `diagnose root-cause` または `quality observability` workflowを候補にできます。小規模な対象へ監視基盤やremote telemetryを推奨するために使わず、workflowの実行・導入を前提にしません。
- Skillの可用性はProject ScopeとUser Scopeを分けます。Project Scopeでは対象リポジトリの実際のSkill探索先にある`module.md`と必要なパッケージ構成を確認します。User Scopeでは選択対象エージェントの実際に確認できる探索先とインストール状態だけを根拠にし、インストール済みであることと実エージェントが発見・選択できることを区別します。User Scopeの状態は他の利用者やCIへ一般化せず、確認不能なら利用可否を未確認とします。個人の絶対パスや設定値を書かず、自動インストールやエージェント固有の呼び出し構文を共有指示へ追加しません。
- 既存`AGENTS.md`は全面再生成せず、プロジェクト固有の原則、検証コマンド、環境、セキュリティ、管理方法、実在するレビュー基準への参照を保って必要な差分を統合します。同じ生成を再実行しても同じ規則を重複追加しないよう、既存記述との重なりを確認します。
- 個人・秘密・環境情報を生成物、ログ、テスト出力、作業報告へ不要に含めず、個人用の絶対パスや実環境設定をサンプルに複製しない方針を記載します。OS/API契約やテストで必要な絶対パスは理由を示せば使用できます。
- 実装済みと検証済みを区別し、未実施の検証と残余リスクを報告するよう指示します。
- レビュー専用の詳細な観点は正式名称 `REVIEW.md` に置きます。生成する `AGENTS.md` には次の「コードレビュー」節を必ず含めます。`agents`モードで旧`REVIEWS.md`だけが存在する場合は移行せず、その既存ファイルを有効な基準として参照するよう節を調整します。両方存在する場合は有効な既存参照を維持し、重要な内容差が確認できたら不確実性を記します。どちらも存在しない場合は節を省略せず、未整備と報告します。
- 次の適用指示は見出しごと含めてください。実際に存在する基準ファイルへの参照を保ち、ファイル不在時の明記を省略しないでください。
- 旧 `REVIEWS.md` の参照がある場合は、Skill本文の「Existing review-file migration」に従います。`agents`モードではファイル移行を行わず有効な旧参照を維持します。`reviews` / `both`モードでは内容を検証し、移行を完了して旧ファイルを削除した後にだけ、新名称へ必要な参照を変更します。競合を解消できない場合は両ファイルとリンクを保護し、参照切れを作りません。
- `.agents/skills/` や `.claude/skills/` 等、実際に存在する探索先を調べ、利用できるSkill名と適用場面を簡潔に案内できます。すべてのエージェントが同じ探索先をサポートすると仮定せず、ベンダー固有の呼び出し構文は共通 `AGENTS.md` に持ち込みません。
- 既存の指示やユーザーの指定を黙って削除・弱体化しません。矛盾があれば報告します。
- 個人の絶対パス、秘密情報、環境依存の資格情報を記載しません。
- 作業報告では原則リポジトリ相対パスを使い、秘密情報を見つけても値を引用・複製せず場所とリスクだけを報告します。
- 要求仕様、ADR、課題表、リスク記録がある場合は、変更に関係するものを確認し、必要な関係をID・リンクで保つよう指示します。

次の節を `AGENTS.md` に含めてください。

```markdown
## コードレビュー

コードレビュー、設計レビュー、プルリクエストのレビューを行う前に、リポジトリルートの `REVIEW.md` を読み、記載されたレビュー基準を適用する。`REVIEW.md` がなく旧 `REVIEWS.md` だけが存在する場合は、移行が完了するまで旧ファイルを読み、旧形式であることを明記する。両方が存在する場合は両方を読み、重要な差異を報告する。どちらも存在しない場合はその旨を報告し、レビュー基準が未整備であることを明記する。
```

## 出力

1. `AGENTS.md` を更新します。既存ファイルがある場合は有効な内容を維持し、重複を整理します。
2. Markdownリンクと記載したコマンド・パスを確認します。要求されていないソース変更やテスト実行は行いません。
3. 報告では、変更したファイル、主要な根拠、未確認事項、実行した確認を簡潔に示します。
