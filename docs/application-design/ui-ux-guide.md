# UI/UXデザイン理論と現代のベストプラクティス

> **対象：Web（HTML/CSS/JavaScript）・ネイティブデスクトップアプリケーション共通**
>
> 版：1.1 / 更新日：2026-10-18 / 対象読者：ソフトウェア設計者、UI/UXデザイナー、Web/デスクトップ開発者、AIコーディングを利用するチーム

## この文書の目的

UI/UXを「見た目を整える仕事」ではなく、**人間の目的達成を支える情報構造・行動・知覚・システム反応を設計する活動**として体系化する。古典的なHCI（Human–Computer Interaction）理論と、2026年時点で有用な設計・実装・検証の実務指針を統合する。

対象プラットフォームはWebとデスクトップの双方。共通理論を中核とし、プラットフォーム固有の制約は切り分ける。モバイル・タッチもレスポンシブ/入力方式の観点で考慮する。

**記述の区分**：

- **[規格]**：公開された標準・達成基準。対象や適用条件を確認する。
- **[実務]**：広く利用される設計慣行。製品特性による例外を許容する。
- **[原則]**：経験則・ヒューリスティクス。絶対的な数値ルールではない。
- **[提案]**：本書が開発時の初期値として提案するルール。ユーザーテストで調整する。

## 1. UI/UXの基本構造

### 1.1 UIとUXの関係

| 概念 | 何を設計するか | 主要な判断基準 |
|---|---|---|
| UX（User Experience） | 利用前・利用中・利用後を含む体験 | 目的達成、信頼、納得、満足 |
| UI（User Interface） | 情報・操作の接点 | 認識、理解、操作、反応 |
| IA（Information Architecture） | 情報と機能の構造 | 発見可能性、分類、一貫性 |
| IxD（Interaction Design） | 操作・反応・状態遷移 | 予測可能性、可逆性、フィードバック |
| Visual Design | 視覚的表現 | 階層、可読性、調和、識別性 |
| Accessibility | 多様な利用者のアクセス可能性 | 知覚可能、操作可能、理解可能、堅牢 |
| Design System | 共通の規約と部品 | 一貫性、再利用、変更容易性 |

**UIはUXを構成するが、UXはUIに還元されない。** 起動速度、データ損失の回避、サービスの信頼性、サポート、プライバシーへの配慮もUXを左右する。

### 1.2 推奨する最上位の設計原則

1. **目的優先**：画面や機能よりユーザーのタスクを起点にする。
2. **認識優先**：記憶させるより、必要な選択肢と状況を見せる。
3. **予測可能性**：同じ操作には同じ意味と結果を与える。
4. **状態の可視化**：処理中・成功・失敗・未保存を区別する。
5. **安全性と可逆性**：誤操作を減らし、可能なら復旧できるようにする。
6. **段階的な複雑性**：初心者を圧倒せず、高度な機能も隠しすぎない。
7. **アクセシブル・バイ・デフォルト**：キーボード、支援技術、拡大表示を最初から考慮する。
8. **プラットフォームへの適合**：WebとOSの慣習を尊重しつつ、製品内の一貫性を保つ。
9. **性能も体験**：応答・安定性・待ち時間をデザイン対象に含める。
10. **データで検証**：「美しい」だけで良しとせず、タスク達成を確かめる。
11. **ユーザーの主体性**：強制・欺瞞・過度な誘導を避ける。
12. **システム化**：デザイントークン、部品契約、レビュー基準を共有する。

UI/UXは実装後の見た目確認に限らず、ユーザーの目的、必要な機能、操作モデル、状態遷移、非同期処理、回復手段を決める入力である。画面がない製品でも、CLIのコマンド/出力、ライブラリのAPI/エラー、バックグラウンドサービスの状態通知など、利用者との接点に応じて人間中心設計を適用する。GUI固有の部品要件はGUIのある製品に限る。

### 1.3 どの理論をどの問題に使うか

| 問題 | 主に参照する理論・手法 |
|---|---|
| メニューが多く迷う | ヒックの法則、IA、情報の香り、カードソート |
| ボタンが押しづらい | フィッツの法則、ターゲットサイズ、入力方式 |
| 情報が雑然としている | ゲシュタルト原則、視覚的階層、チャンク化 |
| 操作した結果が不明 | ノーマンの行為モデル、フィードバック、状態設計 |
| 設定が難解 | メンタルモデル、段階的開示、用語の平易化 |
| 初回利用に時間がかかる | 学習容易性、既存慣習、認識優先 |
| 画面ごとに見た目が違う | Design System、Tokens、Component Contract |
| スマホや狭い窓で破綻 | Responsive/Adaptive、Container Queries、Reflow |
| スクリーンリーダーで使えない | WCAG、Semantic HTML、ARIA APG、OS Accessibility API |
| 見た目は軽快だが実際は遅い | ユーザー中心の性能指標、INP/LCP/CLS、処理状態 |

## 2. 人間中心設計とUXリサーチ

### 2.1 Human-Centred Design（HCD）

**[規格] ISO 9241-210:2019** は対話システムの人間中心設計の原則と活動を扱う。2019年版は2025年に再確認され、2026年10月時点で現行版。Webサイトやネイティブアプリを含む幅広いシステムを対象とする。

実務上、次のサイクルで扱う。

```text
利用状況の理解
    ↓
ユーザー要求の特定
    ↓
設計解の作成
    ↓
要求に対する評価
    └────────→ 必要に応じて反復
```

### 2.2 利用者ではなく「利用状況」まで捉える

ユーザーが同じでも、作業場所、画面サイズ、入力装置、専門知識、時間的制約、ミスの影響によって最良のUIは変わる。

**調査対象**：

- ユーザーの目的：何を終えたいのか。
- 作業状況：どの機器、場所、ネットワーク、入力方法で使うか。
- 頻度：毎日使うのか、年に一度だけ使うのか。
- リスク：間違えると何が失われるのか。
- 代替手段：既存ツールでどのように達成しているか。
- 習熟度：日常操作と専門操作の差はどの程度か。

### 2.3 調査と構造化の手法

| 手法 | 目的 | 留意点 |
|---|---|---|
| インタビュー | 動機、言葉遣い、困難の把握 | 言ったことと実際の行動は異なり得る |
| コンテキスト観察 | 現実の作業環境を理解 | 観察者効果を考慮 |
| タスク分析 | 行動を目標・手順・例外に分解 | 正常系だけに限定しない |
| ジャーニーマップ | 時間軸で体験の断絶を見つける | 検証前の仮説を事実扱いしない |
| Jobs to Be Done | 利用者が達成したい進歩に注目 | 人物属性だけでは理解できない動機を扱う |
| カードソート | ユーザーの自然な分類を探る | 少人数の結果を普遍化しない |
| ツリーテスト | ナビゲーション構造の探索性を検証 | 見た目を切り離し構造を検証する |
| プロトタイプテスト | 操作手順や理解を検証 | 実装前に低コストで確認する |

### 2.4 メンタルモデルと概念モデル

- **メンタルモデル**：ユーザーがシステムについて持つ予測・理解。
- **概念モデル**：設計者がUIを通して伝えようとするシステム像。
- **実装モデル**：内部のデータ構造や技術的制約。

これらは必ずしも一致しない。内部APIが `volume.detach()` でも、UIの「取り外す」がファイル削除と誤解されるならラベルや説明を再設計する。

<a id="sec02-design-to-function"></a>

### 2.5 UI/UXから機能要求を導く

理論をそのまま画面ルールに置き換えるのではなく、対象ユーザー・タスク・利用状況・ミスの影響を根拠に、次の連鎖で機能を設計する。

```text
利用状況・ユーザー目標
  → 理論・観察から得た設計根拠
  → 操作モデル・状態・ドメイン/アプリケーション機能
  → 検証可能な受け入れ条件
  → 適切なユーザー調査・テスト・計測
```

| 理論・観点 | 設計上の判断 | 必要な機能・振る舞いの例 | 受け入れ条件の例 | 検証方法の例 |
|---|---|---|---|---|
| Human-Centred Design / User Goals / Jobs to Be Done | 属性より達成したい進歩、状況、頻度、失敗影響から優先順位を決める | 主要タスクを完了する一連の機能、現状作業からの移行支援 | 代表ユーザーが定義した主要タスクと成功結果を達成できる | 文脈調査、タスク分析、代表ユーザーによるタスクテスト |
| Mental / Conceptual Models、Consistency、Affordance / Signifiers | 利用者の語彙・既存の予測と機能の意味を合わせ、操作可能性と結果を示す | 分かりやすい用語、明示的な操作、予測可能な結果と既定値 | 対象者が操作の結果・対象を誤解せず説明できる | 用語理解テスト、ヒューリスティックレビュー、実利用観察 |
| Norman's Action Cycle、Feedback / Feedforward | 実行前に可能な行動と影響を理解でき、実行後に結果を評価できるようにする | 事前プレビュー、進捗・完了状態、選択対象と結果の対応 | 主要操作の前に影響を認識でき、後に成功・失敗・未確定が区別できる | 状態遷移テスト、タスク観察、操作後の理解確認 |
| Nielsen's Usability Heuristics、Error Prevention / Recovery | 状態を見せ、誤りを予防し、ユーザー制御・回復を設計する | 入力検証、Undo、取消、再試行、部分成功結果、回復手順 | 代表的な誤りを防止でき、失敗時に安全な回復手段が分かる | 境界値テスト、障害シナリオ、復旧タスクテスト |
| Hick–Hyman Law / Cognitive Load Theory | 選択肢・同時表示情報をタスクと熟練度に合わせて整理する | 優先操作、分類、既定値、段階的開示 | 主要タスクで必要な選択・情報を認識でき、高度な機能も必要時に到達できる | 選択時間・誤りの観察、ツリーテスト、認知的ウォークスルー |
| Recognition over Recall / Progressive Disclosure / Information Architecture | 覚えるより見て認識できる構造にし、機能を目的に沿って配置する | 検索、履歴、説明、状態ラベル、関連機能への経路 | 初見利用者が主要機能を発見し、再利用者が過剰な手順なく到達できる | 発見可能性テスト、ツリーテスト、利用者タスク観察 |
| Fitts's Law / Accessibility / Inclusive Design | 操作頻度・精度・入力手段・能力の幅に合わせて到達性と代替経路を設ける | キーボード操作、ショートカット、十分な操作領域、支援技術向け状態 | キーボード等の対象入力だけで主要タスクを完了できる | キーボード・支援技術テスト、対象環境での操作確認 |
| 非同期タスクと実際の状態モデル | 待ち・中断・競合・部分成功がドメイン処理に与える影響を定義する | タスク単位の進捗、キャンセル、再開、再試行、結果一覧 | キャンセル時点と適用済み変更が一貫し、再試行で重複副作用が起きない | 状態機械/統合テスト、障害注入、重複実行テスト |

ここでの受け入れ条件は例であり、心理法則や経験則から数値閾値を自動的に導出しない。数値を設定する場合は対象ユーザー、タスク、環境、ベースラインと測定方法を明らかにする。調査できていない利用者像や仮説は事実として扱わず、仮定と検証方法を要求仕様に記す。

#### タスクから操作・状態・機能へ分解する

1. 利用者の目的、成功結果、頻度、利用環境（入力方法・画面密度・言語/テーマ・OS慣習を含む）、代替手段、誤りの影響を記述する。
2. タスクを開始条件、必要情報、操作、結果、例外・中断・回復へ分解する。
3. 各段階に必要なドメイン能力、アプリケーション処理、表示/出力、永続状態を割り当てる。
4. 主要操作と補助操作を優先し、発見可能性、取消可能性、明示的同意が必要な箇所を決める。初心者には分かりやすい導線を、熟練者には検索・ショートカット・一括操作等の効率経路を必要に応じて用意する。
5. Idle / Loading / Empty / Error / Partial Success / Offline等のうち必要な状態と状態遷移を定義する。
6. 各要求に観測可能な受け入れ条件と検証方法を付け、要求IDから設計・実装・検証を必要な範囲で追跡する。

要求や機能設計では、必要な観点だけを選んで明記する。

| 設計対象 | 設計判断・要求へ反映する内容 |
|---|---|
| 発見可能性・優先順位 | 主要操作の発見経路、補助操作・高度な操作の配置、初心者/熟練者向けの経路 |
| 可逆性・破壊的操作 | Undo/Redoや復元が可能な範囲、影響の事前説明、プレビュー、明示的確認が必要な操作 |
| 状態・非同期処理 | Loading / Empty / Error / Partial Success等の必要状態、進捗・キャンセル・再試行・再開と処理上の意味 |
| 規模・効率 | 大量データや一括処理で必要な段階表示、遅延読み込み、仮想化、バッチ処理、上限・バックプレッシャー |
| 入力・アクセシビリティ | キーボード・マウス・タッチ・支援技術で必要な代替操作、フォーカス・状態通知 |
| 利用環境 | 多言語・長い文言、表示密度、テーマ、ズーム、OS/ブラウザー慣習への必要な対応 |

これらはすべての製品・機能への必須チェックではない。適用する設計判断は根拠を示し、除外が重要なリスクを残す場合は理由や受け入れ可能性も記録する。

例えばファイルコピーの「キャンセル」はキャンセルボタンの表示だけでは完了しない。処理識別子、停止可能な境界、既に書き込んだファイルの扱い、原子的な置換/部分ファイルの除去方針、再開・再実行時の重複、結果通知を定義する。受け入れ条件には、取消後に対象がどの状態になるか、成功済み項目と未完了項目を区別できるか、再実行時に破損・重複が起きないかを含め、必要な統合・障害復旧テストで検証する。

#### 製品形態に応じた接点

| 製品形態 | 人間中心設計の主な対象 | GUI固有要件の扱い |
|---|---|---|
| Web / デスクトップ | タスクフロー、画面・フォーカス、状態、入力方式、OS/ブラウザー慣習 | 適用。キーボード、支援技術、リサイズ等は対象環境に応じて検証 |
| CLI | コマンド発見、引数・既定値、ヘルプ、進捗、終了コード、再実行性 | 画面レイアウト規約は適用しない。端末支援技術やパイプ利用を必要に応じ考慮 |
| ライブラリ/API | 利用者のユースケース、型・関数の発見、契約、エラー、互換性 | GUI部品は適用しない。APIの予測可能性・診断可能性・安全な既定値を設計 |
| バックグラウンド/サービス | 起動設定、運用操作、状態・結果通知、復旧・監視 | GUIの有無を問わず運用者のタスクと診断手段を設計 |

## 3. 認知心理学・HCIの基礎法則

### 3.1 ヒック＝ハイマンの法則（Hick–Hyman Law）

選択肢が多くなると選択に要する時間が増える傾向を示す。単純化した形：

\[
T = a + b\log_2(n+1)
\]

**適用**：機能を意味のあるカテゴリに整理する、検索を付ける、利用頻度の高い操作を見つけやすくする。

**誤用に注意**：項目を隠すほど良いわけではない。階層が深いと探索が長くなり、ラベルの曖昧さも負担を増やす。

### 3.2 フィッツの法則（Fitts's Law）

ポインター操作時間は対象までの距離とターゲット幅に依存する。

\[
MT = a + b\log_2(1 + D/W)
\]

- `D`：ターゲットまでの距離
- `W`：移動方向に対するターゲットの有効幅

**適用**：頻出ボタンに十分なクリック領域、ドラッグハンドルに明瞭な当たり判定、余裕ある操作間隔を設ける。

**誤用に注意**：危険操作を大きく目立たせることが常に正しいわけではない。精度・安全性・操作頻度を同時に考える。

### 3.3 ヤコブの法則（Jakob's Law）

人は他製品で慣れた操作法を新しい製品にも期待する。

- Web：リンクはリンクらしく、フォームは既存の操作慣習に沿う。
- デスクトップ：メニュー、コンテキストメニュー、キーボードショートカット、ウィンドウ操作などを尊重。
- 独自性は **タスクの価値** に向け、慣れた基本操作まで無闇に再発明しない。

### 3.4 ミラーの法則・チャンク化

短期記憶に関する有名な「7±2」は、**UIの項目数を必ず7つ以下にする**という規則ではない。記憶課題、情報の意味、熟練度によって変動する。

**適用**：関連情報を意味単位でまとまりにする。例：ディスクの「基本情報」「ファイルシステム」「接続状態」を分ける。

### 3.5 認知負荷理論

作業記憶には制約がある。タスクそのものの複雑さ（内在的負荷）と、表示や手順が増やしている不要な負荷（外在的負荷）を区別する。

**設計方針**：本質的に難しい操作を無理に単純化するのではなく、不要な判断・記憶・行き来を減らす。

### 3.6 ゴール指向と認識・想起

- **Recognition over Recall**：候補や状態を画面上で認識できるようにする。
- **Information Scent**：メニュー名やリンクから遷移先を予測できるようにする。
- **Progressive Disclosure**：必要になった時点で高度な設定を示す。ただし重要な機能まで深く隠さない。

### 3.7 ピーク・エンドの法則等の扱い

体験における印象や記憶を説明する心理学的知見は参考になるが、これをもって警告や失敗処理を省いて「最後だけよく見せる」べきではない。UXは実際のタスク成功と安全性で検証する。

## 4. 情報アーキテクチャとナビゲーション

### 4.1 機能中心ではなくタスク中心

設計対象を `機能一覧 → メニュー化` とするだけではなく、`タスク → 必要情報 → 操作手順 → UI` の順に検討する。

例：

```text
目的：既存仮想ディスクの容量を増やす
  ├─ 対象ディスクを見つける
  ├─ 現在容量・最大容量・マウント状態を把握する
  ├─ 拡張可能か確認する
  ├─ 新しい容量を指定する
  ├─ 影響範囲を確認する
  ├─ 実行する
  └─ 完了後に結果を確認する
```

### 4.2 ナビゲーションパターン

| パターン | 適した状況 | 弱点 |
|---|---|---|
| Sidebar | 複数の主要領域があるWeb/デスクトップ | 狭い幅で占有が大きい |
| Tabs | 同じ文脈内の近接した画面切替 | タブが増えすぎると破綻 |
| Breadcrumb | 階層が深い情報への移動 | 単体では全体像を示せない |
| Search / Command Palette | オブジェクトや機能が多い | 存在を知らない操作は検索しにくい |
| Context Menu | 対象に関係する操作 | 非表示なので発見性が低い |
| Wizard / Stepper | 順番が重要な多段階操作 | 簡単な操作には冗長 |
| Split View | 一覧と詳細の行き来が多い | 小画面では再構成が必要 |

### 4.3 現代的な複雑性管理

**[実務] Progressive Disclosure + Power User Path** を併用する。

- 初期画面：主なタスクと必要な状態を明瞭にする。
- 詳細画面：高度な設定や診断情報を展開できる。
- 熟練者経路：キーボードショートカット、検索、複数選択、一括操作等を提供。
- 危険操作：高度な機能であっても意味と影響を説明する。

### 4.4 情報密度を用途で選ぶ

情報密度は少ないほど良いわけではない。専門家向けの管理画面では、一度に比較できる情報が多い方が有効なこともある。

**[提案]** `Comfortable / Compact` などの密度オプションを検討し、適切なクリック領域や文字の可読性を犠牲にしない。

## 5. インタラクションと状態の設計

### 5.1 ノーマンの行為モデル

ユーザーが「何をすればよいか」を判断するまでを**実行の隔たり**、操作後に「何が起きたか」を理解するまでを**評価の隔たり**として捉える。

```text
目標 → 意図 → 操作の選択 → 実行
  ↑                         ↓
結果の解釈 ← 状態の知覚 ← システム状態
```

**設計上の問い**：

1. 操作対象と次の行動を見つけられるか。
2. 操作の意味を理解できるか。
3. 押した/入力した結果が分かるか。
4. 完了したことを判断できるか。
5. 失敗したとき回復できるか。

### 5.2 アフォーダンス、シグニファイア、マッピング

- **アフォーダンス**：対象と利用者の関係における行為の可能性。
- **シグニファイア**：操作可能性を知らせる手掛かり。ボタン境界、ラベル、ハンドル、カーソルなど。
- **マッピング**：操作と結果の対応関係。サイズスライダーとプレビューサイズの対応など。

Flat Designでは装飾を削りすぎてシグニファイアを失わないことが重要。

### 5.3 状態モデルを先に定義する

| 状態 | UIの責務 | 典型的な操作 |
|---|---|---|
| Empty | 空の理由と開始行動を示す | 新規作成、インポート |
| Idle | 選択肢を明瞭にする | 編集、開始 |
| Editing / Dirty | 未保存を明示する | 保存、破棄 |
| Validating | 検証中または検証結果を示す | 修正 |
| Loading / Processing | 進捗と待機の意味を伝える | キャンセル可能なら中断 |
| Success | 成功した内容を確認可能にする | 次のタスク、詳細を見る |
| Error | 失敗理由と対応方法を示す | 再試行、詳細表示 |
| Partial Success | 何が成功し失敗したか分ける | 残りを再試行 |
| Offline / Unavailable | 制限と復帰条件を示す | 再接続、オフライン作業 |

### 5.4 エラーの原則

- **予防優先**：入力制約、事前検証、プレビュー。
- **復旧重視**：Undo/Redo、再試行、途中再開、保存復元。
- **意味を説明**：`エラー 0x…` だけにしない。
- **責任を押し付けない**：具体的にどこを直せばよいか記す。
- **重大操作は影響を確認**：削除対象、件数、不可逆性、依存関係を明示。
- **偽の可逆性を示さない**：元に戻せない処理を「あとで戻せます」と書かない。

### 5.5 非同期処理とキャンセル

- 視覚的な処理中表示を出すだけでなく、操作の多重送信を防ぐ。
- キャンセルの意味を定義する：即時停止か、次の安全な境界で中断か。
- 「中断可能」「バックグラウンド継続」「既に適用済み」を区別する。
- 複数処理が並行する場合は、タスク単位で進捗・結果を残す。

### 5.6 フォーム設計

- ラベルを常時識別できるようにする。**placeholderを唯一のラベルにしない。**
- 必須/任意、単位、許容範囲を事前に示す。
- 検証は適切な時点で行い、入力途中の過剰なエラー連発を避ける。
- エラーはフィールド近傍と必要に応じた集約表示の両方で示す。
- 意図せぬデータ損失を防止する。
- 高リスク操作では確認を要求するが、全操作に毎回確認ダイアログを出さない。

## 6. 視覚デザインとゲシュタルト原則

### 6.1 ゲシュタルト原則

| 原則 | 認知的な傾向 | UIでの適用 |
|---|---|---|
| 近接 | 近い要素を関連付ける | ラベルと入力欄、操作と対象 |
| 類同 | 見た目が似ると同種と判断する | 同一操作のボタンを統一 |
| 共通領域 | 囲まれた要素をまとまりと見る | パネル、フォームグループ |
| 連続 | 配列・線を追いやすい | グリッド、ステップ表示 |
| 図と地 | 前景と背景を分離して見る | モーダルと背後の画面 |
| 閉合 | 欠けた形を補完する | シンプルなアイコン |

### 6.2 視覚的階層

`Primary > Secondary > Tertiary` の意味上の優先順位を、コントラスト、サイズ、余白、位置、太さ等の**組み合わせ**で示す。

- 同一画面の主要操作を無制限にPrimaryにしない。
- 危険操作は他の強調と区別する。
- 情報の重要性と文字サイズを一貫させる。
- 余白をグループ境界として活用し、カード/枠線を増やしすぎない。

### 6.3 デザイントークンの推奨分類

| 種別 | 例 | 主な役割 |
|---|---|---|
| Color | `surface`, `text.primary`, `action.primary`, `danger` | 意味の一貫性 |
| Typography | `body`, `label`, `heading`, `caption` | 可読性と階層 |
| Spacing | `space.1`, `space.2`, `space.4` | 配置・関連性 |
| Radius | `radius.sm`, `radius.md` | 部品の視覚言語 |
| Border/Elevation | `border.subtle`, `shadow.popover` | 面の分離 |
| Motion | `motion.fast`, `motion.standard` | 遷移の連続性 |
| Density | `density.comfortable`, `density.compact` | 情報量と操作性 |

**[提案]** 4pxまたは8px系スケールを初期案として採用してよい。ただし規格値ではない。文字の読みやすさ、操作対象、UI密度によって検証・調整する。

### 6.4 色とコントラスト

- 色だけで状態を識別させない。アイコン、テキスト、形状を併用する。
- ダークモードは単に白黒反転するのではなく、サーフェス階層と色の意味を再設計する。
- 主要テキストと背景の対比を維持する。
- 成功/警告/危険を単純な装飾色と混同しない。
- 文字、アイコン、罫線、フォーカスの可視性をそれぞれ確認する。

### 6.5 タイポグラフィ

- 用途に対応する固定的な階層を設ける。
- 本文、見出し、補助情報を安易に極小化しない。
- 行間、文字間、テキスト幅を見直す。
- 長文本文は適切な行長を確保し、密度の高い表には別ルールを適用する。
- 日本語・英語など混在文では字形・折り返し・行高を実機で確認する。

### 6.6 Motion / Microinteraction

アニメーションは「派手さ」より、状態変化・空間的連続性・因果関係の理解に使う。

- 開閉や並び替えの位置関係を伝える。
- 重要な操作をアニメーション完了待ちにしない。
- OS/ブラウザーの Reduced Motion 設定を尊重する。
- 反応速度の実測・知覚を悪化させない。

## 7. アクセシビリティとインクルーシブデザイン

### 7.1 基本方針

**[規格] WCAG 2.2** をWebの実務的な達成基準として参照する。2026年10月時点でWCAG 3.0は草案であり、WCAG 2.2と同列の完成した適合基準として扱わない。デスクトップでもWCAGの原則を参考にするが、**WebのWCAG適合とネイティブOSのアクセシビリティ対応は別の検証対象**である。

WCAGのPOUR原則：

1. **Perceivable**：知覚できる。
2. **Operable**：操作できる。
3. **Understandable**：理解できる。
4. **Robust**：支援技術等と相互運用できる。

### 7.2 よく使うWCAG 2.2の達成基準

| 項目 | 目安 / 基準 | 補足 |
|---|---|---|
| 通常テキストのコントラスト | **4.5:1以上**（AA、原則） | ロゴ等に例外あり |
| 大きなテキストのコントラスト | **3:1以上**（AA、原則） | 規格上の「大きなテキスト」の定義を確認 |
| 意味を持つ非テキストUIのコントラスト | **3:1以上**（AA、原則） | UI境界や状態表示等、適用条件あり |
| ターゲットサイズ | **24×24 CSS px以上**（AA） | 間隔・インライン等の例外あり |
| ターゲットサイズ（強化） | **44×44 CSS px以上**（AAA） | 例外あり。すべてに必須ではない |
| フォーカス可視 | キーボードフォーカスを視覚的に識別 | `Focus Visible` 等を参照 |
| ドラッグ操作 | 必須なドラッグに代替操作を用意 | WCAG 2.2 2.5.7 AA、例外あり |
| フォーカスの遮蔽 | フォーカス対象が完全には隠れない | WCAG 2.2 2.4.11 AA |
| 認証 | 不必要な認知機能テストを避ける | WCAG 2.2 3.3.8 AA |

**注意**：`24 CSS px` をデスクトップGUIの論理ピクセルや物理ピクセルへ機械的に読み替えない。OSスケーリングや入力装置に応じて実利用で確認する。

### 7.3 支援技術と入力手段

- キーボードのみで主要タスクを完遂できる。
- フォーカス順序が視覚上・操作上の意味と一致する。
- スクリーンリーダーに名前・役割・状態・値を伝える。
- マウスホバー専用の情報・操作を設けない。
- 音・色・動きのみで重要情報を伝えない。
- ズーム、文字拡大、ハイコントラスト、Reduced Motion を確認する。
- フォームエラーは音声でも分かる文言と関連付ける。

### 7.4 インクルーシブデザイン

「平均的なユーザー」を前提にせず、視覚・運動・認知・言語・環境の多様性を扱う。障害の有無だけでなく、疲労、片手操作、眩しい環境、狭い画面、遅い回線も考慮する。

**[実務]** 自動テストだけでは不十分。キーボード実操作、スクリーンリーダー、画面拡大、ユーザーテストを併用する。

## 8. レスポンシブ・アダプティブUI

### 8.1 画面サイズから利用状況へ

- **Responsive**：利用可能な領域に応じて流動的に再配置する。
- **Adaptive**：利用環境や条件に応じて異なる構成・振る舞いを選ぶ。
- **Content-first**：先に必要な情報と優先順位を決め、幅に合わせて再構成する。
- **Input-aware**：タッチ、マウス、ペン、キーボードの違いを考慮する。

`Web=モバイル、Desktop=広い画面` という単純化は避ける。デスクトップの細いウィンドウ、ブラウザーのズーム、タブレット上のマウス操作などが存在する。

### 8.2 レイアウト変化の考え方

| 条件 | 推奨する考え方 |
|---|---|
| 狭い画面 / 狭いウィンドウ | 情報の優先順位に基づき1列化、補助ペインを折り畳む |
| 中間幅 | ナビゲーションを縮小、一覧と詳細を必要に応じて切替 |
| 広い画面 | マルチペイン・比較表示・一覧＋詳細を活用 |
| タッチ中心 | ターゲット、間隔、ドラッグ代替を増強 |
| キーボード中心 | フォーカス、ショートカット、コマンド検索を強化 |
| 画面拡大 / 高DPI | 固定幅・固定高さによる欠落を避ける |

### 8.3 現代Web：Media QueriesとContainer Queries

- `@media`：ビューポート、ユーザー設定、入力方式等に応じた分岐。
- `@container`：**コンポーネントを収める領域**の大きさに応じた分岐。
- `clamp()`：値の最小/推奨/最大を指定する流動的な文字・余白設計に有用。
- `minmax()` / Grid / Flexbox：固定ブレークポイントだけに頼らない自然な再配置。

Container Queriesは、同じカードをサイドバーとメイン領域で再利用するような設計に向いている。

### 8.4 レスポンシブに伴う重要な制約

- 列数を減らした結果、情報・機能が消えないようにする。
- ナビゲーションを省略する場合、到達経路を保つ。
- モーダルは狭い領域や拡大率でも操作可能にする。
- データテーブルは無理なカード化が常に正解ではない。横スクロール、列選択、詳細展開等をタスクに応じて選ぶ。
- ブレークポイントは単なるデバイス名ではなく、コンテンツが破綻する条件から導く。

## 9. デザインシステムとDesign Tokens

### 9.1 現代的な構成

```text
Design Principles
    ↓
Design Tokens（値・意味・テーマ・密度）
    ↓
Primitive Components（Button / Text / Surface）
    ↓
Composite Components（Table / Dialog / Form）
    ↓
Interaction Patterns（検索 / 編集 / 一括操作）
    ↓
Screens / Flows（ユーザーのタスク）
    ↓
評価・監視・改善 → 全階層へフィードバック
```

### 9.2 Primitive / Semantic / Component Tokens

| レイヤー | 例 | 責務 |
|---|---|---|
| Primitive | `blue.500`, `gray.900`, `space.4` | 基本値の集合 |
| Semantic | `text.primary`, `surface.raised`, `status.error` | 目的と意味 |
| Component | `button.primary.bg`, `dialog.border` | 個々の部品仕様 |

**[実務]** コンポーネントが直接 `blue.500` を参照し続けるより、意味上の色を通して参照するとテーマ変更に強い。

### 9.3 Design Tokensの仕様状況

2025-10-28に **Design Tokens Community Group (DTCG) 2025.10** の最初の安定版が公開された。ツール間のトークン交換とテーマ表現に使える。ただし**W3C Community Group Reportであり、W3C Recommendationではない**。

- 複数プラットフォームで共通の意味トークンを持てる。
- WebではCSS Custom Propertiesへ変換できる。
- Rust等のネイティブアプリでは定数・テーマ構造体などへ変換できる。
- 自動変換は導入ツールの対応状況を確認する。

### 9.4 コンポーネント契約（Component Contract）

単に「角丸8pxのボタン」と定義するのでは不十分。振る舞いまで含める。

```text
Component: PrimaryButton
Purpose: タスクの主操作
States: default / hover / focus / active / disabled / loading
Inputs: label, icon?, enabled?, busy?, action
Keyboard: Enter / Space（実装基盤に準拠）
Accessibility: accessible name, focus indicator, busy/disabled semantics
Error: action failure is handled by the enclosing flow
Theme: light / dark / high-contrast
Density: comfortable / compact
```

### 9.5 UI設計で分離すべきもの

- **ドメイン状態**：保存済み、接続中、権限なし等。
- **UI状態**：選択中、ダイアログ表示中、hover、focus等。
- **非同期状態**：進捗、完了、失敗、キャンセル。
- **プレゼンテーション**：色、文字、余白、表示密度。

この分離により、UIの見た目変更がビジネスルールを壊すことを防ぎやすい。

## 10. Web（HTML/CSS/JavaScript）固有のベストプラクティス

### 10.1 Semantic HTMLを第一選択にする

**[実務]** ネイティブなHTML要素を使えば、標準の意味・キーボード挙動・支援技術連携を利用しやすい。

- 操作：`<button>`
- 遷移：`<a href="...">`
- 入力：`<label>` と `<input>`
- 構造：`<main>`, `<nav>`, `<header>`, `<section>`
- データ表：`<table>`（レイアウト用には使わない）
- 意味ある一覧：`<ul>` / `<ol>`
- ダイアログ：適切な意味・フォーカス管理を持つ実装。`<dialog>` も検討。

`<div onclick="...">` を安易にボタン代わりにしない。

### 10.2 ARIAはHTMLの代用品ではない

W3C ARIA Authoring Practices Guide（APG）を参照して、必要な場合にARIAの役割、状態、キーボード操作を追加する。

**不完全なARIAは改善ではない。** 例えば `role="button"` を付けても、フォーカス、Enter/Space対応、無効状態の管理は自動では実装されない。

### 10.3 HTMLフォームの最小例

```html
<form>
  <label for="disk-name">ディスク名</label>
  <input
    id="disk-name"
    name="diskName"
    type="text"
    required
    aria-describedby="disk-name-help"
  />
  <p id="disk-name-help">拡張子は自動的に付与されます。</p>
  <button type="submit">作成する</button>
</form>
```

**追加要件**：実際の処理では重複送信防止、入力検証、非同期状態、送信結果の通知、必要に応じたエラーの関連付けを設計する。

### 10.4 レスポンシブCSSの一例

```css
:root {
  color-scheme: light dark;
  --space-2: 0.5rem;
  --space-4: 1rem;
  --layout-gap: clamp(0.75rem, 2vw, 1.5rem);
}

.workspace {
  display: grid;
  grid-template-columns: minmax(13rem, 17rem) minmax(0, 1fr);
  gap: var(--layout-gap);
}

@media (width < 50rem) {
  .workspace { grid-template-columns: minmax(0, 1fr); }
}

.panel-container { container-type: inline-size; }
.card-layout { display: grid; grid-template-columns: 1fr; }
@container (width >= 38rem) {
  .card-layout { grid-template-columns: 1fr 1fr; }
}

@media (prefers-reduced-motion: reduce) {
  .nonessential-motion { animation: none; transition: none; }
}
```

上記は概念例。実際のサポートブラウザー、部品階層、ユーザー設定に合わせて検証する。

### 10.5 Web固有の注意点

- `:focus-visible` 等でフォーカスを見失わせない。
- ページ/ダイアログ遷移でフォーカスと読み上げ文脈を管理する。
- Client-side routingでもページタイトルや見出しを更新する。
- 履歴（戻る/進む）、リンク共有、リロード、深いURLへの直接アクセスを考慮する。
- 失敗しやすい通信には再試行とオフライン時の表示を用意する。
- 読み込み後の要素挿入によりボタン位置が突然変わることを防ぐ。
- `prefers-color-scheme`、`prefers-reduced-motion` 等のユーザー設定を可能な範囲で尊重する。
- ランディングページと複雑なWebアプリでは、最適な情報密度・ナビゲーション構造が異なる。

## 11. デスクトップ固有のベストプラクティス

### 11.1 OSの慣習と製品内一貫性

- ウィンドウの最小化・最大化・サイズ変更・複数ウィンドウ・DPIを考慮する。
- ショートカットはOS慣習と衝突しないようにする。
- ファイルダイアログ、ドラッグ&ドロップ、クリップボード、コンテキストメニューは標準挙動を尊重する。
- 終了操作と「バックグラウンド継続 / トレイ常駐」を区別する。
- OSのテーマ、ハイコントラスト、入力設定、支援技術への接続を確認する。

### 11.2 情報密度と多重タスク

デスクトップでは、一覧・詳細・プレビュー・操作パネルを同時表示できる利点がある。ただし「広い画面前提」にせず、縮小ウィンドウでの再配置やスクロールも考慮する。

- 複数選択、並べ替え、絞り込み、検索、列の表示切替。
- スプリットビューの分割位置保持。
- 選択対象・操作対象の視覚的一致。
- 操作履歴・長時間タスクの一覧。
- キーボードとマウスの往復回数を減らす。

### 11.3 Rust / icedへの適用例

**特定のライブラリに依存しない設計方針**：

```text
Domain Model / Use Cases
          ↓
Application State & Commands
          ↓
UI State / Message / Update
          ↓
Components / Theme / Design Tokens
          ↓
Renderer / OS Integration
```

- ドメインオブジェクトを画面部品と直接結合しない。
- 見た目・ラベル・処理命令・OS操作を層で分離する。
- ネイティブ部品のアクセシビリティ対応は、実際のライブラリ・OS・バージョンで確認する。WebのHTML/ARIA相当の能力が自動的にあると仮定しない。
- 非同期コマンドの成功/失敗/途中経過を明示的にUIへ伝達する。

## 12. 性能・待ち時間・知覚的パフォーマンス

### 12.1 WebのCore Web Vitals

**[実務/Googleの推奨指標]** Web UXに関連する性能を、実ユーザーのフィールドデータで検証する。

| 指標 | 何を測るか | Goodの目安 |
|---|---|---|
| LCP（Largest Contentful Paint） | 主コンテンツの表示速度 | **2.5秒以下** |
| INP（Interaction to Next Paint） | 操作への応答性 | **200ms以下** |
| CLS（Cumulative Layout Shift） | 予期しないレイアウト移動 | **0.1以下** |

これらは推奨される **75パーセンタイル**で判定する。すべてのページ・操作がその値以下という意味ではない。Core Web VitalsはUXの**一部**であり、タスク完了率や理解度を置き換えない。

### 12.2 デスクトップの性能UX

Web指標のLCP/INPをネイティブアプリの規格値として流用しない。代わりに、実際のタスクに対応する指標を設ける。

- 起動から操作可能になるまでの時間。
- クリック・キー入力から視覚応答までの遅延。
- 大量一覧表示時のスクロール安定性。
- ファイル処理・ディスク操作など長時間タスクの進捗更新。
- 一時停止/再試行/復旧までの所要時間。

### 12.3 知覚的な応答設計

- 処理が始まったことを早期にフィードバックする。
- スケルトンはレイアウトが予測できる場合に使い、実際の処理進捗を偽らない。
- 操作結果が確認できるまで状態の整合性を保つ。
- 楽観的更新（Optimistic UI）は、失敗時に確実なロールバックや調整が可能な操作で検討する。
- 一括/破壊的/高リスク操作で「成功したように見せる」更新をしない。

## 13. 国際化・多言語・テーマ設計

### 13.1 Internationalization（i18n）とLocalization（l10n）

- **i18n**：翻訳や地域差に対応できる構造を最初から作る。
- **l10n**：特定言語・地域向けの文言、形式、習慣へ調整する。

実践事項：

1. 文言をコードのロジックから分離し、意味あるキーで管理する。
2. 複数形・選択式・変数挿入等を扱う。文字列連結で文章を組み立てない。
3. 数字、日付、時刻、通貨、単位、並び順をロケールに応じて処理する。
4. ラベルの長さと折り返しを許容する。
5. RTL（右から左）の言語に対応できるレイアウトを検討する。
6. エラーメッセージ、ツールチップ、支援技術向けラベルも翻訳対象に含める。

### 13.2 Webの言語情報

```html
<html lang="ja">
  <body>
    <p>日本語の説明 <span lang="en">Save As</span></p>
  </body>
</html>
```

言語は `lang`、文章方向は必要に応じて `dir` で示す。ユーザー入力など双方向テキストが混ざる場合は適切な要素・属性を使う。

### 13.3 デスクトップの文言管理

RustならFluentのようなメッセージ形式は有力な選択肢となる。**翻訳キー、変数、複数形、語順、ロケール別フォーマット**を設計し、UI要素の幅を言語依存の固定長で決めない。

### 13.4 テーマの基本

- Light、Dark、OS追従、必要に応じてHigh Contrast。
- 色はSemantic Tokenで管理する。
- フォーカス、選択、エラー、ホバー等すべての状態をテーマごとに検証する。
- 選択テーマが保存・復元され、システム設定変更にも適切に対応する。
- ダークテーマ既定は製品方針として妥当だが、明るい場所・印刷・視覚特性等を理由とした切替を妨げない。

## 14. 信頼性・プライバシー・倫理

### 14.1 ダークパターンを避ける

ユーザーを意図しない選択へ誘導するデザインは、短期の成果指標を改善しても、信頼や長期的UXを損なう。

回避すべき例：

- キャンセルだけ極端に見つけにくい。
- 明確な同意がないのに有効化する。
- 「今すぐ決定しないと損」と偽の緊急性を作る。
- 破棄・削除などの文言を曖昧にする。
- 課金条件やデータ収集の目的を隠す。

米FTCの報告書も、利用者の選択を歪めるダークパターンの問題を整理している。

### 14.2 Privacy by Design

- 必要な情報のみ収集する。
- 権限取得は文脈に合うタイミングで要求する。
- なぜ必要か、何が起きるか、後から変更可能かを説明する。
- ログ・分析データに機密情報を不用意に含めない。
- エラー報告やクラッシュレポートでも利用者の同意と透明性を確保する。

### 14.3 破壊的操作の安全設計

操作のリスクに応じて、**選択対象の再確認 / 変更プレビュー / 意味の明示 / バックアップ推奨 / 実行権限制御**を組み合わせる。単純な「本当によろしいですか？」の大量表示だけでは安全にならない。

## 15. AIを含むUI/UXの現代的設計

### 15.1 AIインタラクションの固有課題

従来UIは決定論的な処理を前提にすることが多いが、生成AIや推薦AIでは誤答、不確実性、再現性、説明可能性、権限の範囲が追加課題となる。

**参照枠組み**：Microsoft Researchの *Guidelines for Human-AI Interaction*（18指針、2019年）およびGoogle *People + AI Guidebook*。新しい製品だからといって、従来のHCI原則が無効になるわけではない。

### 15.2 AI機能を設計する際の指針

| 原則 | 具体化 |
|---|---|
| 能力と限界の明示 | できること、できないこと、誤りの可能性を知らせる |
| ユーザー主体 | 提案を採用・編集・拒否できるようにする |
| 出所と根拠 | 参照した情報、処理範囲、変更点を示せるようにする |
| 不確実性の伝達 | 根拠のない断定や架空の確率を表示しない |
| プレビューと差分 | AIによる変更を適用前に確認可能にする |
| 可逆性 | 可能な範囲でUndo、版管理、ロールバックを備える |
| 権限の最小化 | 読み取り、編集、実行、送信を別の行為として管理する |
| 割り込み制御 | 不必要に作業の流れを中断しない |
| 失敗時の回復 | 失敗理由と代替経路を示す |
| モデル依存の隔離 | UIと推論機能の結合を過剰に強めない |

### 15.3 AIコーディング時代のデザイン設計

「かっこいいMaterial風UIを実装」という指示だけでは、状態、アクセシビリティ、優先順位、失敗時挙動が未定義のままになりやすい。

AIへの実装入力としては、少なくとも次を指定する。

- 対象ユーザーと主要タスク。
- 情報アーキテクチャと画面遷移。
- Design Tokensとコンポーネント契約。
- 状態一覧（Loading/Empty/Error/Success等）。
- 操作の権限・キャンセル・復旧条件。
- Web/デスクトップ別の入力・アクセシビリティ要件。
- レスポンシブ/ウィンドウリサイズ要件。
- 実装後の受け入れテスト。

**AIは設計案を量産できるが、ユーザー要求の妥当性と品質評価を自動的に保証しない。**

## 16. UI/UXの評価と改善

### 16.1 定量指標

| 指標 | 定義・例 | 主な目的 |
|---|---|---|
| Task Success Rate | 完了タスク数 / 試行タスク数 | 有効性 |
| Time on Task | タスク完了までの時間 | 効率 |
| Error Rate | 誤操作の件数・率 | 安全性、理解度 |
| Recovery Time | 誤りから復旧するまでの時間 | 回復可能性 |
| First-time Success | 初回実行で成功できた割合 | 学習容易性 |
| SUS / UMUX-Lite等 | 標準化・簡易化された主観指標 | 主観的ユーザビリティ |
| Retention / Adoption | 継続利用、機能採用 | 長期利用状況（目的に応じて） |
| LCP / INP / CLS | Webの表示・応答・視覚安定性 | 性能UX |
| Accessibility findings | 達成基準・実利用時の問題 | アクセシビリティ |

**指標選択の注意**：クリック回数が少ない＝良いUXとは限らない。安全確認の1クリックが重大事故を防ぐ場合もある。速度と品質・安全性を同時に測る。

### 16.2 定性的評価

- 代表的な利用タスクを初見で実行してもらう。
- どこで迷い、何を予測し、何を誤解したかを観察する。
- 発話思考法、終了後インタビュー、失敗状況の再現を用いる。
- 専門家評価（Nielsenの10ヒューリスティクス）と実ユーザー観察を併用する。

### 16.3 Nielsenの10ヒューリスティクス

| # | 原則 | レビュー時の問い |
|---|---|---|
| 1 | システム状態の可視化 | 今何が起きているか分かるか |
| 2 | 現実世界との一致 | 語彙・概念は利用者に馴染むか |
| 3 | ユーザーの制御と自由 | 戻る・中断・取り消しができるか |
| 4 | 一貫性と標準 | 同じ意味の操作が同じ挙動か |
| 5 | エラー防止 | 誤操作を事前に防げるか |
| 6 | 記憶より認識 | 覚えていなくても分かるか |
| 7 | 柔軟性と効率 | 初心者と熟練者の両方を支援するか |
| 8 | 美しく最小限のデザイン | 不必要な情報に埋もれていないか |
| 9 | エラー認識と回復支援 | 失敗理由と復帰方法が明瞭か |
| 10 | ヘルプと文書化 | 必要な説明に到達できるか |

### 16.4 評価をリリース品質に結びつける

以下のような品質ゲートを設けることを推奨する。

1. **Blocker**：タスクが完了できない、重大なデータ損失リスク、主要操作が支援技術で利用できない。
2. **High**：頻出操作で迷う、実質的な操作不能、重大な誤解を生む。
3. **Medium**：非効率、視認性・一貫性の問題、復旧性の不足。
4. **Low**：軽微な整列・余白・微細な表示問題。

重大度は「影響 × 発生可能性 × タスク重要度」等で判断する。単なる美観上の差異と安全上の欠陥を同じスコアで相殺しない。

## 17. 設計から実装への落とし込み

### 17.1 推奨する開発手順

1. **UX要求定義**：対象ユーザー、利用状況、最重要タスク、失敗時の影響を定義。
2. **IA / タスクフロー設計**：オブジェクト、機能、遷移、用語を整理。
3. **状態・例外設計**：非同期処理、失敗、取消、復旧を明文化。
4. **ワイヤーフレーム**：まず情報の優先順位とレイアウトを確認。
5. **デザインシステム**：Tokens、部品、密度、フォーカス、テーマを定義。
6. **プロトタイプ**：操作可能な形でタスクを検証。
7. **実装**：Webまたはネイティブの標準機能を優先使用。
8. **テスト**：タスク、アクセシビリティ、サイズ、言語、性能を検証。
9. **改善**：問題を元の設計判断へフィードバック。

### 17.2 仕様ファイル例

```text
docs/ui-ux/
  principles.md        # 設計原則・対象ユーザー・品質目標
  information-arch.md   # IA、画面構造、ナビゲーション
  interaction.md        # タスクフロー、状態、失敗時挙動
  accessibility.md      # キーボード、フォーカス、支援技術
  responsive.md         # Webの幅/入力方式、Desktopのリサイズ
  design-tokens.json    # 必要に応じてDTCG形式等で管理
  components.md         # 部品契約、状態、配置ルール
  ux-review.md          # 評価・既知の問題・改善計画
```

### 17.3 コンポーネントをレビューするときのテンプレート

```markdown
## Component: [名称]

- 目的：
- 想定タスク：
- 表示する情報：
- 操作と結果：
- 状態：Empty / Idle / Loading / Success / Error / Disabled
- キーボード操作：
- マウス/タッチ操作：
- アクセシブルな名前・役割・状態：
- レスポンシブ/リサイズ時の挙動：
- i18n/RTL：
- Light/Dark/High Contrast：
- 例外と復旧：
- 受け入れテスト：
```

### 17.4 最低限のテストマトリクス

| 軸 | 代表ケース |
|---|---|
| 操作 | Mouse、Keyboard、必要ならTouch |
| 状態 | Empty / Loading / Success / Failure / Offline |
| 表示 | 狭い/標準/広い、ズーム、HiDPI |
| テーマ | Light、Dark、High Contrast |
| 言語 | 日本語、英語、長い文言、必要に応じてRTL |
| アクセシビリティ | Focus、Screen Reader、Reduced Motion |
| データ | 空、1件、大量、異常値、長いファイル名 |
| 環境 | 低速回線、切断、低性能端末、権限不足 |

## 18. 実務チェックリスト

### A. 目的と情報設計

- [ ] 主要タスクと成功条件を説明できる。
- [ ] 利用者の言葉で機能名・操作名が表現されている。
- [ ] 主要機能への到達経路が明瞭。
- [ ] 情報の分類と画面階層が一貫している。
- [ ] 初心者の導線と上級者の効率的操作が両立する。

### B. インタラクションと安全

- [ ] Loading / Empty / Error / Success 等の状態が定義されている。
- [ ] 実行中・実行結果・未保存の状態が判別できる。
- [ ] 破壊的操作の対象と影響が明示される。
- [ ] 取消・復旧・再試行の意味が明確。
- [ ] フォーム入力、エラー、結果通知が適切。

### C. 視覚とデザインシステム

- [ ] 色・文字・余白・角丸・状態のトークンが定義される。
- [ ] 視覚階層が明瞭で、強調しすぎていない。
- [ ] ラベルと入力欄などの関係が直感的。
- [ ] Light/DarkやDensityを意図どおり表示できる。
- [ ] アイコンだけに意味を依存していない。

### D. アクセシビリティと多様な環境

- [ ] キーボードのみで主要タスクを実行できる。
- [ ] フォーカスが見える・順序が自然。
- [ ] コントラスト・ターゲットサイズ等の関連基準を確認した。
- [ ] 支援技術で意味・状態が伝わる。
- [ ] 縮小/拡大/狭い画面で機能を失わない。
- [ ] Reduced MotionとHigh Contrastに配慮している。
- [ ] 日本語・英語など対象ロケールで破綻しない。

### E. Web固有

- [ ] Semantic HTMLを優先し、ARIAは適切に使用。
- [ ] フォーム、ダイアログ、画面遷移でフォーカスを管理。
- [ ] ブラウザー履歴、深いリンク、リロードに対応。
- [ ] レスポンシブレイアウトとContainer Queriesを適切に検討。
- [ ] LCP / INP / CLSを実ユーザーデータ等で評価。

### F. デスクトップ固有

- [ ] 最小ウィンドウサイズ・高DPI・複数モニターで検証。
- [ ] OSのメニュー、ファイルダイアログ、D&D慣習を尊重。
- [ ] ショートカットとコンテキストメニューが一貫。
- [ ] ウィンドウ終了とバックグラウンド継続の意味が明瞭。
- [ ] OS支援技術との互換性を実際に確認。

### G. 評価・継続改善

- [ ] 実ユーザーのタスク完了テストを実施。
- [ ] 重大なUX欠陥をリリース前に修正。
- [ ] 速度だけでなく成功率・回復性・安全性を測定。
- [ ] デザイン変更をトークン/コンポーネントへ反映。
- [ ] AI機能では提案の検証・編集・拒否・復旧を保証。

## 19. 参考資料・規格

以下は設計原則の裏付けまたは実装時の一次参照先。リンク先の改訂や適用範囲を確認すること。

## 結論

> **優れたUIは、人間の認知・行動・期待とシステムの状態・機能を適切に接続する。優れたUXは、その接続を通じてユーザーが安全に、効率よく、納得して目的を達成できることにある。**

現代の実務では、古典的な心理学法則だけでも、美しいデザインシステムだけでも不十分。**人間中心設計、情報アーキテクチャ、インタラクション、アクセシビリティ、性能、プライバシー、定量・定性評価**を横断的に統合することが重要である。Webとネイティブデスクトップは共通のHCI原則を共有しつつ、HTML/ARIA/ブラウザー特性とOS/ウィンドウ/ネイティブ支援技術の違いを尊重して設計する。
