## 機能要求

要求には変更後も維持する一意のIDを付けます。機能要求は `REQ-####`、非機能要求は `NFR-####` を使い、同じ要求仕様書内で番号を再利用しません。状態は要求単位で管理し、`未着手` / `実装中` / `実装済み` / `検証済み` / `廃止` を使います。`実装済み` は受け入れ条件の検証完了を意味しません。

| ID | 要求 | 優先度 | 状態 | 受け入れ条件 | 検証方法・証跡 | 設計・実装・課題 |
|---|---|---|---|---|---|---|
| REQ-0001 | | Must / Should / Could | 未着手 | | | ADR、パス、ISS-#### 等。なければ `—` |

## 非機能要求

性能、可用性、アクセシビリティ、セキュリティ、プライバシー、環境互換性、保守性など、対象に必要な品質特性を記載する。性能要求は想定ワークロード・データ規模・測定環境を、プライバシー要求は扱うデータ・収集・保存・ログ・共有・削除等の適用条件を必要な範囲で明記する。根拠がない数値目標は作らず、測定方法と未確認事項を示す。

| ID | 品質特性 | 要求・条件 | 状態 | 受け入れ条件・検証方法・証跡 | 設計・実装・課題 |
|---|---|---|---|---|---|
| NFR-0001 | | | 未着手 | | ADR、パス、ISS-#### 等。なければ `—` |

要求IDから受け入れ条件、関連設計・実装、検証結果へたどれるようにします。小規模な変更ではこの表の参照欄や関連資料へのリンクで十分です。全項目を重複転記するトレーサビリティ・マトリクスは、規模や規制上の必要がある場合だけ作成します。未対応・未検証の要求や、重要な要求で対応関係が追えない状態は明記し、必要な対応作業があれば既存の課題表へ登録します。

要求の追加・変更・廃止時は、IDと変更理由を保持し、影響を受ける受け入れ条件、ADR、実装、テスト、課題を確認します。廃止したIDは再利用せず、状態と理由を残します。検証証跡には対象コミット、実行した確認、結果、必要な環境を追跡可能な形で記録します。CI等に根拠がある場合はリンクを参照し、結果を重複して転記しません。
