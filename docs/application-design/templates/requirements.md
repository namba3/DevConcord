## 利用者の目的・機能設計（該当する場合）

GUIの有無を問わず、対象利用者・利用状況・主要タスクを必要な範囲で記録します。既存の調査資料や要求表が管理元の場合は、重複転記せず参照してください。UI/UXの経験則を一律適用せず、判断根拠・仮説・未確認事項を区別します。

| タスクID | 利用者・状況 | 目的 / タスク・成功結果 | 設計書出典・節 | 設計根拠（理論・観察・制約） | 導出する機能・状態 | 関連要求ID | 受け入れ条件・検証 |
|---|---|---|---|---|---|---|---|
| TASK-0001 | | | | | | REQ-0001 または `—` | |

タスクIDはこの仕様書内で一意にし、一つのタスクに複数の要求ID、また一つの要求に複数のタスクIDを記録できます。設計書出典は相対パスと節/ページ等を記し、要求を導かない調査上のタスクは要求IDを `—` とします。詳細な根拠やユーザー調査を別資料で管理する場合はタスクIDやリンクを参照し、重複転記しません。

主要な要求は、必要に応じて開始条件、主要/補助操作、発見経路、結果、失敗・中断・回復、可逆性・確認の要否までを記述します。Loading / Empty / Error / Partial Success等の状態、初心者/熟練者の操作経路、大量データの段階表示や一括処理、キーボード・マウス・タッチ・支援技術、多言語・密度・テーマ・OS慣習も、対象ユーザー・タスクに必要な場合に要求へ反映します。キャンセル、再試行、一括処理などがある場合、表示だけでなく処理状態、適用済み変更、重複実行、整合性への影響を定義します。製品に該当しないGUI固有項目は適用しません。

## 主要な技術依存と交換境界（必要な場合）

将来の変更が重要な依存だけを記録します。全依存を抽象化したり、複数実装を先に用意したりしません。交換可能性が不要な依存は、その前提や受容する影響を既存の設計資料で示せば十分です。

| 依存・技術選択 | 交換を考慮する理由・変更影響 | 保護する境界と意味的契約 | 交換時に許容する変更範囲 | 検証・ADR |
|---|---|---|---|---|
| | | | | |

UIフレームワークの場合は、必要に応じてドメイン/アプリケーション状態とUI表示状態、技術中立なユースケースAPI、UI固有イベント・型・ライフサイクルが留まる境界を記録します。ビュー実装まで無変更で交換できる保証は要求しません。バックエンドの場合は、エラー、トランザクション/整合性、並行性、性能、永続形式・マイグレーション、セキュリティ上の意味を必要に応じて契約に含めます。

## 機能要求

要求には変更後も維持する一意のIDを付けます。機能要求は `REQ-####`、非機能要求は `NFR-####` を使い、同じ要求仕様書内で番号を再利用しません。状態は要求単位で管理し、`未着手` / `実装中` / `実装済み` / `検証済み` / `廃止` を使います。`実装済み` は受け入れ条件の検証完了を意味しません。ユーザー目標から導出した機能要求では、必要に応じて関連する `TASK-####` を記録し、タスク表から要求表・要求表からタスク表へ相互にたどれるようにします。複数タスク/要求の関係は各行のID参照で表現し、全プロジェクトに別のトレーサビリティ・マトリクスを強制しません。状態・フィードバック、アクセシビリティ、例外・回復条件も必要に応じて要求へ結び付けます。重要な技術依存の交換要求は、必要な境界・契約・許容変更範囲と検証方法を前項へ結び付けます。

| ID | 要求 | 優先度 | 状態 | 関連タスクID | 設計書出典・節 | 受け入れ条件 | 検証方法・証跡 | 設計・実装・課題 |
|---|---|---|---|---|---|---|---|---|
| REQ-0001 | | Must / Should / Could | 未着手 | TASK-0001 または `—` | | | | ADR、パス、ISS-#### 等。なければ `—` |

## 非機能要求

性能、堅牢性・信頼性、交換可能性、可用性、アクセシビリティ、セキュリティ、プライバシー、環境互換性、保守性など、対象に必要な品質特性を記載する。性能要求は想定ワークロード・データ規模・測定環境・許容範囲を、プライバシー要求は扱うデータ・収集・保存・ログ・共有・削除等の適用条件を必要な範囲で明記する。堅牢性要求では、重要な異常条件、状態・データ整合性、失敗時保証、再実行/復旧、診断、検証方法を必要な範囲で定める。交換可能性が重要な場合は、交換対象、境界、維持する意味的契約、移行時に許容する変更範囲を記録し、API形状だけを同一にすることを適合条件にしない。アクセシビリティ、入力方式、国際化、表示密度、テーマ、OS慣習等も対象製品と利用者に応じて要求化する。根拠がない数値目標は作らず、測定方法と未確認事項を示す。

セキュリティが関係する場合は、保護対象の資産、信頼境界とデータ/制御フロー、想定する脅威・影響を特定し、最小権限、安全な既定値、攻撃面、多層防御、データライフサイクル、依存関係、重要な不変条件を対象に応じて要求化する。各要求は受け入れ条件と検証方法に接続し、対象外の脅威・前提・残余リスクも必要な場合は記録する。すべての項目をすべての製品へ適用せず、詳細は[Security by Design](../../common/ai-assisted-development.md#97-security-by-design)を参照する。

| ID | 品質特性 | 要求・条件 | 状態 | 設計書出典・節 | 受け入れ条件・検証方法・証跡 | 設計・実装・課題 |
|---|---|---|---|---|---|---|---|
| NFR-0001 | | | 未着手 | | | ADR、パス、ISS-#### 等。なければ `—` |

要求IDから受け入れ条件、関連設計・実装、検証結果へたどれるようにします。小規模な変更ではこの表の参照欄や関連資料へのリンクで十分です。全項目を重複転記するトレーサビリティ・マトリクスは、規模や規制上の必要がある場合だけ作成します。未対応・未検証の要求や、重要な要求で対応関係が追えない状態は明記し、必要な対応作業があれば既存の課題表へ登録します。

要求の追加・変更・廃止時は、IDと変更理由を保持し、影響を受ける受け入れ条件、ADR、実装、テスト、課題を確認します。廃止したIDは再利用せず、状態と理由を残します。検証証跡には対象コミット、実行した確認、結果、必要な環境を追跡可能な形で記録します。CI等に根拠がある場合はリンクを参照し、結果を重複して転記しません。

## エラー・境界条件

正常系だけでなく、対象機能に関係する異常条件を選択します。すべての行を埋める必要はありません。失敗時の状態保証と、利用者・運用者への通知は別々に確認します。

| 状況 | 期待する動作 | 利用者への表示・記録 | 検証方法 |
|---|---|---|---|
| | | | |

例として、不正/破損入力、権限不足、リソース/容量不足、ネットワーク切断/タイムアウト、依存先失敗、部分成功、途中キャンセル、異常終了、並行競合、上限を超えるデータ規模、環境差から関連するものを選びます。回復不能なケースは、無理に回復可能と約束せず、保証範囲と残余リスクを明記します。
