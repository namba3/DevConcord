# UI/UX設計クイックチェック

設計レビューや実装前後の確認に使う短いチェックリストです。適用条件と具体例は[UI/UX設計ガイド](ui-ux-guide.md)の該当節を確認してください。該当しない項目は理由を添えて除外します。

## 目的と情報構造

- [ ] 対象ユーザー、利用状況、主要タスク、成功条件が明確で、UI/UXを実装後の見た目だけでなく機能設計の入力として扱った。
- [ ] 重要なUX上の判断が、設計根拠 → 必要な機能・振る舞い → 受け入れ条件 → 検証方法へつながっている。
- [ ] 要求仕様を使う場合、利用者タスクIDとREQ IDが相互参照され、一対多/多対一の関係も既存の要求表で追える（別マトリクスを無条件に追加しない）。
- [ ] 画面・機能名がユーザーの目的や既存の用語と合っている。
- [ ] 優先度の高いタスクが見つけやすく、情報の階層とナビゲーションが一貫。
- [ ] 初回利用と継続利用の双方で、必要な情報を認識できる。
- [ ] 主要操作と補助操作、発見経路、Undo/Redoや確認が必要な操作の基準を検討した。

## 操作と状態

- [ ] Idle、Loading、Empty、Success、Error、Disabledなど必要な状態を定義。
- [ ] 操作後に結果・進捗・失敗理由が分かり、再試行・取消・復旧の方法がある。
- [ ] キャンセル・再試行・一括処理は、処理モデル、部分成功、適用済み変更、重複実行時の整合性まで定義した。
- [ ] 破壊的操作を誤りにくくし、可能な場合は取り消しや復元を用意。
- [ ] 重複送信、通信失敗、保存失敗など現実の失敗条件を扱う。
- [ ] 失敗しても壊れない保証と、失敗したことを正しく伝える要件を区別した。

## アクセシビリティと入力

- [ ] キーボードだけで主要タスクを完了でき、フォーカス位置が見える。
- [ ] テキスト、コントラスト、拡大表示、色以外の状態表現を確認。
- [ ] 支援技術にラベル・役割・状態・エラーを伝える。
- [ ] タッチ・マウス・キーボードの操作対象と対象サイズを確認。
- [ ] Reduced MotionやOSの表示設定を考慮。

## 表示と環境

- [ ] 狭い幅、拡大率、長い文字列、複数言語で崩れない。
- [ ] 色、文字、余白、状態表示が画面間で一貫。
- [ ] Web・デスクトップそれぞれの標準操作やOS連携を確認。
- [ ] 待ち時間を測り、進捗表示や応答性の目標を定義。
- [ ] 性能要求が必要な場合、ワークロード・データ規模・対象環境・測定方法・許容範囲に根拠がある。
- [ ] 大量/低速環境の処理では、遅延読み込み・段階表示・仮想化・キャンセル等の機能/処理方式と失敗時挙動を併せて検討。

## UI設計ソースとモックアップ

- [ ] 曖昧さやリスクを減らせる場合、タスク・情報階層・状態を記録し、編集可能なモックアップを用意した。成果物の形式や分割を一律に要求していない。
- [ ] GUIに影響する実装差分から既存設計資産への影響を意味ベースで確認した（ViewModel、状態、非同期・エラー処理を含む）。影響なし・資産なしなら不要な更新や新規成果物を求めていない。
- [ ] 必要な設計資産は実装と同期した。保留した場合は未整合の内容・影響・理由・既存の対応先と、古い資産の誤用を防ぐ方法を示した。
- [ ] 設計と実装の不一致を要求・設計判断・変更意図・検証証拠で分類し、陳腐化したモックアップを現行仕様として無条件に使っていない。
- [ ] Web/ネイティブの描画環境差を考慮し、画素単位の一致を一律の合格条件にしていない。
- [ ] ソースの構造レビューと、ブラウザー等で描画した視覚レビューを区別した。必要なら実際の操作や対象環境も別に検証した。
- [ ] モックアップの仮データ・未実装動作を実製品の保証と混同せず、実装との整合は意図・状態・受け入れ条件を基準に確認した。
- [ ] 現行性の誤認リスクがある資産だけ状態を示し、`Current`は責任者の確認後に付けた。`Stale`・`Draft`は現行仕様として使わず、`Deprecated`は代替案内と参照整理を行った。
- [ ] [UI Design Drift評価fixture](../../tests/integration/fixtures/ui-design-drift/README.md)を使った場合、fixtureの動作確認とエージェントによる判断評価を別々に記録した。

## 安全性と評価

- [ ] データ損失や誤操作の可能性と、確認・復旧手段を評価。
- [ ] 個人情報、権限、AI生成内容の不確実性を利用者へ適切に示す。
- [ ] 代表的な利用者とタスクで、実際の操作を検証。
- [ ] 使用した検証方法、未確認の環境、残る問題を記録。
- [ ] Boundary / Property-Based / 状態機械 / Fault Injection / Recovery / Concurrency / Resource等から、影響に見合う検証を選んだ（すべてを一律必須にしていない）。
- [ ] Web・デスクトップ・CLI・ライブラリ等の製品形態に合わせ、GUI固有チェックを不適切に強制していない。
