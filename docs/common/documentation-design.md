# ソフトウェアプロジェクトのドキュメント設計ガイド

このガイドは、README、利用者向けガイド、開発者向け資料、API・運用文書などを、読者の目的に沿って設計・改善するための共通原則です。特定のディレクトリ構成、README形式、文書数、公開ツールを必須にしません。プロジェクトの規模、用途、技術、読者、既存規約に合わせて必要な部分を選びます。

## 1. 基本原則

- **Reader-Centred Documentation:** 文書は書き手の組織図ではなく、読者が達成したい目的・タスクから設計します。初めて使う人、日常利用者、導入担当者、開発者、運用者など、実際に必要な読者を特定します。
- **Information Architecture:** 情報を役割・利用場面・詳細度で分類し、名称、階層、導線、相互参照を一貫させます。
- **Progressive Disclosure:** 入口では目的、最初の一歩、重要な制約を伝え、詳細・例外・背景は必要な読者が先へ進める形にします。詳細を削ることではなく、適切な場所へ配置することです。
- **Single Source of Truth:** 同じ規範・設定・手順の正本を明確にします。他の文書では複製せず、要約と参照を使います。複数形式の生成物が必要なら、編集元と生成元を明示して同期を検証します。
- **Docs as Code:** 文書も差分レビュー、版管理、リンク・構造検査、必要なサンプル検証の対象にします。静的検査は事実性や説明の十分さを保証しないため、読者タスクに基づくレビューも行います。
- **Documentation by Design:** 要求・アーキテクチャ・機能を設計するときに、読者、必要な文書、情報の所有者、更新契機、検証方法を考慮します。
- **Traceability:** 要求・設計判断・実装・課題・検証から文書へ、また文書から根拠へ、変更リスクに応じて辿れるようにします。全プロジェクトに別の追跡台帳を増やしません。
- **Maintainability:** 文書の責務、正本、更新条件、変更影響を明らかにし、コード・設定・設計の変化に追従できる構造にします。

これらはDDD、SDD、Self-documenting Code、Performance by Design、Robustness by Design、Replaceability by Designと整合します。コードの名前・型・契約で表す内容と、資料で説明する目的・判断・制約を分けます。性能や障害時の利用・運用手順は、該当する要求と契約に結び付けます。交換価値のある技術依存の説明は必要な境界に絞ります。文書品質を新しい完成度軸にせず、既存のドキュメント整備、設計・アーキテクチャ、コード品質・保守性などへ反映します。

## 2. 文書の役割と情報設計

### 2.1 READMEは入口にする

READMEはプロジェクトの目的を示し、読者を次の行動へ導く入口です。対象に応じて、次のうち根拠があり重要な項目を選びます。

- 何を解決し、誰のためのものか
- 実装済みの主な機能と対象環境
- インストール・利用開始・最小の使用例
- 開発、ビルド、テストの確認済み手順
- 詳細資料への目的別リンク
- サポート、ライセンス、貢献方法（確定している場合）

小さなCLIやライブラリなら、必要事項を一つのREADMEにまとめても構いません。大規模な製品ではREADMEから利用者向けガイド、API、開発者向け資料、運用・リリース資料へ案内します。未実装機能を提供済みと書かず、未検証コマンドを動作確認済みと表示せず、設計資料にない事実・ライセンスを補いません。

### 2.2 利用タスクで文書の種類を分ける

以下は役割の例であり、別々のファイルを作る義務ではありません。

| 文書の役割 | 読者の主な問い | 主に置く情報 |
|---|---|---|
| README / overview | これは何か、どこから始めるか | 目的、状態、前提、最初の手順、主要導線 |
| Getting started / tutorial | 最初にどう動かすか | 順番に実行できる導入・基本タスク |
| How-to / runbook | 特定の作業・障害にどう対処するか | 前提、手順、結果、失敗・回復 |
| Reference | 正確な仕様・選択肢は何か | CLI/API、設定、スキーマ、互換性 |
| Explanation / design | なぜこの構成・判断なのか | 背景、概念、トレードオフ、ADR |
| Requirements / verification | 何を満たし、どう確認するか | 要求、受け入れ条件、検証証跡 |

一つの文書が複数の役割を持つ場合は、読者が迷わない見出しと導線を設けます。手順に背景説明を詰め込みすぎたり、リファレンスを導入チュートリアルの代用にしたりしません。操作方法とその理由は、互いに必要な箇所をリンクします。

### 2.3 構造・見出し・分類

- 読者が探す語を使い、文書名・見出し・ディレクトリ名の粒度と用語を揃えます。内部チームの組織名より、利用目的や情報の役割を優先します。
- 見出しは節の内容を予測できる表現にし、階層を飛ばさず、段落を一つの主題に絞ります。巨大な節はタスクや概念ごとに分けます。
- ディレクトリは既存の構成・公開システム・所有境界に合わせます。分割は独立した読者タスク、更新責務、レビュー容易性などの価値がある場合に行い、文書数や短さ自体を目標にしません。
- 目次は長文で有用な場合に設け、見出しと同期させます。索引・サイドバー・ナビゲーション設定がある場合はREADMEだけでなくそちらも更新します。
- 表は比較や一覧に、図は関係・流れに、コード例は操作可能な例に使います。文章で説明した方が分かりやすい内容を表や図へ押し込みません。

## 3. 可読性とナビゲーション

- 最初に文書の目的、対象読者、重要な結論・制約を示し、読者が読む必要性を判断できるようにします。
- 長い段落は論点ごとに分け、重複説明は正本へ集約します。簡潔化のために前提、契約、例外条件、必要な詳細を失わないでください。
- 用語を一貫させ、略語・専門用語は対象読者が必要とする範囲で説明します。「適切に」「必要なら」などの曖昧な語は、判断基準や例を補います。
- **必須要件**、**推奨**、**例**、**未確認・将来の制約**を読み分けられるよう表現します。例を規範と誤認させません。
- 初めての読者向け入口と、既存利用者が目的別に飛べる導線を両立させます。長い文書には目次、重要節への直接リンク、関連資料へのリンクを必要に応じて加えます。
- 内部参照は可能な限り相対リンクを使い、対象のMarkdown処理系が生成するアンカー規則に合わせます。公開文書ではURL、アンカー、ナビゲーションの変更影響を確認し、参照元を見つけられない場合は互換性を仮定しません。
- コード例には言語・実行条件・期待結果を示します。実行可能な例は検証し、説明用・疑似コードならその旨を明記します。図・表も代替テキストや見出しで文脈を提供します。

## 4. 正本と保守

各主要文書について、必要な範囲で「何を説明するか」「誰が・何を変更したとき更新するか」「関連する正本・検証方法」を定めます。すべての文書に管理メタデータ表を追加する必要はありません。

変更時は影響を受ける文書だけを調べます。例として、新機能は利用案内・仕様、公開APIはAPI参照・例・移行情報、アーキテクチャ変更は設計資料・ADR、CLIや設定の変更はコマンド・設定参照、ビルド・リリース変更は開発・運用手順に影響します。重大な不具合修正は、必要な場合に既知制限や回復手順を更新します。コードや設定と資料の不一致では、実装・承認済み要求・設計判断を照合し、どちらが正か推測しません。

次の場合に文書の分割・統合を検討します。

- 読者タスクや対象読者が異なり、同じ文書が相反する用途を担っている。
- 変更周期・所有者・正本が異なり、独立してレビューする価値がある。
- 重複更新、矛盾、検索困難、巨大な差分が繰り返し発生している。
- 分割後も入口・目次・リンクで全体の理解と発見性を保てる。

一度だけの長さやファイルサイズで機械的に分割しません。見出し名・ファイル名・公開URL変更時は、明示アンカー、外部リンク、検索索引、サイドバー、例を含む参照先への影響を確認します。移動が必要ならリンク転送や互換アンカー等、既存公開契約に合う方法を選びます。

## 5. 開発・AIエージェントとの連携

- 文書をコード・テスト・設定の変更と同じ変更影響確認へ含めます。更新不要と判断した場合も、重要な矛盾を見落としていないか確認します。
- 変更内容から影響する資料だけを絞ります。新機能は利用ガイド・仕様、公開APIはAPI資料・コード例・移行案内、CLIはREADME・コマンドリファレンス、設定は設定リファレンス・配備手順、アーキテクチャは設計資料・ADR、CIや開発環境はセットアップ手順、リリース方式はリリース・運用資料を確認します。該当しない資料を一律に書き換えません。
- コード・設定と文書が食い違う場合、どちらを正とするかを推測しません。検証可能な実装・要求・設計判断・変更意図を照合し、未確定なら確認事項として明示します。
- `AGENTS.md` は日常作業で毎回必要となる短い運用指示と、文書変更時の影響確認を記載します。詳細な文書理論を複製せず、導入先にガイドを採用した場合はその場所へリンクします。
- `REVIEWS.md` はレビュー時に限るプロジェクト固有の確認観点を置きます。読者・目的、正確性、情報構造、重複・矛盾、導線、実装との整合、リンク、必要な追跡性、将来の保守性を、変更リスクに応じて確認します。
- Skillsは必要なタスクの実行手順、共通ガイドは原則・詳細根拠、READMEやリファレンスはプロジェクトの実情報を担います。各役割を混同せず、Skill本文を冗長なガイドの複製にしません。
- 要求ID、課題ID、ADR、API識別子、明示アンカー等は既存の安定したIDを使い、必要な文書間から参照します。新しいID台帳やトレーサビリティ・マトリクスは規模・規制上必要な場合に限ります。
- 長い資料は、エージェントがタスクに必要な節を選べる目次・短い説明・安定したリンクを持たせます。関連する詳細だけを読み込み、重要な契約や例外はコンテキスト節約のために省略しません。

## 6. 検証と導入

既存のMarkdownlint、ドキュメントビルド、リンクチェッカー、APIドキュメント生成、スペル検査、サンプルテストを優先します。新しいツールは、検出するリスクと保守コストを比較して導入します。適切な検証はプロジェクトの公開基盤とファイル形式に依存します。

必要に応じて、以下から対象を選びます。

- Markdown構文、見出し階層、重複見出し・アンカー
- 相対リンク、画像、添付ファイル、明示アンカー
- READMEからの主要導線、目次・ナビゲーション、重要資料の有無
- サイトのビルド、URL・sidebar/navの整合、API参照の生成
- 実行可能なコード例、インストール・設定・開発手順
- 要求・設計判断・実装・課題・検証の必要な参照

DevConcordの検証器はDevConcordの文書体系向けです。外部プロジェクトへそのまま適用できると仮定せず、既存規則・ビルド・ツールを調査してください。構成が異なるだけで不合格にせず、固定的な文字数・行数や単一スコアに依存しません。機械検査で証明できない文章の正確さ、読者タスクへの適合、説明の十分性は、人が根拠と実際の利用場面に照らしてレビューします。

新規プロジェクトでは読者・利用目的・必要な文書と公開先を初期設計で決めます。既存プロジェクトでは現在の構造、リンク、公開URL、ビルド、固有規約を調査し、破壊的な再編を避けて合意された範囲だけ適用します。未対応作業は既存の課題表へ記録し、独立した文書品質台帳を作りません。
