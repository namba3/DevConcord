# AIコーディング時代のソフトウェア設計・開発手法ガイド

> DDD・TDD・SDDを中心に、UI/UXを起点とする機能設計、Performance / Robustness / Replaceability / Security by Design、契約・検証、レビュー、課題表による管理を統合した実践資料

- **版**: 1.4
- **作成日**: 2026-10-11
- **更新日**: 2026-10-18
- **対象**: AIエージェントを利用するソフトウェア開発全般（デスクトップアプリ、Webアプリ、CLI、ライブラリ等）
- **目的**: AIによるコード生成の高速化と、設計の整合性・機能の正しさ・変更の安全性を両立する
- **位置付け**: プロジェクト共通の開発指針。個別仕様、既存の設計判断、セキュリティ要件を上書きするものではない

## 1. 基本思想

AIコーディングにおける中心課題は、単にコードを高速に生成することではない。**何を正しいソフトウェアとみなすかを定義し、その条件を保ったまま継続的に変更できること**が重要である。

開発上の責務を、次のように整理する。

| 対象 | 中心となる問い | 主な手法・成果物 |
|---|---|---|
| 利用者と機能 | 誰がどの状況で何を達成するか | Human-Centred Design、User Goals / Jobs to Be Done、タスクフロー、UI/UX設計 |
| ドメイン | 何を扱い、各概念は何を意味するか | DDD、ユビキタス言語、コンテキストマップ |
| 仕様 | 何を実現し、何を実現しないか | SDD、要求仕様、受け入れ条件 |
| 契約 | 何を前提とし、何を保証するか | DbC、不変条件、インターフェース契約 |
| 振る舞い | 何を観測できれば正しいか | BDD、ATDD、TDD |
| 構造 | 変更・責務・依存関係をどう分離するか | Hexagonal/Clean Architecture、ADR |
| 実装 | 具体的にどう実現するか | 詳細設計、AIコーディング、リファクタリング |
| 検証 | 要求・設計・安全性を満たしているか | CI、契約・性質・状態遷移・回帰テスト、レビュー |
| 維持・進化 | 変更を重ねても設計が壊れないか | Evolutionary Architecture、Fitness Functions、課題表 |

開発では、次の6つを横断的な基本設計原則として扱う。これらは設計品質のすべてを説明するものではなく、正確性、アクセシビリティ、プライバシー等の要求を置き換えない。

| 基本設計原則 | 重視する設計品質 |
|---|---|
| DDD | ドメイン概念と責務の正しさ |
| Self-documenting Code | 設計の理解可能性 |
| Performance by Design | 処理構造の効率性 |
| Robustness by Design | 異常条件への耐性、状態・データ整合性、回復可能性 |
| Replaceability by Design | 主要な技術依存の適切な局所化と、必要な境界での変更容易性 |
| Security by Design | 脅威に応じた予防・検知・影響抑制と、検証可能なセキュリティ契約 |

UI/UXは上記原則と同じ分類に置く技術的品質軸ではなく、人間中心に利用者の要求・機能・操作・状態を方向付ける設計入力である。SDDで要求から検証までをつなぎ、DbCで契約を明確にし、TDDやその他の独立した検証で正確性・性能・堅牢性・交換境界・セキュリティの契約を確かめる。品質間のトレードオフは対象ユーザー、失敗時の影響、ワークロード、脅威、将来変更の可能性とコスト、測定・検証根拠を使って判断する。

### 1.1 推奨原則

1. **仕様を先に明確にする**。ただし仕様自体もレビューし、学習に応じて更新する。
2. **概念・責務・依存関係の境界を明示する**。AIの作業範囲もその境界に合わせる。
3. **要求を検証可能な条件に変換する**。自然言語の説明だけを完成判定としない。
4. **テストと実装の同時誤解を警戒する**。テスト成功は仕様の正しさの証明ではない。
5. **自動検証で保証できる部分と、人間の判断が必要な部分を区別する**。
6. **設計判断を残す**。結論だけでなく、理由・代替案・制約を記録する。
7. **ドキュメントは軽量に保つ**。文書や抽象化を増やすこと自体を目的にしない。
8. **変更を小さく統合する**。レビュー、CI、ロールバック可能性を重視する。
9. **コードで表せる意味・責務・契約・振る舞いは、コードの構造に表現する**。コードだけでは伝わらない要求、設計理由、制約、トレードオフ、運用知識、検証根拠は、それぞれ適切な資料で補う。
10. **品質を設計時から作り込む**。必要に応じて、ユーザーのタスク・性能上重要な経路・異常時の状態と保証を要求・機能・アーキテクチャへ反映する。

Self-documenting Code（自己説明的なコード）は、命名やコメント量だけの規則でも、独立した開発方法論でもない。ドメインの意味、責務、構造、契約、振る舞いを、開発者が実装から理解しやすくする横断的な品質原則である。コードは現在の実装を示すが、要求への適合を保証しない。要求仕様、受け入れ条件、実装から独立した検証を引き続き維持する。自己説明性を評価するときは、[Self-documenting Score（SDS）](../work-management/issue-tracking.md#35-self-documenting-scoresds)を独立した補助指標として参照する。

### 1.2 用語と注意

- **SDD (Spec-Driven Development)** は実務・ツールによって運用が異なる比較的新しい総称として扱う。本資料では「バージョン管理された仕様を中心に計画・作業・実装・検証を接続する開発スタイル」と定義する。
- **DDD (Domain-Driven Design)** はドメイン理解とモデル化を重視する設計アプローチであり、特定のフォルダー構成を強制しない。
- **TDD (Test-Driven Development)** は単なる「後付けテストの自動生成」ではなく、テストを先に用いた短い設計・実装サイクルである。
- 記載する手法の重要度は**一般的な採用判断の目安**であり、実測された普遍的ランキングではない。

## 2. 手法の全体マップと採用優先度

| 手法 | 主な役割 | AI開発での価値 | 推奨度 | 適用上の注意 |
|---|---|---|---|---|
| **SDD** | 仕様中心の開発統制 | 指示・実装・検証を同一の要求に結び付ける | S | 仕様の陳腐化・肥大化を防ぐ |
| **DDD（特に戦略的DDD）** | 概念・責務・境界 | 用語と設計意図の一貫性を保つ | S | 小規模ツールに全パターンを強制しない |
| **DbC / Design by Contract** | 事前条件・事後条件・不変条件 | AIが守る制約を明示する | S | 障害時保証も明確にする |
| **BDD / ATDD** | 具体的振る舞い・受け入れ条件 | 要求の誤解を減らし完成判定を容易にする | S | シナリオの網羅性を別途確認 |
| **ADR** | 設計判断と背景の記録 | AIのセッションをまたいで判断根拠を残す | S | 小さな判断まで記録しない |
| **TDD** | テスト主導の設計・実装 | 小さな変更と回帰検出を支える | A | テストを実装に合わせて書き換えない |
| **CI** | 継続的な自動検証・統合 | 生成コードの基礎的品質ゲート | A | テストが通るだけで安全とは限らない |
| **Hexagonal / Clean Architecture** | ドメインと外部依存の分離 | OS・DB・UI等の差分を管理しやすい | A | 不要なインターフェース増殖を避ける |
| **Evolutionary Architecture** | 設計の継続的な保全 | 長期のAI生成による設計劣化を検出 | A | Fitness Functionsは測定可能なものから |
| **Property-Based Testing** | 性質の大量入力検証 | 境界条件・想定外入力を探索 | A | 正しい性質の定義が前提 |
| **Contract Testing** | 境界間の整合性 | 複数モジュール・エージェントの変更を接続 | A | 契約のバージョン管理が必要 |
| **Mutation Testing** | テストの欠陥検出能力を評価 | 見かけ上の高カバレッジを補完 | B | 計算コストに応じて対象を絞る |
| **Model-Based Testing** | 状態遷移・操作列の検証 | 複雑な状態機械に有効 | B | 参照モデル自体をレビュー |
| **Threat Modeling** | 想定される攻撃・誤用の整理 | 高権限処理や外部入力の安全性を設計段階で検討 | A（高リスク領域はS） | テストとは別に必要 |
| **Formal Methods** | 形式的仕様・検証 | 特定の重要性質を厳密に扱える | 条件付きS | コストと適用範囲に注意 |
| **CQRS / Event Sourcing** | 読み書き責務・履歴の設計 | 監査性や複雑な状態管理で価値 | 用途依存 | 単純なアプリへの安易な導入は避ける |

**S = 特に重視 / A = 積極採用 / B = 選択的採用**。優先度は「常に全部入れる」という意味ではない。

手法は役割を区別して組み合わせる。UI/UXガイドは人間中心の要求・機能設計、SDDは要求から検証への追跡、DbCは契約、DDDはドメイン表現、Self-documenting Codeは理解可能性、Performance / Robustness / Replaceability / Security by Designは横断的な設計品質、TDD・テストは振る舞いの検証を担う。ツールや成果物の導入自体を目的にせず、リスクと規模に応じて必要な部分を使う。優先度は「常に全部入れる」という意味ではない。

### 2.1 Self-documenting Codeへの貢献

自己説明性は以下の設計手法が共通して支える品質原則である。特定の手法や形式を使うこと自体を評価せず、プロジェクトの複雑さに合った形で意味が理解できるかを見る。

| 手法・概念 | 自己説明性への貢献 |
|---|---|
| DDD | ドメイン概念、責務、境界、ユビキタス言語をコードに反映する |
| Clean Code | 命名、凝集度、責務分割、読みやすさを整える |
| DbC | 事前条件、事後条件、不変条件、失敗時の保証を表現する |
| 型駆動設計 | 意味の異なる値や許される状態を型・APIで示す |
| BDD / ATDD / TDD | 期待する振る舞いと受け入れ条件をテストで確認できる形にする |
| アーキテクチャ設計 | モジュール境界、依存方向、責務分離を構造で示す |
| ADR | コードだけから推測できない理由、代替案、トレードオフを補う |

#### 実装で意味を表現する

- **用語と命名:** ドメインと既存資料の語彙を確認し、型・関数・変数・モジュールの名前から役割が推測できるようにする。曖昧な略称や汎用的すぎる名前を避け、同じ概念には一貫した用語を使う。名前の短さ・長さより正確さと文脈での理解しやすさを優先する。
- **ドメインモデル:** 必要な複雑さがある領域では、ユビキタス言語（Ubiquitous Language）、Entity / Value Object、Aggregateと不変条件、Bounded Contextを適切に用い、ドメインモデルと技術的実装詳細の境界を明確にする。小規模なツールへDDDのパターンや文書を形式的に強制しない。
- **型とAPI:** 意味の異なる値は可能なら異なる型で表し、不正状態を型で防げるか検討する。APIは失敗可能性や制約を明確にする。実行時にしか分からない条件は検証・エラー処理で扱い、型や抽象化を増やすこと自体を目的にしない。Rustでは必要に応じて newtype、enum、`Result`、型状態を選択できる。
- **責務と構造:** 関数・型・モジュールの責務、依存方向、外部I/O・副作用・状態変更を理解できるようにする。関心事を適切に分ける一方、不要な抽象化、間接参照、ラッパーを増やして読み手の追跡を難しくしない。
- **契約と振る舞い:** 事前条件、事後条件、不変条件、境界条件、状態遷移、失敗時の保証をコード・型・API・検証に反映する。テスト名とケースは期待する振る舞いを表し、実装詳細をそのまま複製しない。要求とテストの期待値は実装から独立して確認する。

#### コメント・資料との役割分担

コードで明確に表せる内容をコメントで言い換えない。コメントは非自明な設計意図、制約、性能上の理由、回避策など、コードだけでは読み取れない情報を補う。公開APIの利用契約はAPIドキュメント、判断理由・代替案はADR、要求と非機能制約は要求仕様、検証根拠はテスト・CI・レビュー記録など、それぞれの管理元に置く。コメントや文書が少ないことを自己説明性の高さとみなさず、Self-documenting Codeをドキュメント不要論にしない。

### 2.2 Doc CommentsとAnnotation Comments

Doc Commentsは、ソースコードに結び付いたAPIの正式な説明として扱う。公開モジュール、型、インターフェース、関数、設定項目、拡張点では、利用者が実装を読まなくても安全に使えるために必要な情報を記述する。複雑な内部API、ドメインモデル、不変条件、状態遷移、性能制約、安全性上の契約にも、誤用や保守上のリスクに応じて記述する。名前・型だけで意味が明らかな局所ヘルパーや単純なprivate処理には一律で要求しない。

Doc Commentsは、処理を言い換えるのではなく、利用者に必要な意味・契約・保証を説明する。必要な項目だけを選び、目的、振る舞い、事前条件・事後条件・不変条件、エラー、状態変更やI/Oなどの副作用、性能・リソース制約、安全上の注意、使用例、関連APIを記載する。実装が保証していない内容や根拠のない性能値を書かず、実装・要求・テストと一致させる。

| 言語 | 標準的なドキュメント方式 |
|---|---|
| Rust | rustdoc（`///`、`//!`） |
| Python | Docstrings |
| TypeScript / JavaScript | JSDoc / TSDoc |
| C# | XML Documentation Comments |
| Java | Javadoc |
| Go | Go Doc |
| C / C++ | Doxygen等 |

言語固有の記法は各言語の慣習に従う。Rustでは必要に応じて `# Errors` に失敗条件、`# Panics` にpanic条件、unsafe APIの `# Safety` に呼び出し側が満たす安全条件を記す。実行可能な使用例は `# Examples` に置き、可能なら `cargo test --doc` で検証する。例えば次は、解析失敗の契約とdoctest可能な例を示す形式である。

```rust
/// Parses a string as a 16-bit port number.
///
/// # Errors
///
/// Returns a parse error when `value` is not a valid `u16`.
///
/// # Examples
///
/// ```
/// use my_crate::parse_port;
///
/// assert_eq!(parse_port("8080").unwrap(), 8080);
/// ```
pub fn parse_port(value: &str) -> Result<u16, std::num::ParseIntError> {
    value.parse()
}
```

`my_crate` は説明用のcrate名であり、実際の公開パスへ置き換える。この例を採用先の公開APIに付ければ、rustdocはドキュメントコメント内の例をテスト用crateとしてコンパイル・実行し、`use my_crate::parse_port` はそのcrateの公開APIを参照する。`cargo test --doc -p my_crate` は指定パッケージのdoctestを実行する。workspaceでは対象パッケージを明示し、機能フラグ等がある場合は対象の設定も合わせる。

このリポジトリ自体にはRust crateがないため、ここに掲載したコード片は実行していない。対象プロジェクトでは、実在する公開パスを使う例をそのcrateのドキュメントへ置き、同じcrateのdoctestとして実行する。

Rustdocの隠し行（行頭の `#`）はセットアップや補助コードを表示せずに例へ含めるためのもので、例のコンパイル・実行から除外する機能ではない。必要なimport等には使えるが、検証対象APIを隠しコードで同名定義・再実装してはいけない。`no_run`、`ignore`等を付けた例は通常の実行可能なdoctestとは異なるので、検証結果を報告するときに区別する。Doctestの成功が示すのはその例と実行環境での振る舞いであり、API契約全体の証明ではない。Doc Commentsと実装を一緒に更新し、契約の重要な条件は独立したテストでも確認する。

panicし得るAPIでは条件を `# Panics` に、unsafe APIでは必須の呼び出し条件を `# Safety` に記述する。

```rust
/// Returns the item at `index`.
///
/// # Panics
///
/// Panics if `index` is outside the slice.
pub fn required_item(items: &[u8], index: usize) -> u8 {
    items[index]
}

/// Reads one byte from a raw pointer.
///
/// # Safety
///
/// `ptr` must be valid for reads of one byte.
pub unsafe fn read_byte(ptr: *const u8) -> u8 {
    unsafe { *ptr }
}
```

上記の例は説明用である。この `read_byte` の契約では、呼び出し側は `ptr` がnullでなく、初期化済みの1バイトを読み取れる有効な領域を指し、その読み取り中に非同期な書き込みがないことを保証する必要がある。実際のAPIではポインター、寿命、並行性の保証を実装に合わせて記述する。

Annotation Commentsは、ソース上で未解決事項や重要な注意を示す短い目印とする。標準分類は `TODO`（今後の作業）、`FIXME`（既知の問題）、`HACK`（意図的な暫定対応）、`NOTE`（非自明な制約・補足）、`PERF`（性能上の懸念）、`SECURITY`（セキュリティ上の注意・未解決事項）、`DEPRECATED`（非推奨・移行案内）とする。記述例は `TODO(ISS-0042): 部分読み込み時の再試行処理を追加する。` のように、具体的な内容を簡潔に記す。API自体を非推奨にするときは、コメントだけでなくRustの `#[deprecated(since = "...", note = "...")]` や他言語の標準属性・アノテーション等を併用し、利用者への警告や生成ドキュメントに反映する。移行作業が残る場合は標準属性だけに課題追跡を任せず、必要なAnnotationと課題IDで管理する。

重要な未解決事項は既存の課題ID（通常 `ISS-NNNN`）へ結び付け、優先度・状態・完了条件・検証根拠は課題表を唯一の管理元とする。課題IDを推測せず、軽微な局所メモや恒久的な `NOTE` を無条件に課題化しない。課題の解決時には関連注釈を削除するか、現在も有効な制約を示す説明に更新する。Annotationだけで課題を管理したり、正式なAPI契約を代替したりしない。利用者に影響する既知の制約はDoc Commentsにも記し、対応作業は注釈と課題表で追跡する。

Doc Commentsの生成・リンク・使用例や公開API不足の検証は、対象言語の標準ツールと公開範囲に応じて導入する。Annotationの課題ID、解決済み参照、秘密情報などを機械検査する場合は、可能な限り言語対応の構文解析や既存ツールを使い、コード・文字列リテラル・文書例を区別する。単純な文字列検索を意味解析として扱わず、過剰な独自パーサーを作らない。`scripts/validate_docs.py` はMarkdown資料の検証を目的とし、ソースコメントの検証を混在させない。自動検査がない場合も、変更に応じたレビューとテストで整合性を確かめる。

Doc Commentsは現在有効な契約と使用方法、Annotation Commentsは局所的な注意や未解決事項、通常コメントは非自明な実装理由やアルゴリズムの補足を扱う。設計判断の背景・代替案はADR、要求・非機能制約は要求仕様、実際に確認した振る舞いはテストと検証証跡で管理する。情報を複製せず、コード・コメント・資料・テストを一緒に更新する。

コメントにも[Privacy & Environment Hygiene（§11.3）](#113-privacy-environment-hygiene)を適用する。個人情報、秘密、実ユーザー名・ホスト名、不要な個人用絶対パス、機密ログを記載せず、例には架空の値やプレースホルダーを使う。OS仕様やテスト契約に必要な絶対パスは理由を確認して扱う。

Self-documenting Scoreでは、公開APIの契約、必要な制約・副作用・性能情報、実装・テストとの整合、注釈の適切な管理、古い記述の有無を品質根拠として見る。コメントの件数・比率を得点化せず、すべてのprivate関数への記述や `TODO` / `FIXME` の存在だけで加点・減点しない。既存のSDS評価軸と重みは変えない。

## 3. DDD：ドメイン駆動設計

### 3.1 目的とAIコーディングでの価値

DDDは、ソフトウェアが対象とする問題領域の概念・ルール・責務を整理し、設計とコードに反映するアプローチである。

AIは局所的には適切なコードを生成できても、長期開発では次のような問題が起こり得る。

- 同じ概念に異なる名前を与える、または異なる概念を同じ名前で扱う。
- 別の責務を一つの巨大な管理クラスやモジュールに集約する。
- 過去の設計判断を無視して、依存関係を追加する。
- 個別機能は動くが、ドメイン全体の整合性を損なう。

DDDによって概念と境界が明文化されていると、AIの作業範囲・責務・レビュー基準を共有しやすい。

### 3.2 戦略的DDDを優先する

| 概念 | 意味 | AIとの協業における効果 |
|---|---|---|
| **Ubiquitous Language（ユビキタス言語）** | 開発者とドメイン関係者が共有する用語 | 命名と仕様解釈の揺れを抑制 |
| **Bounded Context** | 特定のモデル・用語が有効な境界 | 変更範囲やインターフェースの明確化 |
| **Context Map** | コンテキスト間の関係・連携 | 依存関係・翻訳層・連携方式の明確化 |
| **Core Domain** | 競争力・目的に直結する重要領域 | 人間レビューと設計投資の優先順位付け |

**注意**: Bounded Contextは単なるフォルダーやクラスの分割と同義ではない。モデルや言語の意味が変わる境界であり、1コンテキストが複数モジュールにまたがることもある。

### 3.3 戦術的DDDは必要な箇所に採用

- **Entity**: 識別子によって同一性が保たれる対象。
- **Value Object**: 値とその制約で意味が決まる対象。
- **Aggregate**: 整合性を一貫して保つ単位とそのルート。
- **Domain Service**: 特定のEntityに自然に属さないドメイン操作。
- **Repository**: Aggregate等の永続化を抽象化する境界。
- **Domain Event**: ドメイン上意味のある出来事。

すべての機能をRepository・Service・Eventにする必要はない。状態と不変条件が単純なら、通常の関数・型・モジュールで十分な場合がある。

### 3.4 例：仮想ディスク管理アプリ

ドメイン語彙の例：

| 用語 | 意味 | 混同しやすい概念 |
|---|---|---|
| Disk Image | 仮想ディスクの格納形式・ファイル | Disk Device |
| Partition | ディスク上の領域定義 | Filesystem / Volume |
| Filesystem | 領域上のデータ構造 | Partition |
| Mount | 利用可能な名前空間へ接続する操作・状態 | Image Attach |
| Backend | OS固有操作の提供者 | Domain Model |

責務・モデルの境界として、イメージ管理、パーティション操作、マウント管理、ファイルシステム操作を分けて検討できる。ただし**これらを機械的に別Bounded Contextと断定せず**、用語・整合性・変更理由・業務上の境界を見て決める。

### 3.5 DDD成果物の最小セット

- ドメイン用語集（用語・定義・禁止する混同）
- 主要モデルと関係図
- コンテキスト境界と公開インターフェース
- 不変条件と失敗時の扱い
- 未決定事項と関連ADR

## 4. SDD：仕様駆動開発

### 4.1 基本方針

仕様を「一度書いて放置する説明文」ではなく、計画・実装・検証・課題管理の共通基準とする。

```text
要求・背景
   ↓
仕様 (何を、なぜ、どの条件で)
   ↓
設計 (境界、契約、方針、ADR)
   ↓
課題分解 (担当範囲、受け入れ条件)
   ↓
テスト設計 → 実装 → CI・レビュー
   ↓
差分・未達事項を課題表と仕様へ反映
```

### 4.2 良い仕様に必要な要素

- 目的、対象ユーザー、ユースケース
- スコープと非スコープ
- 機能要件・非機能要件
- 入力・出力・状態遷移
- 前提・制約・エラー時の保証
- 受け入れ条件（観測可能・検証可能）
- 依存する設計・ADR・既知の課題

### 4.3 仕様と実装の同期

- 実装を変更して仕様に不一致が出るなら、**仕様の変更承認と実装変更を対応付ける**。
- 既存仕様と矛盾する提案は、先に差分・影響・判断を記録する。
- 過剰な文書を避け、コードから確実に生成できる情報は重複管理しない。
- 仕様だけで判断できない曖昧さは、AIが推測で確定せず課題として明示する。

## 5. DbC：契約による設計

**Design by Contract**は、操作・コンポーネント・APIが守る条件を明確化する。

| 種類 | 定義 | 例 |
|---|---|---|
| Precondition | 操作開始時に満たされるべき条件 | 対象が変更可能な状態にある |
| Postcondition | 正常終了時の保証 | 結果が指定状態に一致する |
| Invariant | 許容される状態を通じて維持する条件 | 領域間に不正な重複がない |
| Failure Guarantee | 失敗時に何が保証されるか | エラーを返す、部分変更を報告する等 |

### 5.1 契約記述のテンプレート

```markdown
### Operation: <操作名>

- Preconditions:
  - ...
- Postconditions:
  - ...
- Invariants:
  - ...
- Failure guarantees:
  - ...
- Observable errors:
  - ...
- Verification:
  - Unit / Property / Integration / Manual ...
```

契約の保証範囲は現実の実装に合わせる。例えばOSの低レベル操作や停電を含む障害について、検証していない原子性を安易に保証しない。

### 5.2 DDD・DbC・テストの接続

**ドメイン上のルール → 契約 → 受け入れ条件・性質 → テスト**の順で対応付ける。

例：

- ドメインルール：許容されない領域重複を作らない。
- 契約：パーティション変更後、全ての有効領域は制約を満たす。
- 性質テスト：ランダムな変更列について、成功後に領域重複が存在しない。

## 6. BDD・ATDD：振る舞いと受け入れの設計

- **BDD (Behavior-Driven Development)**: 具体例・シナリオを使って関係者の期待する振る舞いを共有する。
- **ATDD (Acceptance Test-Driven Development)**: 機能完成の前に受け入れ基準・受け入れテストを定める。

両者は重なりがあるが、BDDは共通理解と振る舞いの言語化、ATDDは受け入れの判定条件に特に焦点を当てる。

```gherkin
Feature: 仮想ディスクのサイズ変更

  Scenario: マウント中のディスクを変更しようとした場合
    Given ディスクがマウント中である
    When ユーザーがサイズ変更を要求する
    Then 操作は拒否される
    And ディスクイメージは変更されない
```

これは**仮の製品ポリシーに基づく例**であり、全OS・全形式の制約を主張するものではない。

### 6.1 運用指針

- シナリオは実装内部ではなく**利用者が観測する振る舞い**で書く。
- 正常系・境界値・失敗・権限・競合・キャンセルを必要に応じて含める。
- すべてのシナリオをUI E2Eにする必要はない。より安定した層で検証する。
- 課題表の受け入れ条件は、シナリオまたは検証項目にリンクする。

## 7. TDD：テスト駆動開発

### 7.1 Red → Green → Refactor

1. **Red**: 欲しい振る舞いをテストに書き、未達であることを確認する。
2. **Green**: テストを通す最小限の実装を行う。
3. **Refactor**: 振る舞いを維持しながら構造を改善する。

テストコードを書く行為そのものが目的ではなく、短いサイクルで設計へのフィードバックを得ることが重要。

### 7.2 Rustでの簡単な例

以下では「マウント中は禁止」「要求サイズは安全下限以上」という**例示的なルール**を検証する。

先にテストを定める：

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn mounted_image_cannot_be_resized() {
        assert_eq!(
            validate_resize(true, 4096, 2048),
            Err(ResizeError::Mounted)
        );
    }

    #[test]
    fn image_cannot_shrink_below_minimum() {
        assert_eq!(
            validate_resize(false, 1024, 2048),
            Err(ResizeError::TooSmall)
        );
    }

    #[test]
    fn safe_resize_is_permitted() {
        assert_eq!(validate_resize(false, 2048, 2048), Ok(()));
    }
}
```

次に最小限の実装を行う：

```rust
#[derive(Debug, PartialEq, Eq)]
pub enum ResizeError {
    Mounted,
    TooSmall,
}

pub fn validate_resize(
    mounted: bool,
    requested_size: u64,
    minimum_safe_size: u64,
) -> Result<(), ResizeError> {
    if mounted {
        return Err(ResizeError::Mounted);
    }
    if requested_size < minimum_safe_size {
        return Err(ResizeError::TooSmall);
    }
    Ok(())
}
```

実務では境界値、整数オーバーフロー、サイズ単位、実行直前の状態再検証、OS操作の結果などを追加で検証する。**この関数は実際のディスク変更が安全であることを保証するものではない。**

### 7.3 AIコーディングでの重要な注意点

AIにテストと実装を同時に任せると、**誤った解釈に基づくテストと実装が同時に成立**し得る。全テスト成功でも仕様と異なる可能性がある。

推奨する検証分離：

1. 人間＋AIが仕様・不変条件・受け入れ条件を確定。
2. AIがテストケースを列挙し、人間が重要な期待値をレビュー。
3. AIがRed/Green/Refactorを実施。
4. テストを安易に削除・弱体化・書き換えない。
5. 別観点の検証（契約・性質・統合・レビュー）を実施。

**別エージェントへの分離は有用だが、それだけでテストの独立性が保証されるわけではない。**

### 7.4 TDDが適する対象

| 対象 | 適性 | 備考 |
|---|---|---|
| ドメインロジック、入力検証、パーサ | 高 | 入出力・境界条件が明確 |
| 状態遷移、アルゴリズム | 高 | 性質・モデルとの比較も有効 |
| アプリケーションサービス | 中〜高 | 外部副作用を分離して検証 |
| OS固有処理 | 中 | 契約テスト・実機統合テストを併用 |
| GUIレイアウト・ビジュアル | 低〜中 | 視覚的レビュー・操作テストも必要 |
| 探索的な試作 | 条件付き | 変更が激しい段階では過度な先行テストを避ける |

## 8. ADR：設計判断の記録

ADR (Architecture Decision Record) は、重要な判断の**背景・採用案・代替案・影響**を短く残す。

```markdown
# ADR-0001: UIフレームワークの選定

- 状態: 承認
- Date: YYYY-MM-DD

## Context
Windows/Linux向けのRust製GUIを必要とする。

## Decision
UIフレームワークとしてicedを採用する。

## Alternatives
- egui
- Slint

## Consequences
- icedの状態管理に合わせた設計を行う。
- OS固有機能はUIから分離する。

## Related
- REQ-... / ISS-...
```

### 8.1 運用ルール

- 判断が将来の変更に重要な影響を及ぼす場合に記録する。
- 採用理由、却下理由、依存条件を明記する。
- 原則として過去のADRを黙って書き換えず、置き換えの経緯を残す。
- ADRの状態は `提案` / `承認` / `却下` / `置換` / `廃止` を一貫して使う。`置換` は後継ADRが判断を引き継いだ状態、`廃止` は後継ADRなしで判断の適用を終了した状態とする。置換時は後継ADR、廃止時は終了理由を記録する。
- AIには関連ADRを読み、矛盾があれば変更前に提示させる。

## 9. アーキテクチャ：境界と長期的整合性

### 9.1 Hexagonal / Ports and Adapters

ドメイン・ユースケースが、OS、UI、DB、ネットワーク、ファイルシステム等の外部詳細に直接依存しない構造を目指す。

```text
             GUI (iced) / CLI / API
                     |
              Application Layer
                     |
             Domain + Ports (traits)
                  /       \
          Windows Adapter  Linux Adapter
```

- **Port**: ドメイン・アプリケーション側から見た必要な操作・契約。
- **Adapter**: OS・ストレージ・ネットワークなど具体的な実現方法。
- ドメイン制約のテストは可能な限り外部環境から切り離す。
- 共通Portへの**契約テスト**を各Adapterに適用する。
- Clean ArchitectureやOnion Architectureも類似の依存関係管理思想を持つが、用語や境界を厳密に同一視しない。

### 9.2 Evolutionary ArchitectureとFitness Functions

**Evolutionary Architecture**では、アーキテクチャを固定の完成品ではなく、重要な品質特性を守りながら進化させる対象と捉える。

| 守りたい特性 | 自動／半自動のFitness Function例 |
|---|---|
| Domain層の独立性 | UI/OS固有ライブラリへの禁止依存を検査 |
| Adapter契約の維持 | 複数実装へ同じ契約テストを適用 |
| コンテキスト境界 | 越境する依存・公開APIを検査 |
| API互換性 | 破壊的変更の検出・契約テスト |
| 循環依存の回避 | 依存グラフ解析 |
| 性能の安定 | ベンチマークと許容差の監視 |
| リソースの制約 | メモリ・CPU・I/O使用量テスト |
| 安全性 | 権限境界・入力バリデーション等の検査 |

**ADRは「なぜそう設計したか」、Fitness Functionは「今も守られているか」を補完する。**

#### 制約の継続確認

守る必要がある設計制約を特定したら、その重要度とプロジェクトの規模に応じて確認方法を選ぶ。

| 確認方法 | 例 |
|---|---|
| 自動検査 | 依存方向、循環依存、公開API・スキーマ互換性 |
| テスト・計測 | データ形式、不変条件、性能・メモリ上限、セキュリティ境界 |
| 人間の設計レビュー | ドメイン境界、責務分割、将来の変更容易性 |

すべてを自動化したり、特定ツールを全プロジェクトへ導入したりする必要はない。制約、確認方法、結果の根拠を既存の設計資料、テスト、CI、課題、またはレビュー記録に残す。継続的に守る必要のある制約が破られた場合は、影響を評価し、修正が必要なら課題表に記録する。

### 9.3 CQRS / Event Sourcing

- **CQRS**: 読み取りモデルと書き込みモデルを必要に応じて分離する。
- **Event Sourcing**: 状態の変更をイベント履歴として保持・再生する。

監査、複雑な状態遷移、非同期処理等で有効だが、運用・整合性・デバッグを複雑にする。**AIが簡単にコード生成できることを採用理由にしない。**

### 9.4 Performance by Design

Performance by Designは、後工程の最適化だけに頼らず、設計初期から処理構造の効率性を考える基本設計原則である。DDD、Self-documenting Code、Robustness by Design、Replaceability by Designと並ぶ横断原則として、アルゴリズム、データ構造、依存、データフロー、リソース利用が要求するワークロードに適合することを重視する。

#### 要求・ワークロード

性能が製品上重要な場合は、対象となる処理量、入力・データ規模、想定環境を把握する。必要な項目だけ選び、レイテンシ・起動時間・スループット、計算量・空間量、CPU/GPU/メモリ使用、割り当て・コピー、ストレージ・ネットワークI/O、データ局所性、並行性・同期、バックプレッシャー・リソース制御、バックグラウンド負荷、OS・ハードウェア制約を要求仕様や設計資料に記録する。根拠が揃わない段階で数値目標を作らず、前提・懸念・後で確かめる方法を明記する。

#### アルゴリズム・データ構造・アーキテクチャ

- 想定データ規模とアクセスパターンに適した計算量・データ構造を選び、増大時の挙動も確認する。
- 不要な再計算、割り当て、コピー、全量読み込み、変換、I/Oを避ける。ストリーミング、バッファリング、バッチ化、非同期・並列化は実際の効果とオーバーヘッドが見込める場合に選ぶ。
- キャッシュは必要性、無効化、整合性、メモリ上限を含めて設計する。並行処理では同期コスト、競合、バックプレッシャー、リソースのライフサイクルも考慮する。
- Big-Oだけで実性能を断定しない。データ規模、定数コスト、I/O、対象環境を踏まえ、必要な場合に計測する。
- 性能上重要な構造判断や、速度・メモリ・整合性・保守性のトレードオフは、長期的影響がある場合にADRへ記録する。

#### 検証と過剰最適化の防止

基本設計では明らかな非効率や拡張時の破綻を予防する。局所的な最適化は、プロファイルやベンチマーク、想定ワークロード、複雑度などの根拠に基づいて行う。重要な処理では代表的な入力規模でベンチマーク、プロファイリング、メモリ・I/O計測、性能退行検査を選択し、結果にはコミット、環境、入力条件、測定方法と許容差を添える。実行環境差やばらつきを考慮し、固定された単一数値を全環境へ適用しない。

実測を伴わない複雑なマイクロ最適化、必要性の薄いキャッシュ・並列化・SIMDを避ける。性能のために正確性、安全性、自己説明性、保守性を不用意に損なわず、非自明な最適化や性能制約はコードの契約、コメント、ADR、テストで意図と根拠を補う。小さな変更に大規模な性能試験を強制しない。

### 9.5 Robustness by Design

Robustness by Designは、例外処理を後付けで網羅することではなく、異常条件・部分的失敗・環境変化を初期の機能・契約・アーキテクチャ設計に含め、失敗時にも状態とデータを理解・保護・回復できるようにする横断原則である。「失敗しても壊れないこと」と「失敗したことを正しく伝えること」は別の保証であり、重要な操作では必要に応じて両方を要求と受け入れ条件にする。

#### 原則と適用判断

| 原則 | 目的・適用条件 | 注意点・トレードオフ |
|---|---|---|
| Design by Contract | 事前条件、事後条件、不変条件、失敗時保証を明らかにする | 信頼できない入力・境界では実行時検証も行い、内部契約違反を黙って補正しない |
| Design for Failure | 重要な依存・操作について起こり得る失敗と影響を設計する | 可能性の低い全事象を同じ深さで扱わず、影響とコストに応じる |
| Defensive Design | 信頼境界や破損し得るデータを検証し、誤用・破損を封じ込める | すべての内部値の重複検証や、矛盾を隠す既定値化は避ける |
| Fail-Safe Defaults | 不確実・権限不足・未初期化時に安全側へ倒す | 利用者が気付かない機能停止や、誤った成功表示を招かない |
| Graceful Degradation | 一部機能・依存が使えなくても安全な範囲で有用性を維持する | 不正確・古い結果や制限された機能を明示し、整合性を損なわない |
| Fault Isolation / Containment | 障害の影響を境界内に留め、他の処理・データを保護する | 冗長化や隔離の運用・同期コストが便益に見合う範囲で用いる |
| Recovery-Oriented Design | ロールバック、再開、再同期、バックアップ等で復旧できるようにする | 復旧可能性、復旧地点、失われ得る作業を明確にする |
| Idempotency | 再送・再実行で意図しない重複副作用を防ぐ | 操作識別子や重複排除の保存コスト、保持期間を設計する |
| State Consistency / Invariants | 状態遷移とデータ不変条件を保ち、部分状態を定義する | 一時的な不整合を許す場合は、収束条件と利用者への表示を定める |
| Transactionality / Atomicity | 複数変更を一括反映するか、失敗時の中間状態を保証する | 分散境界で完全な原子性を仮定せず、補償処理や部分成功を設計する |
| Resource Safety | ファイル、ロック、メモリ、接続等の所有・解放・上限を明らかにする | 制限値は対象環境・運用条件を根拠に定め、無制限な待機・蓄積を避ける |
| Observability / Diagnosability | 利用者と運用者が結果、原因、相関関係を診断できるようにする | 個人情報・秘密をログに出さず、必要な詳細を適切な利用者へ分けて示す |

#### 異常条件・失敗時契約の設計

機能や境界に関連するものを選び、次の状況を設計時に確認する。

- 不正入力・破損データ・予想外の規模、ファイルやデータの不整合
- 権限不足、ディスク・メモリ等のリソース不足、ディスク容量不足
- ネットワーク切断・遅延・タイムアウト、外部APIや依存コンポーネントの失敗
- 部分的な成功、処理途中のキャンセル、異常終了後の再起動
- 並行処理の競合、OS・環境・バージョン差異

重要な操作では、失敗時にどのデータが変更済みか、原子性の範囲、再実行時の副作用、ロールバック・補償・再開の可否、利用者へ返す状態と診断情報を定める。UI上のキャンセルは見た目だけの操作ではなく、アプリケーション層・ドメイン処理・外部I/Oまで含む停止地点、すでに適用済みの変更、整合性保証を持つ機能要求である。再試行は一時的エラー、タイムアウト、重複実行の可能性と冪等性を確認し、無条件に行わない。

処理の種類に応じて、境界値・Property-Based・状態機械/モデルベース・Fault Injection・復旧・並行性・リソース枯渇・回帰テストから必要な検証を選ぶ。データ損失、不変条件違反、重大な運用影響があり得るほど強い検証を選び、すべてを一律必須にしない。テストやログが示すのは実際に検証した条件の範囲であり、未検証の環境や故障モードまで保証したとは扱わない。

#### 性能・UXとの共同設計

性能と堅牢性はユーザー体験にも影響する。大量データを扱う閲覧機能では、遅延読み込み・仮想化・段階的表示・キャンセルが応答性を高める一方、読み込み失敗・途中キャンセル・古い結果の識別を要する。ネットワーク同期では再試行が利用者の回復手段となる一方、冪等性・競合解決・進捗表示が必要となる。

| 機能 | UI/UXの設計 | Performance by Design | Robustness by Design |
|---|---|---|---|
| ファイルコピー | 進捗、対象別結果、取消と結果の明示 | ストリーミング、適切なI/O、バッチ/同時実行制御 | 部分失敗、破損防止、取消境界、再実行・復旧 |
| 画像ブラウザー | 一覧の応答性、選択状態、読み込み中表示 | サムネイルキャッシュ、遅延読み込み、仮想化 | 破損画像やデコーダ失敗の隔離、再読み込み |
| ネットワーク同期 | 状態・進捗・競合・再試行を利用者に伝える | 差分転送、バックプレッシャー、帯域/CPU制御 | 切断、重複要求、冪等性、競合解決、再開 |
| 設定変更 | 変更内容の理解、プレビュー、必要ならUndo | 変更箇所に絞った再計算 | 原子的保存、安全な既定値、失敗後の復元 |

速度のために整合性を緩める、可用性のために古いキャッシュを返す、自動リトライで意図しない重複操作を起こす、単純なUIのために重要なエラー情報を隠す、並列化で再現性・状態整合性を損なうなど重要なトレードオフは、対象ワークロード、利用者への影響、保証範囲を比較し、長期的・重大な判断ならADRに記録する。

### 9.6 Replaceability by Design

Replaceability by Design（交換可能性を考慮した設計）は、主要な技術依存について将来のライブラリ・フレームワーク・バックエンド・プラットフォーム変更を考慮し、変更影響を必要な境界に留める横断原則である。目的はすべての依存を即座に交換できるようにすることではない。変更の可能性・影響・費用を踏まえて交換価値のある境界を選び、技術固有の詳細からドメイン概念や主要なユースケースを守ることにある。

#### 関連原則・手法の役割

| 原則・手法 | 交換可能性への寄与 | 適用時の注意 |
|---|---|---|
| Separation of Concerns | 技術詳細とドメイン/ユースケースの責務を分ける | 分割単位は実際の変更理由と責務に合わせる |
| High Cohesion / Low Coupling | 関連する振る舞いをまとめ、不要な依存を減らす | 結合をゼロにするのではなく、変更波及を抑える |
| Dependency Inversion Principle | 方針を外部詳細から独立させ、必要な境界で内側が契約を定義する | すべての依存をinterface化しない |
| Dependency Injection | 具体的な実装選択を組み立て時に注入する | Service Locatorや不要なDIコンテナへ置き換えない |
| Interface Segregation Principle | 利用者が必要とする小さな責務別契約を設ける | 不自然に細切れの型・操作を増やさない |
| Ports and Adapters / Hexagonal、Clean Architecture | コアの要求をPort、外部技術をAdapterとして分け、依存方向を内向きに保つ | 導入する層やPort数は必要な境界に絞る |
| Adapter / Anti-Corruption Layer | 外部APIや異なるモデルを内部の意味へ変換する | 変換規則、損失、エラーを明示し、重要な意味を隠さない |
| Strategy Pattern / Plugin Architecture | 実行時の選択や拡張が製品要件となる複数実装を扱う | 実装が一つで拡張要求もない場合は機構を先回りで作らない |
| Evolutionary Architecture / Fitness Functions | 依存方向や重要契約が変更後も守られるか検証する | 重要な制約だけ、自動化コストに見合う形で保護する |

#### 抽象化の境界を選ぶ

抽象化は、技術ライブラリのAPI形状を隠すためだけではなく、アプリケーションやドメインが必要とする意味のある能力と契約を表す。候補となる依存について、設計時に次を確認する。

1. 変更の可能性、供給終了/ライセンス/プラットフォーム/運用リスク、変更時の波及範囲を根拠とともに見積もる。
2. 交換可能性を必要とする理由（複数実装、プラットフォーム差、テスト分離、移行コスト制御など）と、境界を設ける費用を比較する。
3. 境界を選ぶなら、コアが必要とする操作、データ、エラー、トランザクション/整合性、並行性、性能、セキュリティの意味的契約を定義する。
4. 具体的なAdapterは契約を満たし、各実装が同じ契約テストを共有できる構造を検討する。
5. 必要な依存方向の静的検査・アーキテクチャテスト・小さな交換実験のうち、費用対効果のある検証を選ぶ。

低リスクで安定した依存は直接使ってよい。交換が重要な境界でも、開始時から複数実装を用意する必要はない。まずコアと具体的実装を明確に分け、変更の必要が実際に現れた時点で契約やAdapterを発展させる方法も適切である。抽象化する場合も、ライブラリ固有の型・エラー・状態・ライフサイクルが境界を越えてコアへ漏れないことを確認する。

#### UIフレームワークとアプリケーションコア

UIライブラリ（例: Rustアプリでのiced、Dioxus Desktop、Slint）はビュー描画、イベント配送、UIライフサイクルの実装に必要であり、ビュー自体を別フレームワークへ無変更で移行できると約束しない。目的は、UIを変更するときにドメイン、データモデル、主要ユースケースを可能な限り保てる境界を作ることにある。

- ドメインロジックとアプリケーションのユースケースはUIライブラリへ依存させない。
- UIイベントはアプリケーションの操作/APIへ変換し、UI固有イベント・widget型・描画状態をコア型として使わない。
- ドメイン状態、アプリケーション状態、UI固有の一時表示状態（選択中行、展開状態、フォーカス等）を区別する。Presentation Model / ViewModelは変換やUI状態の分離に便益がある場合だけ採用する。
- UI固有の非同期タスク、ライフサイクル、スレッド/ランタイム連携は境界に局所化する。ユースケースと状態遷移は可能な限りUIに依存せずテストする。
- UIから呼ぶアプリケーションAPIは、ユーザーの意図と結果を表す技術中立な操作とし、フレームワークのイベント型をそのまま渡さない。

#### バックエンド・インフラ依存の契約

DB/ストレージ、ネットワーク/HTTP、シリアライズ、ロギング、ファイルシステム、OS API、外部/クラウドサービス、非同期ランタイム、暗号・圧縮・メディア処理は、交換価値がある場合にInfrastructure層やAdapterへ分離する。API形状が似るだけでは互換とは言えない。永続形式と移行、エラーの分類、トランザクション・整合性、順序・並行性、タイムアウト・キャンセル、資源所有、性能特性、セキュリティ保証を比較し、違いを呼び出し側へ明示または意味のある変換で扱う。

技術選択を変更する場合、保存済みデータの後方互換性・マイグレーション/ロールバック、OSやプラットフォーム固有機能、運用・診断、ユーザー体験を含む影響範囲を計画する。Adapterの契約テストだけで実バックエンドの全特性を保証したとは扱わず、必要に応じて統合テストや移行試験を行う。

#### 過剰な抽象化を避ける

次の設計は交換可能性ではなく複雑性・意味損失を招きやすい。

- あらゆる具体型にtrait/interfaceを設ける、あるいは使用予定のない実装に備えて複雑な拡張機構を作る。
- 特定ライブラリのAPIを一対一で包むだけの層を大量に作る。
- 複数実装の最小公倍数のような共通APIを強制し、重要な機能や保証を捨てる。
- 動的ディスパッチ、コピー、変換、追加割り当て、非同期境界の性能・故障コストを無視する。
- 抽象化境界を越えてライブラリ固有の型・エラー・状態を漏出させ、表面だけを中立化する。
- 交換可能性のために現在の信頼性、性能、理解可能性を不必要に損なう。

単一実装で十分なら具体型を直接使用してよい。どの境界を守るか、その理由、許容する依存、交換時に変更が必要な範囲は、必要に応じて要求・アーキテクチャ資料・ADRに記録する。

#### 検証と他の設計品質との関係

交換可能性は「変更なしで差し替えられる」という一般保証ではなく、意図した変更範囲と契約を説明・検証できる品質特性である。必要に応じて次を受け入れ条件にする。

- コア層からUI/バックエンド固有依存への禁止依存がない（依存グラフ/アーキテクチャテスト）。
- 対象Adapterが共有契約テストを満たし、主要なエラー・整合性・状態遷移を保つ。
- 交換対象、変更が必要な層、データ移行・互換性、残るプラットフォーム差を説明できる。
- 性能・セキュリティ・運用・UX上の差異を把握し、必要ならベンチマーク/統合テスト/交換実験で比較する。

DDDはドメイン概念を技術選択から独立させ、Self-documenting Codeは境界と契約の意図を読みやすくする。Performance by Designは間接化・変換コストを、Robustness by Designは交換後にも不変条件・失敗時保証を保つことを評価する。UI/UX-driven Functional Designは利用者の必要な振る舞いをUI技術と分離して定義する。変更容易性と性能・堅牢性・UXの競合は実際の価値と根拠で判断し、重要な選択はADRへ記録する。

### 9.7 Security by Design

Security by Design（セキュリティを考慮した設計）は、資産・利用状況・信頼境界・脅威に応じた予防、検知、影響抑制を、要求・設計・実装・運用・検証へ早期に組み込む横断原則である。セキュリティを特定製品・規制・攻撃者に対する絶対保証とは扱わず、対象外の脅威、前提、残余リスク、検証範囲を明確にする。

#### 適用範囲と脅威分析

変更の影響と攻撃可能性に応じて分析の深さを選ぶ。ローカルの小さな変更で新たな信頼境界・機密データ・特権処理を増やさない場合は、適用外または限定的と判断した根拠を短く残せばよい。次の変更は設計時の脅威分析を重点化する。

- 外部入力、ネットワーク、ファイル、IPC、プラグイン、AIモデル/ツールなどの信頼境界を新設・変更する。
- 認証・認可、特権、秘密情報、個人情報、機密データ、テナント境界を扱う。
- 更新・配布、依存関係・ビルド/CI、暗号、データ削除、破壊的操作など、侵害時の影響が大きい処理を変更する。

対象に応じ、資産と機密性・完全性・可用性への影響、利用者・運用者・依存先、信頼境界とデータ/コマンドの流れ、想定する攻撃者能力・アクセス、攻撃経路・悪用条件、既存の制御、対策後の残余リスクを記述する。全脅威の列挙を目的にせず、判断に影響する範囲を扱う。継続的な脅威分析の共通手順は[Threat Modeling（§11.1）](#111-threat-modeling)を参照する。

#### セキュリティ契約と制御の選択

- **最小権限と安全な既定値:** 必要な主体・処理・時間・資源へ権限を絞る。機能・ユーザー体験・運用要件を保てる範囲で、安全な設定を既定にする。権限昇格・無効化・初期資格情報が必要な場合は、その条件と保護を明記する。
- **多層防御と攻撃面の縮小:** 単一制御を前提にせず、入力境界での検証、認可、分離、制限、監査などを脅威に応じて組み合わせる。不要な入口・権限・データ保持・依存を避けるが、重複制御を追加するだけで安全とみなさない。
- **データライフサイクルと依存:** 収集・利用・転送・保存・ログ・バックアップ・保持・削除を必要な範囲で定める。サードパーティ/供給網の依存、更新元、権限、脆弱性対応も変更リスクに応じて確認する。暗号を使う場合、データ分類、脅威、鍵管理・寿命・ローテーション、実装基盤に根拠を置く。
- **不変条件と失敗時:** 認可されていない状態変更・情報開示がないこと、テナント/資源境界が保たれること、秘密・個人情報が意図しない出力先へ出ないことなど、重要なセキュリティ不変条件を定義する。拒否・タイムアウト・依存障害時の状態、診断、監査、回復をRobustness by Designと一緒に扱う。
- **検証可能性:** 重要な制御を受け入れ条件へ結び、設計レビュー、テスト、静的/動的解析、依存・秘密スキャン、構成確認、手動評価から適切な方法を選ぶ。ツール出力は対象範囲・設定・例外・版とともに解釈し、未評価の攻撃面や未実施検証を明示する。

脅威・影響・要求を記録する必要がある場合は、既存の要求仕様、ADR、リスク記録を使い、実施する軽減・修正・検証作業は課題表で追跡する。新しいセキュリティ台帳や完成度評価軸は追加しない。既知の脆弱性・不適合は将来リスクだけに記録せず課題として扱い、将来の攻撃可能性や残余影響は既存のリスク管理規約に接続する。

#### 参考となる公式資料

以下は対象に合う場合の参照元であり、DevConcordや導入先の準拠認証・包括的な適合を意味しない。版が変わり得るため、規制・契約上の要求に使う場合は適用時点の原本と対象範囲を確認する。

- [CISA et al., Shifting the Balance of Cybersecurity Risk: Principles and Approaches for Secure by Design Software](https://www.cisa.gov/sites/default/files/2023-10/Shifting-the-Balance-of-Cybersecurity-Risk-Principles-and-Approaches-for-Secure-by-Design-Software.pdf)：製品提供者の設計・既定値・責任に関する指針。契約上の規格ではない。
- [NIST SP 800-218, SSDF v1.1](https://csrc.nist.gov/pubs/sp/800/218/final) は確定版。NISTの[公開資料一覧](https://csrc.nist.gov/Projects/ssdf/publications)ではSSDF v1.2（SP 800-218 Rev.1）は2025-12-17公開の草案であり、確定版と混同しない。
- [NIST SP 800-53 Rev. 5](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)：セキュリティ・プライバシー制御のカタログ。変更履歴でRelease 5.2.0（2025-08-27）を確認する。全プロジェクトへ一律適用するチェックリストではない。
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) はWebアプリケーションの検証要求を選ぶ基準（同ページ掲載の最新安定版 v5.0.0を確認）。非Web製品へそのまま適用しない。
- [OWASP SAMM](https://owasp.org/www-project-samm/) は組織のソフトウェア保証成熟度を改善するモデルであり、個別製品の安全性認証ではない。
- [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/) は話題ごとの実務ガイダンス。対象技術・脅威に合う項目を選び、他の制御を代替する保証としない。
- [MITRE CWE](https://cwe.mitre.org/) はソフトウェアの弱点分類、[MITRE ATT&CK](https://attack.mitre.org/) は実世界で観測された攻撃者の戦術・技法の知識ベースであり、要求規格や網羅的脅威モデルではない。

## 10. 検証手法の使い分け

| 手法 | 主な検証対象 | 推奨場面 | 代表的な限界 |
|---|---|---|---|
| Unit Test | 関数・型・ドメインルール | 高速な回帰検出 | モジュール間・実環境の問題は捕捉しにくい |
| Integration Test | OS、DB、外部サービス等との連携 | Adapter・実I/Oの動作 | 遅い・環境依存 |
| Acceptance / E2E Test | ユーザー視点の完成条件 | 主要ユースケース | 不安定・実行コスト大 |
| Property-Based Test | 多数の入力に共通する性質 | パーサ、シリアライズ、領域計算 | 性質が間違うと意味がない |
| Fault Injection / Recovery Test | 依存先の失敗、途中停止後の状態・復旧 | 外部I/O、永続化、重要な非同期処理 | 故障注入範囲・本番との差がある |
| Concurrency / Resource Test | 競合、上限到達、枯渇時の保証 | 共有状態、キュー、バッチ、リソース制御 | 実行環境差・非決定性がある |
| Contract Test | Portやサービス間の互換性 | OS別Adapter、API、複数チーム | 契約外の品質は保証しない |
| Model-Based Test | 参照状態機械と操作列 | マウント状態、キュー、操作ライフサイクル | 参照モデルにも誤りがあり得る |
| Mutation Test | テストが変更を検知できるか | 中核ロジックのテスト品質評価 | 実行負荷、等価ミュータントの問題 |
| Static Analysis | 特定のコード規約・潜在的不具合 | すべてのPR | 全ての仕様違反は発見できない |
| Manual / Visual Review | UX、アクセシビリティ、現実の操作感 | GUIや複雑なユーザーフロー | 再現性・網羅性に限界 |
| Formal Verification | 定式化した特定の性質 | 高リスクなロジック | 形式化の正しさと範囲に依存 |

### 10.1 変更影響分析

実装前に、変更対象から波及する範囲を規模・リスクに応じて確認する。小さな文言や局所的な変更では、影響が限定される根拠を短く示せばよい。公開契約、永続データ、複数モジュール、セキュリティ境界、プラットフォーム依存などに触れる変更では、関連領域を具体的に列挙して検証計画に反映する。

- 変更対象と依存元・依存先、公開APIと互換性
- データ形式、永続化、状態遷移、不変条件
- エラー処理と失敗時の保証
- セキュリティ境界、権限、入力検証
- OS・実行環境差、既存テストと回帰範囲
- 関連する要求、ADR、課題、リスク、文書

変更後は実際の差分を当初の影響分析と照合し、想定外の波及や未実施検証を報告する。影響分析の記録は作業依頼、変更説明、または既存課題の詳細に置き、独立した台帳は作らない。

### 10.2 Rustでの候補

- 標準: `cargo test`, `cargo fmt`, `cargo clippy`
- Property-Based Testing: `proptest`、`quickcheck`
- Mutation Testing: `cargo-mutants`
- セキュリティ・依存関係監査: プロジェクト環境に応じて `cargo-audit` 等
- ベンチマーク: `criterion` 等
- E2E/UI: OS・GUIの実行環境に合わせて選定

### 10.3 CIの基本ゲート例

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
```

コマンドはプロジェクト構成・feature設定・対象OSに応じて調整する。Windows/Linux固有の処理は各OSでのCI・実機検証を別途用意する。

### 10.4 テストの品質は「数」だけで測らない

- カバレッジ率だけでは正しいアサーションの有無を示せない。
- 仕様上重要な失敗パス・境界値・競合・権限を重視する。
- テストの成功と要求適合性は別々にレビューする。
- flakyなテストを放置せず、原因と対処を課題として記録する。

## 11. セキュリティ・信頼性・形式的手法

### 11.1 Threat Modeling

Security by Design（§9.7）の適用範囲と記録先に従い、変更で信頼境界・資産・攻撃面が変わる箇所を選んで分析する。特に、管理者権限やOS低レベル操作、破壊的なディスク/ファイル操作、ネットワーク入力、認証・認可・秘密情報・ユーザーデータ、更新機構・外部コマンドを扱う変更は影響を評価する。対象に応じ「資産・信頼境界とデータ/制御フロー・攻撃者/アクセス・脅威と影響・緩和策・残余リスク・検証方法」を記録する。すべての変更へ同じ規模の分析を要求せず、低リスク変更は限定範囲の根拠を示す。

### 11.2 Formal Methodsの位置付け

形式的手法は全プロジェクトに全面導入するものではない。状態機械、整合性、並行処理、危険なデータ操作など、**誤りの影響が大きく仕様を形式化しやすい部分**を候補とする。形式的な保証も、モデル化した前提と性質の範囲内に限られる。

### 11.3 Privacy & Environment Hygiene

開発中に扱う情報は、内容の機密性・公開可能性と、共有に必要な理由に応じて次のように区別する。

| 区分 | 例 | 基本的な扱い |
|---|---|---|
| 個人情報 | 氏名、個人メール・電話・住所、個人アカウントID、個人を識別できる値 | 必要最小限を扱い、共有資料・ログ・出力に目的なく含めない |
| 個人環境情報 | ユーザー名入りホームパス、ホスト名、マウントポイント、ローカルネットワーク、個人設定や端末構成 | 共有には相対パス、環境変数、標準API、明示的なプレースホルダーを使う |
| 秘密情報 | APIキー、トークン、パスワード、秘密鍵、認証Cookie、資格情報入り接続文字列 | コード・設定・資料・テストへ実値を埋め込まず、秘密管理機構から実行時に渡す |

絶対パスを一律に禁止しない。OS仕様、API契約、固定のシステムパス、パス処理テストなどで必要な場合は使用できる。問題にするのは実ユーザー名や個人環境を不要に埋め込むこと。共有用サンプルは架空値や `<PROJECT_ROOT>` などのプレースホルダーを使い、実環境の設定や秘密情報を含むファイルと分離する。

この扱いはソース、設定、テスト、ログ、例外、スクリーンショット、CI出力、生成物、AIの応答・作業報告に適用する。ターミナル出力や診断情報を共有する前に個人・環境・秘密情報を確認し、報告には原則リポジトリ相対パスを使う。既存ファイルに機密情報が含まれる可能性がある場合、調査・検証・報告のために内容を別ファイルへ複製しない。発見時は値を転載せず、場所と影響を安全に報告し、露出した秘密情報の無効化・交換が必要かを適切な担当者へ伝える。個人情報は必要性と根拠なしに外部サービスへ送信しない。

ログには認証情報を記録せず、個人情報も必要最小限にする。エラー調査に必要な情報と公開・保存すべきでない値を分け、可能ならそもそも収集しない設計を優先する。マスキングや匿名化は補助策であり、完全な防御とみなさない。ローカル検証やCIログ、テスト失敗出力にも同じ規則を適用する。

文書のパターン検査は明白な個人パス・連絡先・既知形式の秘密らしき値を補助的に検出できるが、誤検出・見逃しがあり、秘密スキャンの代替ではない。コード・設定等も含むプロジェクトでは、必要性に応じてリポジトリ全体に適用できる専用シークレットスキャンを選ぶ。既知の秘密情報をGitへ追加しない。

## 12. AIエージェントとの役割分担

| 作業 | AIに任せやすいこと | 人間が重点確認すること |
|---|---|---|
| ドメイン分析 | 概念候補・矛盾の洗い出し | 用語と現実の意味・境界の妥当性 |
| 仕様策定 | 要件整理・シナリオ草案 | スコープ・優先度・受け入れ条件 |
| 設計 | 代替案、依存関係分析、ADR草案 | トレードオフと重大判断 |
| テスト | ケース列挙、テストコード生成 | 期待値と抜け漏れ、独立性 |
| 実装 | 詳細設計、コード、リファクタリング | 安全性・設計整合性・変更範囲 |
| 検証 | テスト実行、静的解析、差分分析 | 結果の意味・残存リスク |
| 課題管理 | 課題分類、進捗・未達事項更新 | 完了判定と次の優先順位 |

### 12.1 AIへの共通ガードレール

- 作業開始前に、関連仕様・ドメイン文書・ADR・既存テストを確認する。
- ユーザー向け機能では目的・主要タスク・状態・操作・受け入れ条件を確認し、GUIがない製品では実際の利用者接点に合わせる。
- 変更する責務と変更しない責務を示す。
- 既存契約に矛盾する場合、黙って変更せず差分を報告する。
- 重要な機能では性能上のワークロードと異常時の契約・整合性・復旧可能性を必要な範囲で確認する。
- 速度・UX・整合性・安全性・保守性のトレードオフを明示し、重大な判断は必要に応じてADRへつなぐ。
- テストを通すためだけに仕様・期待値を弱体化しない。
- モックのテスト成功を実環境の保証として扱わない。
- 大きな変更は段階に分割し、それぞれで検証する。
- 未実施の検証は実施済みと記載しない。
- 完了時に、変更点・テスト結果・残余リスク・課題表更新を報告する。
- 利用可能なAgent Skillsがある場合は、適用条件を確認して必要な作業ワークフローだけを利用する。Skillsは常時適用ルールの `AGENTS.md`、レビュー基準の `REVIEW.md`、詳細規約の `docs/` を置き換えず、エージェントの実行権限境界にもならない。実行結果と検証証跡は独立して確認する。
- 共通Skillは標準 `SKILL.md` とポータブルな機能を優先し、ベンダー固有の呼び出し構文や権限設定を混在させない。Skills非対応環境では、正本のSkill本体と必要な詳細資料の全文を対象エージェントへ渡して実行する。

## 13. 課題表ベースのプロジェクト管理への統合

### 13.1 推奨される追跡関係

```text
Requirement (REQ-... / NFR-...)
  ├─ Acceptance Criteria
  ├─ Design / ADR (when needed)
  ├─ Implementation (code / PR)
  ├─ Verification (test / CI / review evidence)
  ├─ Issue (ISS-... when work remains)
  └─ Risk (RISK-... when future uncertainty exists)
```

すべての小さな変更にすべてのIDを強制する必要はない。重要な要求・制約・意思決定・実装・検証を**必要な粒度で追跡可能**にする。

要求仕様書が要求IDと受け入れ条件の管理元、ADRが設計判断の管理元、課題表が不具合・改善・技術的負債と対応作業の管理元である。検証結果はテスト・CI・レビュー記録を根拠とし、要求や課題から参照する。将来の不確実性と残余リスクはリスク管理資料で管理する。IDやリンクで関係を結び、同じ内容を複数文書で状態管理しない。小規模プロジェクトでは要求仕様書内の参照欄で十分であり、巨大なマトリクスを強制しない。

### 13.2 課題表の推奨項目

| 項目 | 内容 |
|---|---|
| ID | 課題の一意識別子 |
| Title / Type | 機能・バグ・設計・テスト・セキュリティ等 |
| Priority / Risk | `P0` / `P1` / `P2` / `P3` の優先度と失敗時の影響 |
| Requirement | 対応する要求仕様 |
| Context / Component | 対象ドメイン境界・モジュール |
| Contract | 関連する事前・事後・不変条件 |
| Acceptance Criteria | 完了を判定できる条件 |
| ADR | 関連する設計判断 |
| Tests / Evidence | テストやレビューの根拠 |
| Status | `未着手` / `進行中` / `レビュー待ち` / `ブロック` / `完了` / `見送り` |

横に広くなりすぎる場合、一覧表には `ID / 概要 / 優先度 / 状態 / 参照リンク` のみを配置し、詳細を個別節へ分離する。

### 13.3 課題記述テンプレート

```markdown
### ISS-0123: ディスクイメージの安全なサイズ変更

- 状態: 未着手
- 優先度: P1
- リスク: 高
- 要求: REQ-DISK-008
- コンテキスト: Disk Image Management
- 関連ADR: ADR-0007

#### 目的
サイズ変更操作の事前検証と失敗時の扱いを確立する。

#### 契約
- 事前条件: サポート対象形式・変更可能状態・安全下限を満たす。
- 事後条件: 成功時は要求された変更が反映される。
- 失敗時: 保証可能な状態・未確定状態を明確に返す。

#### 受け入れ条件
- [ ] サポート外の要求を適切なエラーで拒否する。
- [ ] 境界値をテストする。
- [ ] 変更前後の状態再検証を行う。
- [ ] 各対象OSの統合テスト結果を記録する。
- [ ] 既存仕様やADRとの矛盾がない。

#### 根拠・検証
- 単体テスト:
- 性質テスト:
- 統合テスト:
- レビュー:

#### 残存リスク
- ...
```

### 13.4 Definition of Ready（着手条件）

- [ ] 課題の目的と対象が明確である。
- [ ] 参照すべき仕様・設計・ADRを特定した。
- [ ] 重要な曖昧さ・依存関係を解消、または明記した。
- [ ] 受け入れ条件と検証方針がある。
- [ ] 安全性・互換性への影響を確認した。

探索・調査課題では成果物を「調査結果・選択肢・未解決事項」とし、実装と同じ完成条件を無理に当てはめない。

### 13.5 Definition of Done（完了条件）

以下は課題ごとの完了条件を置き換えない共通の最低基準である。変更内容に該当する項目を適用し、該当しない項目は理由を簡潔に示す。

- [ ] 仕様・契約・受け入れ条件を満たすことを確認した。
- [ ] 設計原則・既存アーキテクチャとの整合と、変更影響範囲を確認した。
- [ ] 必要なビルド、静的解析、正常系・異常系・境界条件の検証を実施した。
- [ ] CIおよび必要なOS別検証を実施した。実行できない場合は理由と残るリスクを記録し、成功扱いにしない。
- [ ] セキュリティ・互換性・パフォーマンス・堅牢性の影響を評価した。重要な操作は関連する異常条件、整合性、復旧の検証を行った。
- [ ] 設計変更があればADR・仕様・関連文書を更新した。
- [ ] 必要なレビューを完了し、指摘を解決または別課題として記録した。
- [ ] 検証証跡、未解決リスク、関連課題の状態を更新した。
- [ ] 要求・設計・実装・検証の参照関係が必要な範囲で追跡できる。
- [ ] 変更対象の意図・責務・契約・振る舞いがコード、型、構造、テスト等から理解できる。コードで示せない設計理由や制約は適切な資料で補った。
- [ ] 公開または変更された重要なAPIに必要なDoc Commentsがあり、契約・エラー・副作用・制約・使用例が実装と一致する。必要な使用例は可能な範囲で検証し、変更で古くなった記述も更新した。
- [ ] 未解決事項や重要な注意を必要に応じてAnnotation Commentsで示し、重要な作業は既存課題IDへ関連付けた。解消済みの注釈を残さず、課題表を唯一の進捗管理元とした。
- [ ] コメント・例・生成された文書に秘密情報や不要な個人環境情報を含めていない。
- [ ] 変更に関係する個人情報・秘密情報・環境情報を確認し、不要な値や個人環境依存を共有物へ含めていない。ログ・テスト出力・生成物も対象とする。
- [ ] 性能に関係する変更では、計算量・メモリ・I/O・同期等の影響を検討し、明らかな非効率を導入していない。重要な変更で未実施の計測や性能リスクがあれば理由とトレードオフを記録した。
- [ ] 重要な変更では、関連する異常条件・状態不変条件・失敗時保証・再実行や復旧方法を確認し、必要な検証と未確認範囲を記録した。

これらの項目は変更内容に関係する範囲で適用する。文章修正や機械生成物の更新など、該当しない変更に全面的なSDS再計算や大規模な性能試験を要求しない。

**既存文書がある場合は名称・役割を尊重し、無理に複製しない。** 小規模プロジェクトでは `domain.md` と `contexts.md`、あるいは仕様と受け入れ条件を一つにまとめてもよい。

### 14.1 `AGENTS.md` に追加する短い指示例

```markdown
## Design and development policy

- Read `docs/common/ai-assisted-development.md` before substantial design changes.
- Treat documented requirements, contracts, and ADRs as design constraints.
- Consult `docs/application-design/domain.md` and `docs/application-design/architecture.md` where relevant.
- For each issue, identify acceptance criteria and a verification strategy.
- Prefer small, reviewable changes; preserve existing behavior unless approved.
- Do not weaken or delete tests solely to make implementation pass.
- Keep personal data, credentials, and machine-specific values out of shared files, logs, and reports; use repository-relative paths when possible.
- For user-facing or user-operated features, derive required behavior and acceptance criteria from user goals and tasks; adapt to the product's interaction model.
- Consider workload, algorithm/data-structure cost, CPU/GPU, memory, and I/O when relevant; measure before local optimization.
- For important operations, define relevant failure conditions, invariants, consistency, and recovery guarantees; test the selected failure modes.
- Report verification actually performed, limitations, and remaining risks.
- Update the existing issue table and related design docs when needed.
```

パスはプロジェクトの実際の構成に合わせて変更する。

## 15. AIへの作業依頼テンプレート

### 15.1 設計・課題分解

```text
関連する要求仕様、ドメインモデル、アーキテクチャ、ADR、課題表を確認してください。
対象機能について次を行ってください。
1. 目的・対象範囲・非対象範囲を整理する。
2. ドメイン概念と既存の責務境界を確認する。
3. 利用者の目的と主要タスク、必要な操作・状態・フィードバックを整理し、UX上の判断を必要な機能要求へ変換する。既存の要求仕様書を使う場合はTASK IDとREQ IDを相互参照し、一対多/多対一をリンクで表す。
4. 事前条件・事後条件・不変条件・失敗時保証と、必要に応じて性能上重要な経路・異常条件・復旧条件を整理する。
5. 交換価値のある技術依存がある場合、変更可能性・波及影響と抽象化費用から境界・意味的契約・許容変更範囲を決める。
6. 代替設計とUX・性能・堅牢性・交換可能性のトレードオフを比較する。
7. 受け入れ条件と検証方法を定義し、TASK → REQ → 設計/実装 → 受け入れ条件 → テスト/証跡を必要な範囲で追跡できるようにする。別の巨大なマトリクスは必要性がある場合だけ作る。
8. 既存課題表に必要な課題を追記する。
9. 仕様の曖昧さと未決定事項を明示する。
既存設計と矛盾する場合、勝手に変更せず指摘してください。
```

### 15.2 実装とテスト

```text
指定課題の仕様・契約・受け入れ条件・関連ADRを確認してください。
テスト設計を先に行い、重要な境界値・異常系を列挙してください。
可能な範囲で Red → Green → Refactor の短いサイクルで実装してください。
既存テスト・契約・公開APIを正当な理由なく弱体化しないでください。
実装後は自動検証と差分レビューを実施し、以下を報告してください。
- 変更内容と設計上の根拠
- 実行したテストと結果
- 実行できなかった検証
- 残るリスク・既知の制限
- 課題表・設計文書に反映した内容
```

### 15.3 設計整合性レビュー

```text
変更差分について、仕様・ドメインモデル・契約・ADR・アーキテクチャ制約への
適合性をレビューしてください。特に次を確認してください。
- ユーザーの目的・タスクから機能・状態・受け入れ条件が導出され、性能と異常時の契約・復旧も関連する要求に含まれているか。
- 技術依存の交換境界に根拠があり、変更影響・意味的契約・データ移行・性能/堅牢性上のコストが評価されているか。全依存への抽象化、API一対一ラッパー、コアへの技術型漏出がないか。
- 概念や用語の不一致
- 責務の越境、循環依存、過剰な抽象化
- 不変条件・失敗時保証・原子性・再実行時副作用・復旧可能性の破壊
- 受け入れ条件の不足、弱いテスト、境界値の欠落
- セキュリティ・OS差分・性能・UX・互換性への影響
指摘は重大度、根拠、修正方針、対応する課題IDとともに記録してください。
```

## 16. 典型的なアンチパターン

| アンチパターン | 問題 | 推奨対応 |
|---|---|---|
| テストが通れば正しいとみなす | 同じ誤解を持つ実装・テストが成立 | 仕様レビュー・独立した検証を追加 |
| DDDをクラス・フォルダーの命名規則に矮小化 | 概念や境界が整理されない | ドメインと言語の理解から始める |
| DDDパターンを一律に強制 | ボイラープレートと複雑性が増加 | 戦略的DDDを優先し必要な型だけ使う |
| 仕様書を大量作成して放置 | コードとの乖離・二重管理 | 参照元を明確化し変更時に同期 |
| 過去の設計判断を黙って変更 | 長期的一貫性を損なう | ADRと影響範囲を更新 |
| AIがテストを都合よく修正 | 不具合が見えなくなる | 期待値変更は仕様根拠・レビューを要求 |
| モックだけで外部操作を保証 | 実OSやネットワークで失敗 | Adapterごとの契約・統合テスト |
| 大量の変更を一度に統合 | 検証・切り戻しが難しい | 小さな単位でCIとレビュー |
| すべてをE2Eで検証 | 遅く不安定で原因特定困難 | 適切な層にテストを配置 |
| 実施していないテストを「完了」と記録 | 誤った品質評価 | 実施・未実施・未確認を区別 |

## 17. 導入ロードマップ

### Phase 1: 最小の統制基盤

- 既存の要求仕様・課題表・`AGENTS.md` の参照関係を整理する。
- `domain.md` に最重要用語と不変条件を記載する。
- 各課題に受け入れ条件と検証方法を用意する。
- CIの基本ゲートを整備する。

### Phase 2: 設計一貫性の確保

- 主要コンテキストと依存関係を可視化する。
- 重大な設計判断をADRに記録する。
- 高リスクな操作にDbCと失敗時保証を明記する。
- Contract Test・OS別Integration Testを設ける。

### Phase 3: テスト品質と長期保守性

- 中核ロジックにProperty-Based Testingを導入する。
- 状態が複雑な部分にModel-Based Testingを検討する。
- Mutation Testingで重要テストの検出力を点検する。
- Architecture Fitness Functionsで依存制約と品質特性を検証する。
- 課題表の完了条件と設計整合性レビューを継続改善する。

### 17.1 成果の評価観点

手法の導入数ではなく、次を観察する。

- 仕様未達・重大バグ・回帰の発生傾向
- 設計境界の違反や破壊的変更の検出状況
- 仕様からテスト・実装への追跡可能性
- レビューでの手戻りと変更リードタイム
- テストの安定性・信頼性・実行コスト
- 文書の更新負担と参照される頻度

数字は測定方法・母集団・対象期間を揃えて評価する。形式的な完成度スコアだけで品質を断定しない。

### 17.2 設計書から新規リポジトリを初期化する

新規プロジェクトでは、設計書をコード生成の指示としてだけでなく、要求・責務・契約・品質特性・検証条件の出典として扱います。[Design-to-Repository Bootstrap](../../.agents/skills/devconcord-bootstrap-from-design/SKILL.md) は、入力資料の読取範囲と矛盾を整理してから、指定範囲に応じた開発基盤・設計資料・テスト・最小骨格を作るための専用ワークフローです。既存プロジェクトへの共通資料導入や導入済み資料の同期とは区別します。

設計書の出典・節からTASK/REQ/NFR、ADR、構造、初期課題、受け入れ条件へ必要な範囲で追跡し、読めなかった内容・仮定・未決事項を残します。要求仕様書とADRテンプレートの出典欄を使い、独立台帳や設計書の複製は必要性・共有許可がある場合に限ります。対象の既存ファイルやGit履歴は保護し、初期化範囲外の機能や成功を偽るスタブは作りません。実装済みと検証済み、実行済みの確認と将来の検証計画を区別します。

### 17.3 Bootstrap / Adoption後の設計Skill推奨

BootstrapやAdoptionで既に集めた情報・成果物・確認結果から、後続作業として専門Skillが有用かを判断する。推奨だけのために対象全体を再調査せず、Bootstrapが実施した初期設計を繰り返さない。対象プロジェクトの実態と、今回の作業で実際に確認できた根拠から、次の関係を説明できる候補だけを示す。

> 確認済みの特徴または未解決事項 → 設計上の影響 → 必要な専門的検討 → Skill → 期待成果物と検証

#### 推奨状態

| 状態 | 意味 |
|---|---|
| 実施推奨 | 重要な設計判断・不足を次の作業として検討する価値が高い |
| 後続フェーズで推奨 | 必要性はあるが、依存する要求・設計・実装が整うまで待つ方がよい |
| 現状で十分 | 確認した範囲では追加の専門Skill作業の価値が低い。設計・実装の完全性や品質保証を意味しない |
| 対象外 | 製品特性や要求から適用する必要がない |

必要な情報や証拠が足りない場合は、状態を推測せず「判断保留」または「未評価」とし、確認に必要な情報を述べる。「現状で十分」は、対象の記録や検証を確認した範囲に限る。専門Skillを利用した事実と成果物の十分性、実装・検証済みであることは別々に扱う。

#### 候補Skillの選択

次の条件は確認項目の網羅を求めるものではない。観測したプロジェクト情報と影響から必要なSkillだけ選ぶ。

| Skill | 検討する根拠の例 |
|---|---|
| `devconcord-ux-functional-design` | ユーザータスクと機能の対応、利用者とのCLI/API契約、操作や状態遷移、エラー・取消・進捗、アクセシビリティに重要な未決事項がある。GUI固有の要求はGUI製品だけに適用する |
| `devconcord-design-performance` | 大量データ、高頻度処理、重要な応答・資源制約、I/O・並列・ストリーミング等の構造判断、ワークロードや計測方法の未定義がある。根拠のない数値目標は作らない |
| `devconcord-design-robustness` | 永続データやファイルの変更、部分成功、取消・再試行・復旧、並行・非同期・外部依存、重要な整合性不変条件について未解決事項がある |
| `devconcord-design-replaceability` | 交換価値のあるUI・ストレージ・OS・通信・サービス等の依存があり、結合・移行・互換性の影響が大きい。全依存の抽象化は推奨しない |
| `devconcord-design-security` | 機密情報、外部入力、ネットワーク、権限境界、信頼を越えるデータ/制御フロー、攻撃面、セキュリティ不変条件に重要な未整理事項がある。脅威に応じ分析深度を選ぶ |
| `devconcord-documentation-architecture` | 読者・目的が複数ある、文書の重複や矛盾、公開API/CLIの案内、正本・導線・更新責務、設計と実装の整合に有意な問題がある。小規模な対象に複雑な階層を求めない |
| `devconcord-gap-analysis` | Adoption後などに複数領域の現状・要求/設計/実装/検証の関係が未評価で、横断的なFull Assessmentに価値がある。既存の有効なレポートがあれば無条件に再実行せず、Incremental Assessmentまたは該当Skillを検討する |

具体的なコード欠陥や変更の回帰リスクが詳しい調査を必要とする場合は `devconcord-repository-review` を後続候補にできる。これは設計Skill推奨の一律対象ではない。

#### 推奨の出力と境界

推奨を出す場合は、必要な候補だけを示し、Skill名、状態、対象機能/設計領域、確認した根拠と影響、未解決事項、実施時期と依存関係、期待する成果物・検証、関連するREQ/ADR/既存課題IDを含める。優先度は対象プロジェクトに既存の尺度があればそれを使い、新しい数値スコアは作らない。複数Skillの順序は実際の設計依存関係から決め、依存しない作業を不必要に直列化しない。Bootstrap / Adoptionの範囲外の作業であることを示す。関連Skillがない小さな修正にSkillを割り当てず、不要な候補を列挙しない。

推奨はSkillの自動実行・自動インストール・作業範囲拡張を許可しない。Skill間の自動呼び出しを前提にせず、専門Skillの実行結果を確認するまでは設計課題を解消済みにしない。既存の要求、ADR、課題表、リスク記録を参照し、推奨専用の台帳やスコアは作らない。

## 18. 結論

AIコーディングでは、コードの生成速度が上がる一方、誤った要求解釈・設計不整合・不十分な検証が高速に拡大する危険がある。

推奨する統合アプローチは、次の通り。

1. **Human-Centred Design / UI/UX**で利用者の目的・タスクから機能・操作・状態・受け入れ条件を導く。
2. **SDD**で要求・設計・課題・検証の対応を保ち、**DDD**で概念、用語、責務、境界を定義する。
3. **Self-documenting Code**で意図・契約・振る舞いの理解可能性を保つ。
4. **Performance / Robustness by Design**でワークロードに合う処理構造と、異常時の整合性・回復を設計段階から考える。
5. **DbC + BDD/ATDD**で前提・保証・正しい振る舞いを検証可能にする。
6. **ADR + Hexagonal/Clean Architecture**で重要な判断、トレードオフ、依存境界を管理する。
7. **選択的TDD + CI + 各種テスト + 課題表**で実装・検証・継続改善をつなぐ。

**最終的な目標は「AIに大量のコードを書かせること」ではなく、「設計の意味・制約・検証可能性を維持したままソフトウェアを進化させること」である。**
