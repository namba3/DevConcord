# リスク管理規約

> 対象: ソフトウェア開発プロジェクト共通。プロジェクトの規模・性質に応じて適用する。

## 1. 目的と管理元

リスクは、まだ発生していない不確実な事象と、その場合に起きる影響を扱う。次の区別を保つ。

| 種別 | 意味 | 管理先 |
|---|---|---|
| リスク | 将来発生する可能性がある事象と影響 | この資料のリスク記録 |
| 課題 | 既に存在する欠陥・不足・改善事項と対応作業 | 既存の課題表（`ISS-####`） |
| 技術的負債 | 将来の変更・保守・品質へ継続的な負担を生む状態 | 課題表の `技術的負債` 分類 |

この資料は将来の不確実性と残余リスクの管理元であり、対応作業の台帳ではない。軽減・調査・回避の作業は既存の課題表へ登録し、リスク記録から課題IDを参照する。顕在化して欠陥や作業が生じた場合も、対応を課題表へ登録する。リスクと課題は同じ事象を別の意味で関連付ける場合があるが、状態や作業内容を二重更新しない。

小規模プロジェクトでは、必要なリスクだけを課題表や要求仕様の詳細欄に記録してもよい。その場合も、将来の不確実性であることと、対応作業の管理先を明記する。

## 2. 記録項目

リスクには再利用しない一意の `RISK-####` IDを付ける。記録は次のテンプレートを必要な範囲で使う。

```markdown
| ID | リスク事象・影響 | 発生可能性 | 影響度 | 根拠・不確実性 | 対応・検証 | 状態 | 関連 | 残余リスク・判断 |
|---|---|---|---|---|---|---|---|---|
| RISK-0001 | （条件・事象・影響） | 未評価 | 中 | （観測事実と不明点） | （方針、検証、必要ならISS-####） | 特定 | REQ-0001、ADR-0001 | （残余影響、受容者・理由または解消条件） |
```

- 発生可能性と影響度は `低` / `中` / `高` / `未評価` の定性的な尺度を基本とする。プロジェクトで別の尺度を使う場合は定義を併記する。
- 根拠がない確率や数値は作らない。可能性が見積もれない場合は `未評価` とし、不確実性と判断に必要な調査を記載する。
- リスク事象は「もし条件Xが起きれば、事象Yにより、利用者・データ・運用などへZの影響がある」の形で具体化する。
- Robustness by Designに関する将来の不確実性（例: 外部依存の障害時にデータ整合性や復旧可能性が保てるか未検証）はリスクとして記録できる。既に確認された欠陥や実施すべき修正・検証はリスク台帳へ重複登録せず、既存課題表で管理する。
- Security by Designに関する将来の不確実性（例: 新しい信頼境界に対する攻撃経路や、採用した制御後の影響が未評価）は、既存のリスク記録で扱う。脆弱性や要件不適合が既に確認された場合、または軽減・調査・検証作業が必要な場合は、リスクの記録だけで済ませず既存課題表へ登録し、必要なら `RISK-####` と関連付ける。
- 対応欄には回避・軽減・移転・受容の方針と、検証方法を記載する。実施作業は課題IDで参照する。
- 関連IDは該当するものだけを記録する。存在しない要求・ADR・課題を形式のために作らない。
- 受容する場合は、残る影響、受容理由、判断者、適用範囲または見直し条件を記録する。

## 3. 状態とライフサイクル

状態は `特定` / `軽減中` / `受容` / `顕在化` / `解消` を使う。

| 状態 | 意味・更新条件 |
|---|---|
| 特定 | リスクを記録し、影響や不確実性を評価中、または対応方針を決めた |
| 軽減中 | 課題表で追跡する軽減・回避・検証作業が進行中 |
| 受容 | 残余リスクを権限ある関係者が明示的に受け入れ、理由と見直し条件を記録した |
| 顕在化 | 想定事象が発生した。影響と既存課題表の対応課題を関連付ける |
| 解消 | 事象の前提がなくなった、または根拠によりリスクが解消した |

新しい設計・運用条件や検証結果が得られたときは、発生可能性、影響度、対応、残余リスクを再評価する。リスクが顕在化したら影響を確認し、必要な修正・復旧・調査を課題表に登録する。作業完了だけでリスクを自動的に解消扱いにせず、受け入れ条件や検証根拠で判断する。受容済みリスクは見直し条件に該当した場合に再評価する。

記録はリスクが未解消または意思決定上重要な間保持する。解消・顕在化後も識別子と判断の履歴を残し、IDを再利用しない。

## 4. 完成度評価・リリース判断との接続

リスク管理は既存の10評価軸や重みを変更しない。未解決リスクは影響を受ける評価軸の根拠、評価の確度、主要課題への参照に反映する。重大なリスクが残る場合、総合完成度が高くてもリリース判定を `可` にしない。`条件付き` とする場合は、条件、残余影響、受容者を明記する。

## 5. 見直しのタイミング

固定周期の会議を設ける必要はない。次のイベントで関連リスクを見直す。

- 重要な要求・設計・依存関係の変更
- 想定外の検証結果、障害、脆弱性またはデータ保全上の問題
- 大きな機能追加や運用条件の変更
- リリース判断、完成度評価の更新
- リスクの前提や受容条件の変化

見直しでは、影響、根拠の新旧、関連する要求・ADR・課題、対応作業の状態、残余リスクを確認する。変更がない場合は同じ内容を繰り返し記録しない。
